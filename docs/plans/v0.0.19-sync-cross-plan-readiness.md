## 1. 一句话结论

> 0.0.18 的“同步基础”只表示**可演进的本地专业事实真源与原子 outbox**；它不等于网络同步已经就绪。跨端同步的唯一实施入口是 **Sync S0**：先冻结每种对象的 transport contract、自然键、版本、删除/恢复和远端 apply 语义，再允许 Linux 服务接收任何真实用户数据。

因此正确顺序不是“现有 outbox → 立刻写 API”，而是：

```text
0.0.17 既有生命周期/Finance 边界
        ↓
0.0.18 本地领域真源与 Garmin 真实性验收
        ↓
Sync S0：本地同步迁移 + contracts（仍不联网）
        ↓
Sync S1：Linux 服务安全空壳
        ↓
Sync S2：只对 transport-ready 的 Journal/Health 事实开放双端同步
        ↓
恢复/Android；之后才分别设计 server connector、TickTick、Finance
```

## 2. 四份计划的统一职责

| 输入 | 对同步的有效约束 | 在统一路径中的角色 |
| --- | --- | --- |
| 0.0.17 收束 | `dataDir` 切换是受控的跨窗口生命周期；Finance `.bean` 只可经本地 Finance Commit 写入；0.0.17 不做手机/Web/NAS 只是当期范围，不是否决未来 sync。 | 提供根切换与 Finance 禁区，不能被 Sync Core 绕过。 |
| SQLite Foundation | `{journalRoot}/journal.sqlite` 是新本地事实根；旧 JSON 不迁/不读/不 fallback；专业事实、UUID、source、local revision、tombstone 与原子 outbox；0.0.18 不做 API/ACK/冲突。 | 必须先验收的领域真源基础。 |
| Health 初版设计 | Health 只读消费事实与快照；缺失不等于 0；趋势/轨道/摘要均为投影；“获取更多历史”受 Garmin 采集边界控制。 | 约束数据不可被同步层伪造、聚合或反写。 |
| Linux sync 架构 | 独立 SQLite 副本、记录级 API、幂等操作、cursor、冲突保留、历史、设备身份；Finance 仅排除在 v1 实现范围外。 | 定义 Sync S0–S5；Finance v2 后续复用同一个 Core，但其 S0 只能在 Foundation 语义验收后开始。 |

所有计划共同确认的稳定边界：

- SQLite 文件不经 SMB、Git、网盘或复制同步；客户端和服务器各持独立数据库，仅传版本化事实与操作快照。
- `daily` / `routine` 是日期查询投影，不能作为网络对象、冲突对象或持久化容器。
- 上海业务日、UTC 时序、`wake_date`、无精确时刻不造时间、缺失与数值零区分，均由领域 contract 保持，服务端不重新推断。
- Garmin 是单向、只读外部来源；token、rate-limit、原始响应不进入 Sync。它的特殊性是 collector 入口与写入授权，不是另一套 Sync Core。Finance `.bean` 永远不进入 Sync v1；Finance v2 的 Transaction / Posting 在其独立计划中复用同一个通用 Core。Observation、缓存、投影与本机 materialization 不进入 Sync。

## 3. 当前计划之间必须消除的歧义

### 3.1 Foundation 的 outbox 不是 wire envelope

Foundation 中“后续 `orbita-sync` 直接消费记录快照、不能再次迁移真源”的意图应保留为：**不再重构专业事实表**。它不能被理解为“当前 v1 `sync_outbox` 可以直接发网络”。

当前 outbox 只有本地操作的基础字段；没有 server base/version、contract version、delivery ACK/retry、cursor、远端影子、inbox 去重、冲突或 replica 身份。`revision` 只在一份本地库里递增，不能比较两个设备的先后，也不能用作服务端 cursor。

统一措辞应为：

> 0.0.18 提供 Sync S0 所需的领域事实和事务 outbox 基础；网络接线前仍必须完成独立的 Sync Core migration、完整 transport snapshot、来源自然键、canonical contract、恢复语义与远端 apply 验收。不得把 v1 `sync_outbox` 直接作为网络协议。

### 3.2 Health 的“同步状态”只指 Garmin 数据更新

Health 计划顶部的成功、手动同步、失败与重试，目前只能表示 **Garmin 拉取**：最后抓取、无 token、token 无效、429 冷却及本机导入结果。它不能代表服务器已收到 outbox，不能代表其他设备已下载，也不能掩盖冲突。

Sync S2 后应有独立的全局 Orbita 跨端状态：最后远端成功、pending 数、冲突数、认证/网络错误、下次重试。两类状态不可复用 `garmin_sync_meta`，也不得把曲线缺失解释为任一种同步失败。“获取更多历史”只触发授权 collector 的 Garmin 拉取，不自动暗示服务器 bootstrap 或 push/pull。

### 3.3 data root 切换等于切换 replica

0.0.17 已要求 `dataDir` 切换经窗口 guard、重载和 Finance sidecar 重启，且不搬数据。对 Sync Core，`journalRoot`（包括自定义 root）更进一步表示**另一份本地副本**：必须停止旧 root single-flight 会话，隔离其 cursor、outbox delivery、account binding 与内存 token，再以 attach/bootstrap 流程打开新 root。不能把旧库的同步身份、cursor 或未发送 outbox 静默带去新库。

## 4. 服务端前的 Sync S0 阻断清单

下列任一项未完成时，S1 可以仅做无真实数据的服务骨架；S2 不得接收 Journal/Health 用户记录。

1. **来源自然键和投影规则。** 当前部分 v1 约束未把 `source` 放进 daily、sleep、metric snapshot、activity 的自然键，可能使 Garmin 覆盖同日手工事实。每个 type 必须选择 source-aware natural key 与投影规则，或明确其只能有单一权威来源；服务端不得猜测。
2. **完整的 type-specific transport snapshot。** 每种首发对象可独立 round-trip：带 UUID、source、领域自然键、时间字段、完整规范化 payload、tombstone 与 canonical hash。`metric_day_snapshot` 必须有 `metric_name`；Garmin nap、activity、body measurement 必须有可验证的外部键，未定者禁止入 v1。
3. **本地 Sync Core migration。** 落地 `replica`、entity remote shadow、server version、change cursor、inbox dedupe、outbox delivery、conflict。业务变更同事务冻结 `base_server_version`、contract version、hash 与完整 envelope；同一实体未确认操作严格串行。
4. **远端 apply 事务。** 远端记录、tombstone、shadow、cursor、inbox receipt 必须同一事务持久化，并处于不写 outbox 的 `apply_remote` 路径；不得复用会制造回声的普通本地 upsert。
5. **统一删除/撤销。** 现有 5 秒 undo 会清除 tombstone；协议必须明确为显式 `restore`（推荐）、新 UUID 重建或禁用撤销之一。任何选择都需覆盖离线 edit/delete、history、base version 与冲突。
6. **跨记录不变量。** `mood.primary` 是“每上海日最多一条”，不是单 ID 规则。应引入范围 version / invariant conflict，或首版不同步 primary；禁止静默 LWW。
7. **唯一 Garmin 写入者。** 首版配对时指定一台具 `garmin_collect` capability 的桌面设备；只有它能上传 Garmin source，其他客户端只 pull。服务端应按认证 capability 而非 payload `origin` 授权。未来 server connector 是独立迁移：先停桌面 collector，再切换 principal，不能双写。
8. **真实 L3 证据。** Foundation 的生产 schema、事务、不读旧 JSON、源隔离、Garmin 零 SSO/429、时间与缺失语义必须独立验收；分支有代码或局部绿测都不等于同步就绪。

## 5. 首发对象允许表

Sync S2 不按“表已出现”开放，而按 transport readiness 逐项 allowlist。推荐首发策略：

| 对象 | S2 默认 | 条件 |
| --- | --- | --- |
| `events`、`notes` | 允许 | 完整 snapshot 与本地/远端 apply fixture。 |
| `moods` | 仅 non-primary，或完成范围冲突后允许 | 不可静默产生两个 primary。 |
| `meals`、手工 `naps`、手工 `activities` | 允许 | 手工 natural key、可选时间与 tombstone/restore 已验收。 |
| Garmin daily / sleep / metric snapshot / nap / activity | 仅 collector 写、其他端 pull | 每 type 的 source natural key、外部键和完整 snapshot 已验收。 |
| `body_measurements` | 暂不开放多端写 | 同日多测量、external identity、自然键、摘要选择仍未定。 |
| `daily`、`routine`、趋势/轨道缓存 | 禁止 | 它们是派生投影，不是事实。 |
| Finance、TickTick、原始 FIT、token、App State | S2 禁止 | Finance 仅待其独立计划接入同一 Core；其余各有凭据、大对象或写入边界。 |

## 6. 统一实施与验收顺序

### A. 完成 0.0.18 本地领域真源

不启动网络。完成 Foundation 的替换矩阵、production-schema 测试、Garmin probe/规范化、数据源隔离、日期语义和 Health 查询/UI 验收。Health 只读投影不得反向驱动事实写入。

### B. Sync S0：本地协议冻结

仍不接真实 Linux 服务。建立 `contracts/` v1：每 type schema、canonical JSON/hash、自然键、错误码、脱敏 fixtures；执行本地 v2 sync migration；完成上述八个阻断项。用两份独立桌面库模拟离线、崩溃、重复 operation、root 切换、冲突与 restore。

### C. Sync S1：Linux 安全骨架

仅建立 Tailscale-only ingress、account/device enrollment/revoke、服务端 SQLite migration、health/readiness、备份/runbook 和 contract tests。此阶段不因“API 已启动”宣称数据同步可用。

### D. Sync S2：受限的真实收敛

开放 allowlist 对象的 push/pull、`op_id` 幂等、server version/change cursor、历史、冲突与可见状态。Garmin 只由指定 desktop collector 写；客户端显示 Garmin 更新与 Orbita 跨端同步两个独立状态。

### E. 后续独立计划

- S3：180 天历史、tombstone 回收、加密备份、隔离恢复演练与 RPO/RTO。
- S4：Android 本地库、bootstrap/换机与兼容矩阵。
- Server Garmin connector、TickTick：分别处理 OAuth/token、限流、单一写入者迁移与用户体验。
- Finance：在同一通用 Sync Core 上使用自己的 canonical Transaction / Posting aggregate，再经单一 materializer → Finance Commit → `.bean` reconciliation；绝不复用 Journal 的领域协议直接写账。

## 9. 交付判定

在 A 完成前，不得称“本地已具备可联网同步能力”；在 B 完成前，不得让 Linux 服务接收真实数据；在 C 完成前，不得称“服务已保障同步”；在 D 的对象级矩阵全部通过前，不得称“Journal/Health 已跨端同步”。

这条纪律保留 0.0.18 的本地价值，也防止服务端替尚未定案的来源、删除、时间或投影语义作不可逆决定。
