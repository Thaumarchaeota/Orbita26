# v0.0.19 Orbita Sync：可部署 Linux 与第三方连接器生产计划

> **状态**：部署级架构与实施计划，尚未授权部署。目标不是“API 能启动”，而是完成后能在深圳 Linux 上被实际配对、持续同步、可恢复地使用。
>
> **范围**：桌面 Sync Core、`contracts/`、独立 Linux `orbita-sync`、Journal/Health 跨端同步、Garmin 服务器 connector、TickTick（滴答清单 / Dida）服务器 connector、部署/备份/恢复/切换 runbook。
>
> **前置**：[`v0.0.19-sync-cross-plan-readiness.md`](v0.0.19-sync-cross-plan-readiness.md) 的本地语义与 Sync S0 阻断项；0.0.18 遗留的 L3 本地真源、Garmin 实机与 Health 验收。未满足前，不部署真实用户数据服务。

## 1. 交付定义

本计划完成后，用户应能够：

1. 在一台已配对桌面设备离线记录 Journal / Health，恢复网络后可靠同步到 Linux，并在另一台设备恢复；重复请求、断网、服务重启和冲突不丢数据。
2. 在 Linux 上看到不含内容的服务健康、备份新鲜度、设备、积压和冲突状态；可以撤销设备，并从一致性备份进行隔离恢复。
3. 由服务器作为唯一 Garmin connector 拉取并规范化健康事实；客户端只读取这些 Garmin 事实。
4. 由服务器作为唯一 TickTick API caller；Schedule Adapter 只将已存在的 Orbita Schedule 映射到 TickTick，并经 Sync Core 的受控 adapter commit 回写已确认的外部变化。Orbita SQLite Schedule 始终是本地事实源。

“容器已启动”“能访问 health endpoint”或“桌面本机 Garmin 仍能拉取”均不构成生产可用。所有四项达到验收才可称为本计划完成。

```text
Desktop / Android（各自 SQLite、Sync Core、离线操作）
       │   Tailscale HTTPS + device identity
       ▼
tailscale Serve ──► 127.0.0.1:8787 ──► orbita-sync API
                                            │
                      server SQLite: current / operation / history / conflict
                         │                 │                    │
                 backup + restore     Garmin worker        TickTick worker
                                          │                    │
                                       Garmin              Dida/TickTick
```

## 2. 已可复用与必须新写的边界

| 能力 | 当前可复用 | 必须新写 / 重做 |
| --- | --- | --- |
| Journal/Health | 专业事实表、本地 revision/tombstone、事实与 outbox 原子事务、Garmin 规范化入库。 | Sync Core 的远端影子、cursor/ACK/retry/conflict、完整 envelope、remote apply 无回声。 |
| Garmin | Python token-only fetch、错误分类、日/睡眠/活动/体测/时序规范化、内容 hash 去噪。 | Linux runtime/container、credential vault、单一调度/限流、server principal、切换/回滚；不得搬 Windows 路径、代理探测或 token 文件。 |
| TickTick | Dida OAuth 授权码交换、项目/任务 CRUD、完成→3 秒 undo、due/start 语义。 | 服务端 OAuth callback、PKCE/state、refresh/token lifecycle、加密凭据、任务镜像、command outbox、幂等/对账、轮询与切换。 |
| Linux | Debian/Tailscale/SSH/存储与断电恢复基线。 | Docker/Compose、专用 appdata/backup 根、服务、备份 timer、恢复演练、Tailscale Serve、告警与访问控制。 |

`services/sync/` 与 `contracts/` 当前仅有目录边界；不能假定已有可部署服务。Finance `.bean`、原始 FIT、App State、SQLite 文件、Garmin/TickTick token 都不进入 Journal/Health sync payload。

## 3. 发布阶段与停止线

### P0：0.0.18 本地真源收口（不联网）

完成 Sync S0 的全部前置：source-aware natural key 或明确单源对象、每 type 完整 snapshot、canonical JSON/hash、`restore`、primary mood 不变量、replica/root 语义、Sync Core 本地 migration 与 L3 证据。

**停止线**：缺 `metric_name` / 外部键、outbox 不能 round-trip、remote apply 会回声、或 Garmin source 可被普通设备伪造时，不得进入 P1/P2 数据接入。

### P1：契约与客户端 Sync Core（无生产数据）

- `contracts/journal-health/v1`：versioned schema、canonical hash fixtures、错误码、对象 allowlist、兼容矩阵。
- `journal.sqlite` v2（或等价独立同步库）：replica identity、entity server shadow、cursor、inbox dedupe、delivery、conflict；业务写入同事务冻结 `base_server_version`。
- Sync worker：每实体串行、单飞、退避、root detach/attach、remote apply transaction、独立 UI 状态。
- 两独立本地库完成离线、重放、服务已提交但响应丢失、客户端 apply 崩溃、delete/restore、冲突、换 root 的测试。

**停止线**：本地 revision 不可作为远端版本；未 durable apply/ACK 前不得清 outbox。

### P2：Linux `orbita-sync` 与可用 Journal/Health 同步

先交付真正可用的核心同步，首发 allowlist 为 `events`、`notes`、合规 `moods`、`meals`、手工 nap / activity，以及已逐项满足 transport contract 的 Garmin facts。未成熟对象（尤其 body measurement 多测语义）返回 `not_supported`。

服务端实现：account/device/capability/enrollment/revocation、operation receipt（`op_id` 幂等）、current/version/history/tombstone/conflict、条件写与 change cursor、push/pull 分页、IDOR 防护、大小/速率限制、health/readiness、脱敏日志与单一 retention worker。

**P2 验收**：两台真实桌面独立 replica 完成 bootstrap、离线新增/编辑/删除/恢复、同 ID 并发冲突、网络中断重放、服务重启、撤销设备、根切换与 history restore；不通过任何一项，不能称“Linux 同步可用”。

### P3：Linux 生产运行与恢复

完成专用目录、Compose/systemd、Tailscale Serve、加密备份、恢复演练、容量/备份/错误告警和 RPO/RTO 责任。P2 运行在生产拓扑后才有用户价值；S1 空壳不单独交付为“已部署”。

### P3.5：首次数据迁移与写入权切换（必须有水位）

“第一次以 PC 为源，之后以 NAS 为库”不能实现成一次全量复制后立即双向写。正确模型是：**PC 是首次种子的临时权威副本；服务器随后成为 Orbita 同步 current/history/conflict 的协调权威；Garmin 是外部事实源，TickTick 只是由 Schedule Adapter 管理的外部映射。**

| 数据类 | 初始迁移时的权威源 | 稳定运行后的写入/裁决 | 绝不发生的事 |
| --- | --- | --- | --- |
| Journal、手工 Health | 指定的一台 PC seed replica | 任一客户端可离线写；服务器按版本/冲突裁决并保存历史 | 服务器直接覆盖未同步的本地修改，或客户端文件复制 DB。 |
| Garmin Health | Garmin；PC 仅是暂时 collector | Garmin 仍是事实源；G1 后 server connector 是唯一导入者，客户端只 pull | 把 NAS 当 Garmin 数据的业务源，或 desktop/server 双 collector。 |
| TickTick Schedule 映射 | Orbita Plan Schedule（经确认的外部映射） | Orbita SQLite Schedule 仍是事实源；W1 后服务器是唯一 API caller / command executor | 把 TickTick 当 Orbita Work/Plan 真源，或 desktop/server 双写。 |
| Finance | 现有 PC `.bean` | 仍只经 Finance Commit | 本计划同步或迁移 `.bean`。 |

#### M0：迁移前冻结与可回退证据

1. 选择唯一的 **seed PC**、唯一 `journalRoot` 和一个明确 account；其他设备在迁移窗内只读或不接入，不能成为第二个 seed。
2. 完成 P0/P1 的 schema、snapshot、restore、source key 与 Sync Core 验收；记录桌面版本、contract version、source replica ID、待发 outbox 水位。
3. 用 SQLite 一致性 backup API 生成 seed PC 的只读迁移快照，校验完整性；旧 JSON 仍不读、不导、不改。此快照是回滚证据，不上传为服务器 SQLite 文件。
4. 迁移期间新本地写入继续成功，但必须进入“snapshot cutoff 之后的 delta outbox”；UI 显示“正在初始化，尚未可跨设备确认”，不得显示已同步。

#### M1：空服务器建立 seed checkpoint

1. 服务器创建空 account、device/replica registration 和一次性 seed session；拒绝非空 account 的“重新 seed”操作，避免误覆盖已有 history。
2. PC 上传的是 contract 的逐记录 seed snapshot：current facts、未过期 tombstone、type/source/natural key、canonical hash，以及固定 cutoff 前的本地水位；不是 SQLite、JSON 年文件或 App State。
3. 服务端单一事务/受控批次写入 current、initial history、server version 和连续 `change_seq`，并生成不可变 `seed_id` / `seed_cursor`。任何一批失败只可重放同一 seed session，不能混入普通同步操作。
4. PC 在本地事务写入每实体 `server_version`、`seed_cursor` 与同步影子；只有被 seed checkpoint 覆盖的 outbox 才能 ACK。cutoff 之后产生的 delta 保持 pending，随后按普通 push 发送。

#### M2：对账、转向与第二设备 bootstrap

1. 对每个 allowlist type 对账：有效记录数、tombstone 数、自然键唯一性、canonical hash、Garmin external key 与抽样业务字段；任何不匹配停止，不让第二设备接入。
2. 对账成功后，服务器成为该 account 的同步协调权威：PC 不再“全量推覆盖”，只按 `base_server_version` 推送自己的 delta；服务端 current/history/cursor 成为恢复来源。
3. 第二设备只执行分页 pull/bootstrap，完成本地事务与 cursor 落盘后才开放写入；不得把 seed PC 的 DB、token 或 cursor 复制过去。
4. 回滚仅在没有其他设备写入或已完整导出/处理其 delta 时可进行：停 ingress、保留服务端 DB 与 PC snapshot，恢复为 seed PC 单机模式。迁移后已有多端操作时，不允许以旧 PC 全量覆盖服务器。

#### M3：Garmin collector 切换（PC → server connector）

P2 初期 PC 可以持有唯一 `garmin_collect` capability，以已验证的桌面逻辑导入 Garmin 事实并同步上行。G1 切换必须是单写入者状态机：

```text
desktop collector active
  → drain（停止新 fetch，Garmin outbox ACK 到最终水位）
  → server connector observe（重叠窗口只抓取/对账，不写 current）
  → server connector active（唯一 writer）
  → desktop pull-only
```

server observe 要以 Garmin external key 和 canonical hash 比对日摘要、sleep、metric snapshot、nap、activity；任一 type 未具稳定自然键则该 type 不切换。回滚必须先停止 server writer、记录最终 cursor，再恢复一台 desktop collector，永不并行导入。

#### M4：TickTick direct desktop → Schedule Adapter 切换

TickTick 是 Schedule 的可移除外部映射，不是 Orbita Work / Plan 的事实源。切换顺序为：

```text
desktop direct API
  → server OAuth + read-only mirror / 对账
  → desktop write freeze（仍可读）
  → server command broker active（唯一 API caller）
→ clients write local Schedule facts / pull confirmed adapter commits
```

切换前必须对 Schedule 映射、due/start 与外部任务状态对账。切换期间桌面不再直接调用 Dida；离线 Schedule 编辑先写本地事实，经 Core 接受后由服务器按 `command_id` 执行外部动作。若第三方 create 的幂等性无法被 correlation marker + read-after-write 证明，则超时 create 停在人工确认，不可自动重发。回滚前先暂停 server command worker、清点 pending command 并取最终 TickTick 映射；不得恢复双写。

### G1：Garmin server connector 迁移

目标是 Linux 成为唯一 Garmin writer。此阶段在 P2/P3 后独立发布，不能和基础同步混作一次不可观察的大迁移。

1. 实现独立 worker、account-scoped lease、持久 `next_run_at` / `cooldown_until` / `last_successful_window` / 审计和可见 connector 状态。
2. 凭据采用独立加密 vault；显式服务端重新授权或受控导入，**不自动拷贝**桌面 token；无 token=`no_token`、无效=`token_invalid`、429 进入冷却，零 SSO fallback。
3. 每账号只有 server connector principal 可 `write:health:garmin`；抓取按保守滚动窗口和显式历史回填队列，拆成可中断日期批次。
4. 切换：桌面 collector drain（停止新抓取 → ACK 现有 Garmin outbox → 记最终水位）→ server 首次只读重叠抓取和外部键/hash 对账 → 启用 server writer → 撤销 desktop `garmin_collect` capability。
5. 回滚：先停 server writer、记录 cursor/未完成窗口，才可将 capability 交回一台桌面；绝不双写。

服务端 connector 只写同一规范化事实/change-log 内部入口；不直接碰客户端数据库、不会上传原始响应/FIT/token，也不能阻塞普通 Journal 同步。

### W1：TickTick / Dida Schedule Adapter 迁移

Orbita Plan Schedule 是事实源。Orbita server 是唯一 TickTick API caller、可靠命令执行者和外部映射缓存；它不是与 TickTick 双主的任务库，也不替 TickTick 创建 Work Object。

1. 新建服务端 OAuth：HTTPS callback、短寿命授权 transaction、PKCE + state/CSRF 校验、加密 access/refresh token、scope/expiry/revoke 信息。首先实测 Dida OAuth redirect URI 能否改为服务器；不行时另设一次性 desktop authorization broker，绝不上传普通 desktop token。
2. 新建 `schedule_command` outbox：`command_id`、client/origin、预期 Schedule revision/hash、external task id、payload hash、attempt、结果摘要与状态。create 遇到“第三方已接受但超时”不能盲重试；需 correlation marker + read-after-write 对账，不能证明幂等时进入人工确认。
3. server worker 串行执行 provider 写命令并保守 polling/按需刷新；不承诺未验证的 webhook 或增量 cursor。外部人工修改经受控 adapter commit 与离线 Schedule 编辑形成 Core aggregate conflict，UI 可处理。
4. 切换：先把现有 due/start 映射固化为 adapter contract → 服务端授权和首次 Schedule/external-task 对账 → 桌面停止直连观察 → 启用 server 唯一 caller → 删除或使本机 token 失效并让 UI 改调 Orbita API。
5. 回滚：先暂停 server command worker，导出并处理 pending command 和最终 provider fetch，才恢复一台桌面直连；不允许双写，也不回滚已保存的 Orbita Schedule 事实。

## 4. Linux 部署蓝图

### 网络与存储

```text
Tailnet HTTPS → tailscale Serve → host 127.0.0.1:8787
                                      ↓
                               Compose private network
                                      ↓
              NVMe /srv/appdata/orbita-sync/state/server.sqlite
                                      ↓
             一致性加密备份 → 非 SMB HDD backup 根 → 异地冷备
```

- 无公网端口、无 LAN `0.0.0.0` listener、无数据库端口、无 SMB 访问运行数据库；Tailscale 仍之外还要 device auth。
- API/worker 是非 root 用户；容器 read-only rootfs、最小 RW volume、`no-new-privileges`、资源限制、私有 bridge network。
- `state` 在 NVMe 的 `/srv/appdata/orbita-sync`，权限 `0700`；一致性备份在非 SMB `/srv/storage/backup/orbita-sync`，权限 `0700`。不可把运行 DB 放 mergerfs/NFS/网盘同步目录。
- 配置在受限 `/etc/orbita-sync`；secret 不进 Compose、Git、镜像、日志或 shell history。设备私钥只在客户端 OS secure storage，服务器只存 token hash/public key/capability/撤销记录。

### 服务形态

- Compose 以不可变 image digest 发布，仅 loopback `127.0.0.1:8787:8787`；无 repo bind mount、无 `latest`、无自动 Git 部署。
- `orbita-sync.service` 在 Docker、tailscaled、挂载和网络就绪后启动；Compose 负责进程重启。独立 backup service + timer 调用应用内 SQLite online backup，不裸复制活跃 WAL 文件。
- `/health/live` 只判进程；`/health/ready` 判 DB transaction、migration、容量及备份新鲜度，不泄露业务内容。
- `tailscale serve` 配置是发布验收的一部分；服务本地 ready 但 tailnet 不可达，视为部署失败。

### 初次部署与配对

1. 确认 Debian/Tailscale/NTP/NVMe/HDD backup mount、Docker Compose、SSH key 与 ACL；现有 SMB 不作为该服务部署对象。
2. 建专用用户/目录/密钥，启动 P2 所需 image，运行唯一 migration，配置 Serve；从另一台被授权 tailnet 设备验证 HTTPS、无公网/LAN/DB 暴露。
3. 仅通过受控服务器 admin CLI 生成短寿命、一次性 enrollment invite（服务仅留 hash）；不在日志/截图/文档写出邀请码。
4. 客户端为每个 journalRoot 新建 `replica_id` 与 device key，经 invite 配对；先完成 pull/bootstrap，再允许真实 push。新 root/换机总是新 replica + 新 invite。
5. 完成一个 fixture account 的 smoke 和隔离 restore 后，才配对真实数据 account；随后按 P2/G1/W1 的分别门槛开放能力。

## 5. 运行、备份与事故处理

- 每日一致性备份、每次发布/migration 前即时备份；HDD 本地加密副本与既定异地加密冷备。建议首期确认 RPO ≤24h、RTO ≤4h；若未确认，不能称生产 ready。
- 180 天 history 与 tombstone 保留是业务策略；备份轮转不能替代 history/tombstone。tombstone 至少覆盖最大离线窗口与安全余量。
- 指标只含元数据：DB/磁盘、backup age/result、restore drill、migration、API/push/pull/error/dedupe/conflict、active/revoked devices、outbox age，及后期 connector lag/cooldown。日志绝不含 snapshot、健康正文、token 或 OAuth code。
- DB 满、backup 过期或 migration 失败时 readiness 失败并停止接收新远端写；客户端继续本地写和 outbox。不得自动删除 current/history/tombstone 来“恢复”。
- 恢复只可：停 API → 隔离路径恢复一致性加密备份 → integrity/schema/current-oplog 校验 → 测试客户端 pull → 维护者确认 cutover → 恢复 ingress。禁止用 SMB 或活 WAL 文件覆盖运行库。

### 可诊断性是 P2/P3 的上线门槛

同步系统不得只给“成功 / 失败”两个状态。每个操作必须能以 `op_id` 跨端追踪下列 durable 阶段；没有记录到哪一步，就必须诚实显示“未知，保留待重试”，绝不伪造成功：

```text
local fact committed → local outbox durable → request attempted
→ server accepted | rejected | conflicted | deduplicated
→ remote change delivered → remote durable apply → client ACK
```

每条诊断事件只允许含：`op_id`、脱敏 account/device/replica 摘要、record type、kind、local/server version、cursor、结果码、时间和 correlation ID。**禁止**含 snapshot、随记正文、心情/健康值、OAuth code、token、凭据或原始第三方响应。

生产实现必须提供：

1. **客户端 Sync Doctor（后续 Windows/Android 任务）**：本地 outbox 数、最早 pending、最后 server cursor、最后成功、冲突、retry 分类和 root/replica 身份；只导出脱敏诊断包。
2. **服务器 operation timeline**：按授权 account/device/op 查询 operation receipt、current/history 版本、delivery/ACK、conflict、connector run 与 correlation ID。普通用户只能看自己的脱敏记录；本机受控 admin 才可进行跨设备恢复审计。
3. **错误分类与行动语义**：例如 `offline`、`auth_expired`、`device_revoked`、`contract_upgrade_required`、`retryable_server`、`conflict_pending`、`connector_cooldown`、`provider_ambiguous_create`。每个码必须规定“自动退避 / 用户重试 / 必须 resolve / 必须重新授权”，不能把内部错误原文直接返回。
4. **脱敏 support bundle**：可选导出最近有限 operation timeline、版本/迁移/backup 状态、指标和错误码；导出前自动检查不含业务 payload 或 secret。
5. **确定性故障演练**：协议模拟器必须覆盖服务端已提交但响应丢失、客户端 apply 崩溃、cursor 中断、冲突、Garmin writer 切换、TickTick ambiguous create；每个场景都断言医生/时间线能定位责任边界。

Garmin 数据更新、Orbita 跨端同步、TickTick command broker 是三条独立链路：一个失败不应把另两个显示为失败或“未同步”。若 P2/P3 没有上述诊断面、operation audit 或脱敏测试，即使数据看似能同步，也不得部署真实用户数据。

## 6. 部署授权与产品决策清单

开始实际 Linux 部署前，需要维护者明确提供或确认：

1. Docker/Compose、专用 appdata/backup 目录、systemd/timer、Tailscale Serve 与 SSH 管理权限。
2. tailnet ACL/允许设备、稳定 Serve 名称、account 模型、invite 有效期与设备撤销责任人。
3. RPO/RTO、备份频率/保留、加密及密钥托管/灾难恢复责任。
4. Sync S0 的 source keys、restore、primary mood、body measurement、最大离线期/tombstone 决策。
5. Garmin 与 TickTick 凭据何时被明确授权迁移到服务器；初次 P2 部署不得默认取得它们。
6. Dida OAuth 应用是否允许服务器 HTTPS redirect URI；若不允许，须先批准单独授权 broker 设计。

## 7. 最终验收矩阵

| 范围 | 最低真实证据 |
| --- | --- |
| P2 同步 | 两真实 replica 的 bootstrap、离线 CRUD、冲突、delete/restore、重复/超时、服务重启、撤销、root 切换与 history restore；每个 allowlist type round-trip。 |
| Linux | 重启/断网恢复后 Serve/API/backup timer 正常；tailnet HTTPS 可达，公网/LAN/DB 不可达；备份隔离恢复成功；日志无敏感数据。 |
| Garmin G1 | 无 token/无效/429/网络中断/重叠窗口/重复活动/缺失指标/切换回滚均正确；服务端与桌面 collector 从不同时写。 |
| TickTick W1 | OAuth 撤销/失效、429/5xx、超时 create、完成→undo、外部人工编辑、离线 command 冲突、切换/回滚均无重复任务或静默丢失。 |
| 恢复 | 从加密备份恢复 current/history/conflict/cursor/connector metadata；按已确认 RPO/RTO 达标。 |

## 8. 不得借此扩大范围

- 不将 Finance、`.bean`、原始 FIT、App State、AI/第三方 token 或 SQLite 文件塞入同步 payload。
- 不用 “server connector” 为由引入自动 Garmin SSO、凭据静默复制、双 collector、双 TickTick writer 或无限重试。
- 不因服务器上线而回退客户端离线优先；connector 故障不能阻塞 Journal/Health 本地写入和一般跨端同步。
- 不在未完成 P0/P1/P2 证据时把 Linux service、Garmin 或 TickTick connector 宣称为已可用。
