## 1. 目标与边界

### 1.1 要做什么

1. **功能对齐**：从 BKeasy 参考实现提取全部仍有效的 Finance 行为，在 Orbita Insight 中可验收地复现。
2. **架构重构**：前端采用 Shell / Layout / Surface / Content 分层（见 §2），消除滚动、层叠、居中等布局特例渗透业务逻辑的问题。
3. **契约收口**：Parser、Validate、Commit 的职责与错误语义在前后端一致；所有写盘必经 Finance Commit。
4. **交互可预期**：保存、确认、校验失败、加载未完成、离开未保存等路径有明确反馈，不得吞错或伪造成功。

### 1.2 不做什么

与 [`specs/orbita-finance.md`](../../specs/orbita-finance.md) §1、§6 一致，本计划**不包含**：

- 手机端、NAS、公共 Web API
- Rust 重写 Parser / Commit；不引入 BQL（Beancount 仅作为既有 Python sidecar 内的候选账本校验依赖，见 §25.2）
- 未经受控结构工作流的账户 open 行改动；账户/分类仅允许按 §25.10–§25.11 创建、删除或迁移
- 跨日拖拽、`seq` 落盘、`*_inv.bean` 读写
- 自动 dataDir 迁移、未经确认的 AI 写账
- Panel 记一笔、Dashboard 真实指标 API（可保留占位）
- 代码层 `bkeasy` → `ledger` 批量改名（另立兼容计划）

### 1.3 文档优先级

发生冲突时：

1. 用户已验收的现行行为（`CURRENT.md`）
2. 本计划（重构范围与验收）

4. `reference/20260717_BKeasy/` 与 `docs_legacy/v0.0.17-ledger.md`（历史证据，解释「原 BKeasy 怎么做」）

## 2. 前端架构契约（功能向，非视觉）

重构后的前端须满足下列**可测试契约**；具体 DOM/CSS 可调整，但不得破坏这些行为边界。

### 2.1 四层分离

| 层 | 职责 | 禁止 |
| --- | --- | --- |
| **App Shell** | 视图路由、keep-alive、滚动位置记忆、懒加载首次进入回调 | 猜测 `#detail-list` 等全局 ID；内嵌布局算法 |
| **Layout Engine** | 单栏/双栏 grid、折叠右栏、居中、`max-width` | 业务字段、保存状态机 |
| **Chrome** | 顶栏标题、返回、筛选开关、全局保存按钮、右栏折叠 | 列表渲染、Parser 调用 |
| **Surface / Content** | 列表、表单、导入区；各自注册滚动根 | 跨 surface 的 `z-index` 竞争 |

### 2.2 滚动契约

| 视图 | 滚动根 | 注册方式 |
| --- | --- | --- |
| Dashboard / 统计 / 导入 | primary surface 的 `.finance-scroll` | `getScrollTargets().primary` |
| 明细列表 | 虚拟列表根（delegate） | `getScrollTargets().primary` 指向 virtual root |
| 明细右栏记一笔 | secondary surface 的 `.finance-scroll` | `getScrollTargets().secondary` |

keep-alive 存储：`{ view, primary: number, secondary?: number }`。

### 2.3 层叠契约

- Finance 页面根节点 `isolation: isolate`，内部层叠不泄漏到 admin titlebar。
- **主内容区禁止 `z-index`**；仅 chrome、toolbar 下拉、popover、拖拽中条目可提升层级。
- 双栏布局使用 **CSS Grid 真并排**，禁止 `absolute + translateX` 作为主布局手段。

### 2.4 模块通信

- 禁止跨模块 `getElementById("save-btn")` 等全局 ID；由 mount 返回 **handle**（保存按钮、滚动根、筛选容器）。
- 子系统间通过 **ledger store 事件**（如 `onDetailMutated`）或显式回调通信。

## 3. 运行时与连接（功能）

> 源：`reference/20260717_BKeasy` 无 Tauri 层；行为以 Orbita 现行定案 + BKeasy API 语义为准。

### 3.1 启动与连接序列

```text
ledger_api_base → GET /health → GET /api/settings → GET /api/accounts
→ 四组账户总数 > 0 → 进入 Dashboard；并行/异步 loadDetail
```

| 场景 | 必须行为 |
| --- | --- |
| Panel / Agent 启动 | 不启动 Python |
| Insight 打开 | 异步 ensure Service；**不得**阻塞窗口显示 |
| 连接 base | 仅用 Rust 返回的实际 base；**禁止** fallback `:8000` |
| health OK 但账户为空 | 「资产管理服务未就绪」；说明需要 `account.bean`、`category.bean`、`ledger/*.bean` |
| 连接失败 | 可见错误 +「重试」；重试 = reset base → restart sidecar → reconnect |
| 非空 `bill/` 初始化 | 「新建（覆写）」须 `window.confirm`；禁止静默覆盖 |
| Orbita 退出 | 结束本进程启动的 Python child |

### 3.2 错误反馈（连接层）

| 条件 | 用户可见结果 | 禁止 |
| --- | --- | --- |
| sidecar 未启动 / 端口错误 | 标题 + 可行动说明 + 重试 | 空白页、无限 loading |
| venv 缺失 / spawn 失败 | 指向 `%TEMP%\orbita-ledger.log` 或等价排错入口 | 吞 stderr |
| 历史进程占用错误数据根 | 重试后新进程读正确 `{dataDir}/bill` | 认领孤儿 `/health` |

### 3.3 dataDir 切换

- 换目录 = 换一套数据，**不迁移**。
- 切换后：webview 重载、可 rebase 路径清空、sidecar 重启读新 `{dataDir}/bill`。
- 新空目录：Finance 未就绪；**不得**显示旧账本数据。

## 4. 数据根与存储不变量

### 4.1 目录布局（唯一支持）

```text
{dataDir}/bill/
├─ account.bean
├─ category.bean
├─ ledger/{year}.bean          ← 默认 write target
└─ .bkeasy/settings.json       ← { "write_target": "ledger/YYYY.bean" }
```

### 4.2 bean 格式不变量（Parser / Commit 共同遵守）

| 项 | 规则 |
| --- | --- |
| 交易头 | `{date} {flag} "{payee}" "{remark}" {tags}` |
| posting 行 | 至少 2 空格缩进；account 左对齐 pad 30；`{amount:.2f} {currency}` |
| 类型元数据 | `bkeasy-type: "{type}"` 行保留（键名不改） |
| 块分隔 | 条目之间 `\n\n`；文件末尾保留换行 |
| open 注释 | `;一级:二级` / `;短名`；`;` 后无空格 |
| 跨币种 | posting 尾 `@@ {cost_amount} {cost_currency}` |
| inv 文件 | 不 parse、不 commit、不在 UI 展示 |

### 4.3 内存扩展字段（仅前端）

| 字段 | 含义 | 进 API / bean |
| --- | --- | --- |
| `_is_new` | 本会话新建 | 否；commit 时生成新 id 语义 |
| `_deleted` | 软删，待 commit 过滤 | 否 |
| `seq` | 同日内排序键 | 否；**不落盘** |

## 5. Finance Parser（读路径）

> 源：`reference/20260717_BKeasy/services/parser.py`、`render.py`（逆过程）、`orbita/python/ledger/services/parser.py`。

### 5.1 职责边界

- **只读**：解析 bean → `Entry[]`；不修改文件。
- 缓存：按文件 `mtime` 缓存解析结果；commit 后须 `invalidate_parse_cache`。

### 5.2 解析规则

| 步骤 | 行为 |
| --- | --- |
| 识别交易头 | 正则：`^(\d{4}-\d{2}-\d{2})\s+(\S+)\s+"([^"]*)"\s+"([^"]*)"(.*)$` |
| 元数据行 | `bkeasy-type: "{type}"` → 覆盖推断类型 |
| posting 行 | `^\s{2,}(\S+)\s*(.*)$`；尾部分解析 amount/currency/`@@` 成本 |
| 空行 / `;` 注释 | 跳过 |
| 类型推断 | 无 metadata 时：`Expenses:` → expense；`Income:` → income；否则 transfer |
| 隐式金额 | 恰一条 posting 金额为 0 时，填平使合计 ≈ 0（`_fill_implicit_amounts`） |
| 默认币种 | 空 currency → `CNY` |
| Entry.id | `{source_file}:{source_line}`（头行号） |

### 5.3 加载后处理

| 函数 | 行为 |
| --- | --- |
| `assign_initial_seq` | 按文件行序同日赋 `a0`, `a1`, … |
| `sort_for_display` | 日期降序 → 同日内 seq 降序（新在上） |

### 5.4 `GET /api/entries`

| 参数 | 语义 |
| --- | --- |
| `date_from` / `date_to` | 含端点；空=不限 |
| `limit` / `offset` | 分页；`has_more` 表示还有更多 |
| 响应 | `entries`, `total`, `has_more`, `date_min`, `date_max` |

### 5.5 Parser 验收用例（smoke 移植）

| ID | 断言 |
| --- | --- |
| H0 | `write_target` 可读（默认当年 `ledger/YYYY.bean`） |
| H1 | `parse_write_target` count > 0（样例数据） |
| H2 | 全量 `validate_entries` 无错 |
| H3 | 含 metadata 的条目 type 正确 |
| H4 | 无 metadata 时 posting 推断 type |
| H5 | `render_entry` 含 `bkeasy-type` 行 |
| H6 | `assign_initial_seq` 同日 `a0,a1,…` |
| H7 | commit 排序为日期升序、同日内 seq 升序 |
| H8 | posting 推断 expense |
| H8b | `list_accounts` 四组非空；无 Equity；`name` 无 `;` |
| H9 | 运行时 API entries 带 seq |

## 6. Finance Validate（校验路径）

> 源：`reference/20260717_BKeasy/services/validate.py`、`POST /api/validate`。

### 6.1 职责

- Commit **前**校验候选 `Entry[]`；**不写盘**。
- 返回**全部**错误或首错均可，但前端须能定位**第一条**到 UI 字段。

### 6.2 单条规则

| 字段 | 规则 | 错误 field |
| --- | --- | --- |
| `type` | ∈ `expense` \| `income` \| `transfer` \| `inv` | `type` |
| `date` | `YYYY-MM-DD` 可解析 | `date` |
| `flag` | 非空 | `flag` |
| `postings` | 至少 2 条 | `postings` |
| `postings[i].account` | 非空 | `postings[i].account` |
| `postings[i].amount` | ≠ 0 | `postings[i].amount` |
| 配平 | 单币种：Σ amount ≈ 0（ε=0.001） | `postings` |
| 跨币种 | 无 `@@` 成本 → 拒绝 | `postings` |
| 跨币种+成本 | 成本币种计入后未标注币种须配平 | `postings` |
| `source_file` | 必须等于当前 `write_target` | `source_file` |

### 6.3 前端配平预览（不等同 validate）

- inline 编辑金额时，**客户端** `validatePostingBalance` 实时更新条目 badge（✓ / 未配平）。
- 预览失败**不阻止**编辑；保存时 validate 仍可能失败。

### 6.4 Validate 失败反馈

| 阶段 | 行为 |
| --- | --- |
| 保存第一次点击 | `saveLock=checking`；按钮 spinner + 禁用 |
| validate 返回 errors | 回 `edited`；**首错条目** `field-error-block` + `scrollIntoView`；保存钮 **shake 350ms** |
| 网络/500 | shake；**不**进入 confirming |

## 7. Finance Commit（写路径）

> 源：`reference/20260717_BKeasy/services/commit.py`、`api/commit.py`。

### 7.1 职责边界

- **唯一常规写盘路径**；记一笔、inline 编辑、软删、拖拽、CSV 导入均只改内存，须经 Commit 落盘。
- 按**整文件**覆写 write target；不得以局部列表覆盖未加载部分。

### 7.2 提交流程

```text
内存活跃条目 → buildCommitPayload → POST /api/validate（保存态机第一次）
→ 用户确认 → POST /api/commit → 服务端 sort_for_commit → render_file → atomic_write
→ 前端 loadDetail(true) → 更新 baseline → 清除 confirmSnapshot
```

### 7.3 排序语义（落盘）

| 维度 | 顺序 |
| --- | --- |
| 日期 | 升序 |
| 同日 | `seq` 升序（`a0` 在文件上方；新分配的大 seq 在文件底） |
| 无 seq | 回退 `z{source_line:09d}` |

### 7.4 `POST /api/commit` 请求/响应

**请求**：

```json
{ "entries": [ /* 当前 write_target 的活跃 LedgerItem[]，已过滤 _deleted */ ] }
```

| HTTP | 含义 | 前端必须 |
| --- | --- | --- |
| 200 + `ok:true` | 当前 write target 成功 | 成功动画 → reload → unedited |
| 400 / 422 | 空候选、受限 directive 或候选不合法 | 可行动错误文案，回 confirming |
| 500 | 写盘或服务异常 | 不得报成功，保留 confirming 与脏数据 |

### 7.5 部分加载保护

| `loadState` | 保存按钮 | 点击保存 |
| --- | --- | --- |
| `loading` | 禁用或 loading 文案 | — |
| `partial` | 「加载中…」禁用 | `ensureLoadReady()`；未完成则 **alert**「数据仍在加载，请稍候再保存」 |
| `ready` | 随脏状态 | 允许进入 validate |

**原因**：局部列表 commit 会覆写整年文件，必须等全量合并后再允许提交。

### 7.6 Commit 成功后处理

1. 软删条目：播放 `collapseEntryWrap` 折叠动画（可选，BKeasy 有）。
2. `loadDetail(true)` 重新 GET 真源。
3. `baseline = clone(entries)`；`confirmSnapshot = null`。
4. 保存钮成功态（勾）**900ms** 后回 unedited。
5. 列表就地去掉 new/modified 高亮（commit 后均为 unchanged）。

### 7.7 Commit 失败反馈

| 阶段 | 行为 |
| --- | --- |
| `submitting` 中 | 按钮 spinner；禁止重复点击 |
| 业务/写盘失败 | shake + 可行动错误摘要；回 **confirming**（保留 confirmSnapshot，用户可改后重试） |
| 网络异常 | 同上 |

## 8. 保存状态机（明细 Finance Commit UI）

> 源：`reference/20260717_BKeasy/static/js/detail/save.js`。

### 8.1 脏检测

```text
ledgerStateEqual(a, b) = ledgerEqual(语义字段) AND commitOrder(id 序列) 相同
```

- `ledgerEqual`：仅比较**活跃**条目（非 `_deleted`）；`normEntry` 规范化后 JSON 比较。
- `commitOrder`：活跃条目按日期升序、seq 升序的 id 拼接。

### 8.2 状态表

| 状态 | 按钮文案 | 可点 | 进入条件 |
| --- | --- | --- | --- |
| `unedited` | 保存 | 否 | 等于 baseline |
| `edited` | 保存 | 是 | 脏且 ≠ confirmSnapshot |
| `checking` | 保存 + spinner | 否 | 第一次点击后 validate 中 |
| `confirming` | **确认保存** | 是 | validate 通过且 == confirmSnapshot |
| `submitting` | 确认保存 + spinner | 否 | commit 中 |
| `partial` | 加载中… | 否 | `loadState === "partial"` |

### 8.3 流转

```text
edited ──(点保存)──► checking ──(validate OK)──► confirming
confirming ──(再点)──► submitting ──(commit OK)──► 成功动画 ──► loadDetail ──► unedited
checking ──(validate fail)──► edited + 首错高亮 + shake
submitting ──(fail)──► confirming + alert + shake
```

### 8.4 与 inline 编辑的协作

- 点保存前须 `commitEdit()` 提交进行中的 inline 单元格。
- 右栏记一笔表单区域点击**不**触发外部 commitEdit（避免冲突）。

### 8.5 离开确认

| 条件 | 行为 |
| --- | --- |
| `isLedgerDirty()` 或 `saveLock` 非空 | `beforeunload` 阻止默认（浏览器原生未保存提示） |
| 视图 keep-alive 切换 | 不丢内存脏数据；滚动位置按 §2.2 恢复 |

## 9. 数据加载策略（明细）

> 源：`reference/20260717_BKeasy/static/js/state/ledger.js`。

### 9.1 分阶段加载

| 阶段 | 行为 |
| --- | --- |
| 首屏 | `date_from = today - 90d`（`RECENT_DAYS`）→ `GET /api/entries?date_from=...` |

| ready | `baseline` 深拷贝；`loadState = "ready"` |

### 9.2 滚顶加载更早

- `loadState !== "ready"` 且 `scrollTop < 80` → `tryLoadOlder()`（与 BKeasy 一致，若 Orbita 已实现则保留）。

### 9.3 write_target 变更

- `PUT /api/settings` 成功后：`syncAllEntrySourceFiles()`；`loadDetail()`；`recomputeSaveUI()`。

## 10. 明细：筛选、排序、编辑、拖拽

### 10.1 筛选（功能语义）

| 控件 | 语义 |
| --- | --- |
| 起始/截止日期 | 含端点；空=不限 |
| 类型 chip | 支出/收入/转账/投资多选；**未选 = 不过滤（全选）** |
| 软删条目 | **仍显示**，参与筛选 |
| 类型筛选开启 | `dragEnabled() === false`；隐藏拖手柄 |

筛选变更 → `applyDetailFilters()` → 重绘列表；**不**改 baseline。

### 10.2 展示排序

```text
date 降序 → 同日内 seq 降序（新在上）
```

虚拟列表：`buildFlatList` 插入 date 分隔行；sticky date pin；与 pin 重叠的 date 头可跳过渲染。

### 10.3 可编辑字段

| 字段 | 约束 | 副作用 |
| --- | --- | --- |
| `date` | `YYYY-MM-DD` | 改日期 → `seq = nextSeqForDate(newDate, id)` |
| `payee`, `remark` | remark ≤ 50 | — |
| `type` | 四枚举 | — |
| `flag` | `*` / `!` / `?` | — |
| `tags` | chip；Enter 添加 | — |
| `account`, `amount`, `currency` | amount step 0.01 | 金额变 → 配平 preview |
| `cost_amount`, `cost_currency` | 可选 | 展开成本面板 |

**编辑提交**：Enter 确认；Escape 取消；点击外部 `commitEdit()`。

### 10.4 软删

| 操作 | 行为 |
| --- | --- |

## 25. 已确认补充规格（2026-08-08 对话结论；待回填到对应章节）

本节是为避免重构讨论中的产品结论丢失而追加的决策记录。后续整理本计划时，应将其拆回 Parser、Validate、Commit、Detail、Composer、Statistics 等章节；若与前文冲突，以本节为准。对应的实现边界与数据流见 [v0.0.17-architecture.md](v0.0.17-architecture.md)。

### 25.1 托管账本、支持子集与 Canonical Commit

- 当前 `write_target` 是单一年度交易文件 `ledger/YYYY.bean`。一次加载、编辑、候选校验和 Commit 只针对这一个文件；不是跨年度或多文件保存。
- `ledger/YYYY.bean` 是 Orbita 托管的交易账本。首次 Commit 起，Finance 可对该文件进行全量 canonical render：重排已支持条目、统一格式，并覆盖文件全部内容。
- 该文件允许的 directive 子集为：`transaction`、`pad`、`balance`；transaction 可带本节定义的 metadata。
- `event`、`price`、`document`、`note`、`commodity`、`custom`、`open`、`close`、`include`、plugin/options，以及任何未支持的 transaction/posting 语义，均不属于该托管文件的可 Commit 子集。普通 transaction 的 `@` 单价、`@@` 总价、`{}` cost 与空 posting 是本轮支持的 Beancount 原语义；它们由 Candidate/Beancount 裁决，UI 不计算配平，也不提供投资产品能力。
- Parser 必须定位并报告不支持 directive/语义的源文件与行号；存在此类内容时可拒绝进入可保存状态，**绝不**因 canonical render 静默删除它。
- `account.bean` 与 `category.bean` 是账户声明上下文，不由普通 Finance Commit 覆写；分类仍走受控的 categories commit。
- 本轮不做 Finance 打开期间由外部编辑器/Fava 同时改写同一 ledger 的冲突合并或 revision 保护。该限制是个人单机使用范围的明确前提，不得假装支持并发合并。

### 25.2 Beancount 是候选账本的权威最终校验

- 调整 §1.2 的“不引入 beancount pip 包”：Finance Service 可以在既有 Python sidecar 进程中使用 Beancount 作为候选账本校验依赖；不启动额外常驻后台进程，不引入 BQL，也不改为 Rust Parser/Commit。
- Beancount 不监控磁盘上的旧账本，也不在每次输入时实时运行。编辑中的脏数据尚未落盘，检查旧文件没有意义。
- 第一次点击“保存”（`edited -> checking`）时，服务端必须校验**内存候选版本**：先做 Orbita 字段/模型校验，再 render 当前 `LedgerItem[]` 的候选 `ledger/YYYY.bean`，连同 `account.bean`、`category.bean` 上下文在隔离临时位置交给 Beancount 检查；不得写入真实账本。
- 通过后直接进入 `confirming`，按钮文案仅为“确认保存”；面向普通用户不解释 Beancount、候选文件或内部覆盖机制。
- confirming 中任一语义变更必须退回 `edited` 并重新走候选校验；第二次点击“确认保存”才执行 atomic write。Commit 成功后重读真源，`new / modified / deleted` 视觉状态消失。

### 25.3 统一 LedgerItem 与同日顺序

```ts
type LedgerItem =
  | Transaction
  | { kind: "pad"; date: string; account: string; source_account: string; seq: string }
  | { kind: "balance"; date: string; account: string; amount: number; currency: string; seq: string };
```

- `pad`、`balance` 不是 transaction：不进入 Composer、CSV、交易配平、交易 type 推断或交易统计。
- Parser 读取文件时，按每个日期内的原始文件顺序分配 `seq`（如 `a0`、`a1`……）；`seq` 是同日顺序的内存/API 字段，不写入 bean。
- Commit 按 `date ASC -> seq ASC` 输出全部 `LedgerItem`。现有 `pad` 与 `balance` 不假设为同日、一对一或自动配对；真实 Beancount 语义由候选账本校验决定。
- transaction 的同日拖拽只能改变 transaction 的 `seq`；`pad` / `balance` 的 UI 展示位置、创建、编辑、删除入口尚未定稿，当前不得用临时“自动配对”或“固定在交易后”规则替代其语义。

### 25.4 Transaction metadata 与投资边界

```ts
type Metadata = Array<{ key: string; value: string }>;
```

- 支持 transaction-level、`key: "string"` 形式的 metadata：Parser -> 内存 -> canonical render 必须保留未知 key，不能因 UI 未展示而丢失。
- 暂不支持 posting-level metadata，或 metadata 的日期、金额、布尔值等非字符串值；遇到它们必须阻止 Commit 并定位错误。
- `bkeasy-type` 是保留的历史兼容 metadata key，不代表用户可见产品命名。
- metadata 可承载 Finance 内部的稳定标识或来源信息，但未来跨领域 Connection/Relation 仍应是独立引用层，不能把“交易关联某日记/骑行/照片”的关系仅写进 bean metadata。
- 投资产品、commodity、lot 的专用 UI/统计不在本轮范围；但普通交易的 posting `@` 单价、`@@` 总价、`{}` cost 与空 posting 必须透明 parse → model → render，并交由 Beancount 候选校验。交易级字符串 metadata（例如 `time: "2026-05-19T14:32:00+08:00"`）只透明读写，不参与排序或 UI 业务逻辑。

### 25.5 Transaction type：保守推断、可人工覆盖

- `type` 是 Orbita 的浏览、筛选、Composer 与展示语义；它不决定单文件 Commit 位置，也不改变 Beancount 的会计语义。
- 有有效 `bkeasy-type` metadata 时，metadata 绝对优先。
- 无 metadata 时，仅对恰好两条 posting 的严格标准结构推断：`Expenses + Assets/Liabilities => expense`；`Income + Assets/Liabilities => income`；两侧均为 `Assets/Liabilities => transfer`。
- 多分录、代买、报销、应收应付、混合分类，或任何无法严格匹配的交易均为 `type = ""`，UI 中性显示“未分类”；未分类不是校验错误，也不阻止保存。
- 用户可手动选择支出、收入或转账；该选择写入/更新 `bkeasy-type`。清除分类时删除该 metadata，回到自动推断或未分类。`inv` 不作为本轮普通交易的手工 type。

### 25.6 账户、统计与待保存反馈

- Composer、CSV 与 inline 编辑只能选择已在 `account.bean` 或 `category.bean` 中声明的账户；未知账户是保存前错误。代买、应收等不需要特殊产品规则，由用户自行使用已声明的账户表达。
- `type` 不决定统计：月度支出和分类 Top N 按 `Expenses:` postings 聚合；收入按 `Income:` postings 聚合。复杂或未分类交易中的真实费用/收入不得被漏计。未来改用 Beancount 原生统计时必须保持此口径。
- “记录”成功只表示 Entry 已加入当前内存的待保存队列，不表示已写入 bean。绿底 `new` 条目和全局保存修改数量表达待保存状态，不再显示冗余的“已加入待保存”反馈；仅在 Commit 成功并重读真源后，才可表达“已保存到账本”。

### 25.7 候选诊断、Pad/Balance 账户限制与稳定交易 ID

- Beancount 候选校验返回的是诊断集合而非仅首错：`{ message, item_ids: string[], raw? }`。每个 `item_id` 都显示错误态；保存区显示总数并仅自动滚至第一处；`item_ids` 为空时显示为全局错误。原始 Beancount 诊断仅保留给日志/开发排查。
- `balance.account` 与 `pad.account` 只能是 Assets 或 Liabilities；`pad.source_account` 只能是 Equity。账户管理页继续不展示 Equity，但 Pad 的来源选择器可从 `account.bean` 读取 Equity。普通 transaction 与 CSV 仍不允许选择 Equity。
- 为未来 Connection 的稳定 `ArchiveRef { domain: "ledger", id }` 保留 transaction metadata：`orbita-id: "txn_<ULID>"`。
- `orbita-id` 的格式为 `txn_` + 26 位 Crockford Base32 ULID（`^txn_[0-9A-HJKMNP-TV-Z]{26}$`）；每个 transaction 恰有一个，重复或格式错误阻止 Commit。它不编码交易日期、年份、文件名或行号，生成后永不变化。
- canonical metadata 输出顺序固定：`bkeasy-type`，`orbita-id`，其余 key 按字典序。未知 metadata 必须保留 key/value，但无需保留原始排列顺序。
- 不在打开账本时自动写入 ID。旧交易继续以 `source_file:source_line` 作为本会话临时身份；用户第一次正常 Commit 时，候选账本为所有缺失 `orbita-id` 的旧 transaction 补齐，且仅在“确认保存”成功后写入真实 bean。

### 25.8 报告本位币与账户币种约束

- `.bkeasy/settings.json` 增加 `reporting_currency`，默认 `CNY`，在 Finance 设置中可修改。它只改变统计/展示口径，不重写历史交易、不改变 `write_target` 或 Commit 语义。
- 设置页优先提供 `account.bean` 已声明的币种；无可用换算依据的外币不得强行折算进报告币总额。
- 报告币统计是固定推导，不是每笔交易的用户选择：若交易已有报告币种的 `Expenses:` posting，直接聚合它们并忽略同交易的 `@@` 以避免双计；若没有报告币费用 posting、但存在可明确对应报告币的 `@@` 总成本，使用该成本金额折算；多外币/多成本而无法明确归属时，归入“未折算外币支出”，不混入报告币总额。
- Parser 必须解析 `open` directive 的允许币种。`open ... USD` 只允许 USD；`open ... CNY, USD` 只允许两者；未声明币种约束的账户允许任意合法币种。
- Composer、CSV、inline 编辑共享同一账户币种校验；违反约束是可定位字段错误，不能进入确认保存。该预校验不替代 Beancount 的最终候选账本校验。

### 25.9 CSV 导入：明细页 staging modal

- 明细页标题区的操作顺序为“资产 · 明细 + 筛选”在左侧，“导入”在“保存”左侧。导入不是独立工作流的落盘入口。
- 点击“导入”打开明细页上的 modal，完成文件选择/拖放、模板下载、表头与逐行校验、错误列表、行序选择和“确认添加”。不离开当前明细页。
- CSV 模板固定为 10 列：`date,time,type,amount,currency,from_account,to_account,payee,remark,tags`。`time` 可为空；非空必须是本地 24 小时制 `HH:mm`，导入时与 `date` 合成为 transaction-level 字符串 metadata：`time: "YYYY-MM-DDTHH:mm:00+08:00"`。该 metadata 只透明读写，不参与文件排序、同日 `seq`、统计或 UI 业务逻辑。
- 校验通过且用户点击“确认添加”后，CSV 行批量 merge 到当前明细的内存 `LedgerItem[]`，生成新的 transaction 与 `orbita-id`，以绿底 `new` 状态显示；全局保存状态立即变为 `edited`。
- CSV 绝不自动 Commit。关闭 modal 后的新增项必须走“保存 -> 候选校验 -> 确认保存 -> Commit”统一管线。
- 本轮不自动去重、不静默跳过。每次确认添加均是显式新增一批待保存交易；未来可增加“疑似重复”提示，但不得自动决定跳过。
- 导入确认后自动清空日期与类型筛选，并滚动到第一条新记录，保证新增绿底条目立即可见。

### 25.10 账户树与中文分类树：锚定展示、显式迁移

- `name` 是 Beancount 的真实账户身份与交易引用 key；`label` 是唯一落盘的中文展示文本；`label_path` 与 `brief` 均由 `label` 推导，不能独立写入。
- 示例：`Expenses:Food:Dining ;餐饮:外出就餐_咖啡、奶茶` 中，`name = Expenses:Food:Dining`，`label = 餐饮:外出就餐_咖啡、奶茶`，`label_path = [餐饮, 外出就餐]`，`brief = 咖啡、奶茶`。`:` 分隔中文层级；最后一层 `_` 后的文本是可选 `brief`。
- 分类账户的中文 `label_path` 与 canonical `name` 去掉根（`Expenses:` / `Income:`）后的层级必须一一对应；`brief` 只是解释文本，不参与层级。没有 `label` 时才回退显示 canonical 名称的后续段。
- 创建分类/账户允许直接填写完整 canonical path，不使用父级选择器；必须校验根类型、路径语法与全账本唯一性，不强制父级 open 行存在。
- 新建是安全的结构操作：仅向 `category.bean` 或 `account.bean` 增加 open 行，不改历史交易；分类可新建 Expenses/Income，账户可新建 Assets/Liabilities 并配置可选允许币种。Equity 不进入普通账户管理，初始化提供 `Equity:Opening-Balances`，Pad 仅引用它。
- 不允许普通 inline 操作重命名、移动或删除 canonical `name`。这不是普通 label 编辑，而是独立的“账户迁移”工作流。
- 账户迁移前必须没有任何未落盘的交易、分类、账户或 CSV staging；输入为旧完整路径与新完整路径，且迁移该路径及所有 `old:*` 子账户。
- 迁移必须通过结构化 Parser 修改所有年度 ledger 中 transaction posting、Pad、Balance 的账户字段，并更新 `account.bean` / `category.bean` 的 open 行；禁止裸字符串 replace。
- 迁移前生成候选结果，运行 Beancount 校验，展示受影响文件数、条目数、账户数与 diff 摘要；用户明确确认后，先准备全部临时文件，全部成功再替换。失败不得产生半迁移；成功后全量 reload 并清空 session 状态。

### 25.11 结构删除与最小余额核验

- 账户或分类只有在当前 Finance 没有任何未落盘交易、分类、账户或 CSV staging 时才能请求删除。
- 删除前服务端必须扫描所有年度 ledger 中 transaction posting、Pad、Balance 的账户引用，并检查是否存在任何 `name:` 子账户。仅在零引用且无子账户时，才可显示删除操作。
- 删除必须展示扫描结论并要求明确确认；随后以受控结构写入原子更新 `account.bean` 或 `category.bean`。只要存在引用或子账户，用户必须保留该账户/分类，或改走账户迁移，禁止直接删除。
- v0.0.17 的统计优先级是余额核验，而非完整消费分析：统计/余额只读取当前 `write_target` 对应的年度 ledger，默认只反映已落盘账本。跨年度汇总明确延后。
- 余额视图由 Beancount 计算 Assets / Liabilities 的各账户原币余额，不强制外币折算；显示最近的 balance 断言状态（通过 / 不通过 / 尚无断言）。本月支出、分类 Top N 与未折算外币支出仅作轻量辅助信息。
