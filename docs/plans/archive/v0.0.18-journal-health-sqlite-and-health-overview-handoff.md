> 用途：暂存于 `orbita-plan/` 的完整实施、审阅与修复基线；待 Orbita 工作区可写后，再迁入其 `docs/plans/`。

## 1. 目标与不可扩大范围

0.0.18 的目标是让 Journal 与 Health 从混合 JSON 真源切换到可同步的本地 SQLite 事实模型，并交付一个**纯只读、用于回看与分析的 Insight Health 总览**。

本版本的两项最高原则：

1. 表面无感：除旧 JSON 有意不迁入、Garmin 需重新同步、历史 Meal 需补记外，用户不应理解数据库或看到两套数据入口。
2. 同步不返工：本地 SQLite 从第一天起就带稳定 ID、来源、版本、软删与原子 outbox，使下一版本的 `orbita-sync` 可以直接消费事实快照，不重新设计客户端真源。

明确不做：服务器 API、认证、设备身份、同步 push/pull、冲突裁决、outbox ack、tombstone 回收、手机端、Finance SQLite 投影、远端 `.bean` 写入、Activity/FIT detail、Garmin Nutrition、AI 营养估算、血压 UI、Journal Insight UI、统一 Health 记录页。

## 2. 已确认的数据真源与同步护栏

### 2.1 初始化与旧 JSON

- 数据库固定为 `{journalRoot}/journal.sqlite`；`journalRoot` 延续已有设置，默认才是 `dataDir`。
- 仅检查 SQLite 是否存在；不存在就自动创建空库。
- 旧 `journal/YYYY.json` **不读取、不导入、不删除、不改写、不作为 fallback**。它只是不被触碰的历史备份。
- 不迁入 App State、凭据、token、Garmin 原始响应/缓存或 Finance `.bean`。
- SQLite 文件绝不经 SMB、Git、网盘或拷贝方式同步；未来只同步 API 传递的事实与操作快照。

### 2.2 专业事实表，而非旧容器

`daily` 与 `routine` 必须降为查询投影，不能再是可整体读写、混合 Garmin 与人工字段的持久化容器。不得改回万能 `records(data_json)` 或通用 Event 表。

需要独立寻址、独立生命周期与独立来源约束的事实至少包括：

| 领域 | 事实 | 关键规则 |
| --- | --- | --- |
| Garmin 健康 | 日指标、指标日快照、夜睡、Garmin nap、轻量活动摘要 | `source=garmin`，只读；时序为 UTC；夜睡有 `wake_date` |
| Health 人工 | Meal、手工 Nap、手工 Activity、Body measurement | `source=manual`；无精确时间只保存 `local_date` |
| Journal 人工 | Event、Mood、Note（随记） | `source=manual`；业务日为 `Asia/Shanghai` |
| 同步 | outbox 操作 | 不是业务事实表；指向上述事实 |

每个可同步事实都必须有：全局 UUID、`source`（首版仅 `manual` / `garmin`）、递增 `revision`、创建/更新时间、tombstone 状态。领域关键字段必须可被 schema 约束和查询；不允许把 Meal、Nap、Activity、Event、Mood、Note 再塞成不可验证的大 JSON blob。指标日快照可以保存规范化样本数组，但其 metric、local date、coverage、content hash、revision、来源与时间字段必须独立可查询。

### 2.3 所有权、时间与删除

- Garmin 事实永远只读、不可由用户删改；修正必须在 Garmin 完成后再同步。0.0.18 不做字段 override、双真源、恢复 Garmin 或 Orbita 上传 Garmin。
- 手工 Meal、Nap、Activity、体重/体成分、Event、Mood、Note 可创建、编辑、软删与 5 秒撤销；撤销是新的版本化 upsert。
- Garmin Nap 与手工 Nap 可同日共存，Garmin 同步不触碰手工 Nap。
- 手工记录必须有 `local_date`；只有用户或数据源给出精确时刻时才保存 UTC 时间。**没有时刻就不得伪造 00:00、视窗左缘、右缘或任意 occurred_at。** 无时刻的 Meal/Nap/Activity 不进日内时间轨，只能出现在日期级聚合或管理投影中。
- 时序点统一保存 UTC；页面与业务日期统一按 `Asia/Shanghai` 映射；夜睡额外使用醒来日归档。
- tombstone 不自动清理，直至未来同步协议定义服务端确认与回收规则。

### 2.4 Meal 与 Journal

- Meal 是独立的 **Health** 事实，不属于 Journal。
- Meal 至少包含发生日期、可选时间、餐别、食物/描述/备注及可扩展 `nutrition`：kcal、蛋白质、碳水、脂肪等。
- 日摄入与 Panel 摄入环从 Meal 聚合；禁止另存可变的“日总摄入”第二真源。
- Note（随记）是独立 Journal 事实：日期必填，时间/标题可选，正文必填。
- Journal 必须完成 SQLite、稳定 ID、revision、tombstone、outbox 及既有 Panel/AI 调用兼容；**Journal 的 Insight UI、搜索、筛选、管理页全部延期。**

### 2.5 原子 outbox 与 Garmin 幂等

- 手工新建、编辑、软删、撤销必须在同一 SQLite transaction 内写事实、递增 revision、写 outbox。
- outbox 至少包含：`op_id` UUID、领域/记录类型、记录 ID、revision、`upsert | delete`、origin、可重放的完整快照、创建时间。
- Garmin 先规范化，再计算内容 hash。hash 相同：不增 revision、不写 outbox、不产生未来同步。`fetched_at` 不进入 hash；样本、coverage 和会影响 UI 的缺失状态进入 hash。
- 日摘要及 HR、Stress、Body Battery、Respiration、SpO2、HRV 等高密度数据的同步单位是“**本地日 + 指标 + 规范化快照**”，绝不逐采样点出 outbox。
- 服务器只同步 SQLite 中的规范化事实、快照与同步元数据；不传 Garmin 原始响应。
- 0.0.18 不发网络、不 ack、不解决并发冲突、不清 outbox；冲突策略显式延期，禁止悄悄 last-write-wins。

## 3. Garmin 拉取范围与真实性

首批目录：日健康摘要；全天 HR、Stress、Body Battery、Respiration、SpO2；睡眠详情、HRV、喝水、体重/体成分；血压仅 capability probe 和数据结构预留。

实施前先做“今天 + 昨天”的有界只读 probe，核对真实字段、采样频率、空洞、时区与速率预算。不得触发 SSO、重试风暴、数据写入或自动历史回补。

首次正式同步只拉最近 7 天。用户切到 `30D/90D/1Y` 时，只展示本地已有数据，并提供明确的“获取更多历史”动作；绝不自动拉一年。

Activity 只保留轨道所需的轻量摘要（类型/名称/开始结束/时长/距离）。没有可靠开始结束时刻就不画区间；不得把它钉到视窗左缘。不得下载 FIT 或建立 Activity detail 页面。

日内累计步数曲线只在确有真实带时刻、可构成累计序列的 Garmin 数据时画。日总步数或同步时间不得伪造成单点／日内曲线。

## 4. Health 总览：完整视觉与交互规格

### 4.1 信息架构与视觉语言

Health 默认入口是一个三层、只读的工作台，而不是“轨道页面”或记录列表：

```text
每日轨道：一天内发生的过程
  ↓
长期趋势：多个日的变化
  ↓
当日摘要：选中日的关键结果
```

采用浅色、安静、高信息密度的健康仪表盘语言：浅中性背景、白色/近白模块、细低对比边界、圆角卡片、纤细网格与曲线。不要厚重阴影、调试式坐标纸、过饱和大色块或粗糙 canvas 空白。

Insight Health 只承担回看、理解与分析。它不承担创建、编辑、删除、跳转、详情下钻或统一记录管理；既有手工 Health CRUD 继续留在 Panel。Panel 只迁到新读取边界，并移除手工喝水编辑，不重做 Panel UI。

### 4.2 页面顶部

从左到右：

1. `Health` 标题。
2. 日期组：日历图标、本地日期、前一天/后一天；今天不能再前进，未来日期不可选。
3. 紧邻日期的 Garmin 状态：成功显示 `已同步 HH:mm` 且可手动同步；同步中显示低干扰 loading；失败显示失败状态和重试。不得把重试散落到曲线旁。
4. 右侧趋势范围分段控件：`7D / 30D / 90D / 1Y`。它只影响趋势，不改变轨道日期/窗口。

桌面宽度不足时顶部可折为两行，但每个控制组内部不得拆散。

### 4.3 日内轨道：一个共享时间系统

轨道是一个卡片，包含固定左侧语义栏和右侧**单一共享时间绘图区**。不得用三个独立 canvas 各自画日期、刻度和网格。

- 左栏建议 150–180px（最小 136px），淡底色、固定不随轨道平移。
- 右侧是三条轨道共用的 x 轴、时间网格和 hover 坐标。三行可有独立 y 区，但所有数据严格对齐同一个时间系统。
- 主刻度默认每 2 小时；跨日处使用更醒目的分隔线及 `MM-DD` 标签，不能重复堆叠 `22:00 / 00:00` 或日期。
- 每轨建议 92–118px 高；Track 1 可稍高。没有数据仍保留轨道标题、图例、网格和高度，不塌成无意义大空白。

#### 窗口、拖动与日期联动

- 历史日期 `D` 的默认视窗：`D-1 22:00 → D 24:00`，共 26 小时。
- 初次打开/回到今天/点击“今天”时：保持 26 小时，但右边缘精确贴到当前时刻 `now`，即 `now - 26h → now`；右侧绝不留未来空白。
- 可连续水平拖动回看过去；不做自由缩放、框选或越界惯性。
- 禁止未来：今天右缘 `≤ now`；历史日期右缘 `≤ D 24:00`；未来日期不可选。
- 视口中心时刻按 `Asia/Shanghai` 映射日期，驱动顶部日期与当日摘要；顶部日期反向定位视窗。更新视口范围时必须加载该范围数据，不能只在中心日期变化时刷新。

#### Track 1：恢复 / 心肺

左栏标题 `恢复 / 心肺`，图例顺序：睡眠、心率 (bpm)、HRV (ms)、血氧 SpO2 (%)、呼吸（默认关闭）。

- Sleep：深靛/蓝灰圆角区间 block；主睡眠厚，Nap 更浅更细；可用月亮图标，但绝不画成曲线。
- HR：珊瑚红细曲线；只连接真实相邻样本。
- HRV：弱于 HR 的蓝紫曲线；图例与睡眠开关联动。
- SpO2：自顶向下 tick；长度 100≈点、90≈满长；按数值渐变色带（见 `colors.ts`）。日间约每小时、睡眠约每分钟（字段见 spec §4.2.1）。
- Respiration：浅青绿细线，默认关，z 低于 HR。

#### Track 2：压力 / 能量

左栏标题 `压力 / 能量`，图例为压力 (0–100)、Body Battery (0–100)。

- Stress：竖柱；低值淡黄、高值深橙，整柱按数值着色。
- Body Battery：蓝色中等权重平滑曲线。
- 两者共用 x 轴，不混淆 y 量纲。

#### Track 3：行为 / 活动

左栏标题 `行为 / 活动`。只允许以下对象：

- Steps：细蓝色累计步数曲线；无真实时序就不画。
- Activity：绿色圆角时间区间条，表示起止；仅轻量名称、类型、时长/距离。
- Meal：与 Activity 共用一条事件 rail 的橙色点；kcal 越高点越大；无 kcal 为标准大小空心点。

Water 不进入轨道，仅在趋势和当日摘要显示总量。Nap 只在 Track 1。不得做 Activity/FIT detail。

### 4.4 图例、hover 与缺失

- 每指标图例始终存在，首次进入默认全开。
- 开启状态为彩色；点击后变灰并完全隐藏对应图形。状态跨日期、跨重新进入 Health 持久。
- 设备不支持或该日没有样本时，图例仍保持开启彩色、时间区不画；这必须和用户关闭的灰色状态可区分。
- 所有轨道共用贯穿三行的垂直 hover 游标与一个统一 tooltip。tooltip 只显示当前开启指标，列出名称、数值、单位；没有合理近邻样本显示 `—`。
- tooltip 只在命中时显示睡眠/Nap 区间、Activity 名称/时段或 Meal 餐别/kcal；不命中时省略事件。
- tooltip 在左右边缘自动翻转，不能被裁切。
- 曲线必须按连续采样段绘制：`null`、coverage 空洞或超出本指标允许间隔的样本结束 path。不得滤掉缺失点后跨洞连线、补 0、画虚线或把远处样本吸附为当前值。
- 查询/SQLite/同步失败必须显示可行动错误或顶部同步失败，绝不能静默降级为“空数据”。

### 4.5 长期趋势

- 固定为一条水平 rail，四个领域面板始终按固定顺序保留：恢复（睡眠/HRV/SpO2）、身体与能量（体重/记录能量平衡）、喝水、Stress。
- 桌面上四张等宽；建议每张最小 260–300px。宽度不足时 rail 横向滚动，不换行、不缩窄为不可读迷你卡。页面本身仍垂直滚动。
- 每个子指标独立 y 轴、共享日期顺序；不得把不同单位硬叠在一个轴。
- 每个子指标显示名称、单位、当前窗口主值、与紧邻上一等长窗口的变化、日级微折线/柱。只比较 `7D vs 前7天`、`30D vs 前30天` 等，不使用“相对昨天”。
- 聚合：Sleep/HRV/Stress/Water 等取窗口日均；Weight 取窗口最新有效测量。
- 能量只统计有 Meal 记录的日期，显示覆盖度，例如 `5 / 7 天已记录`。0 Meal 表示“未记餐食”，不是摄入 0，不参与差额平均。
- 外层四个面板必须稳定保留；数据少于 2 个有效日点时，对应子图显示克制的“暂无足够数据”，不隐藏面板、不画假线。

### 4.6 当日摘要

- 标题为 `当日摘要 · YYYY-MM-DD`；只有选中日是今天时才可简称“今日摘要”。
- 摘要同样是一条单行横向滚动 rail，每张卡建议最小 150–180px；禁止自动换行。
- 候选：Steps、Sleep、Resting HR、Body Battery、Water、Weight、SpO2、Energy。
- 每张卡只讲**选中日实际值**；不得显示趋势窗口均值、sparkline 或与上一周比较。
- 某指标从未在本机出现：不显示卡。曾出现但选中日缺失：保留卡并显示 `—`。
- Energy 与普通摘要卡同等级，显示：已记录摄入、Garmin 消耗、记录差额。无 Meal 时显示“未记餐食”，不伪造 0 或差额。
- 卡片可有小图标、简短状态或进度条，但没有编辑入口。

## 5. 当前实现审计：不得忽略的阻断项

以下是对当前进行中实现的只读审计结论；在修复前不得把 0.0.18 或任一子阶段标为完成。

### P0：必须先修

1. **步数轨道断链。** 当前导入生成 `steps` 单点并以同步时刻作为时间，而查询/前端读取 `steps_cumulative`。这既导致曲线为空，也会把历史步数伪造到错误时间。必须等待真实日内数据或不画步数轨道。
2. **无时刻事实被伪造到轨道左缘。** 当前查询将无时间 Meal、duration-only Nap、无开始时间 Activity 锚到视窗起点。这违反时间语义，必须改为不进入日内轨道。
3. **Activity 链路不完整。** 导入只处理 cycling，未保存开始时间，字段名与查询不一致；活动条会错位、距离为空。必须先规范化轻量 Activity 摘要或暂不画。
4. **今日/未来边界违例。** 今天仍画到午夜，拖动没有 now/历史日终点 clamp。必须按 4.3 修复。
5. **真实错误被吞成空页面。** 查询 load failure 被转为空 overview，违反可信保存和错误可行动原则。必须保留明确错误状态。
6. **生产 schema 测试未运行。** Rust DB tests 被禁用/旧 harness 与生产 DDL 不一致。必须先让测试覆盖实际 schema，再声称事务、tombstone、hash/outbox 或日期行为经过验证。

### P1：架构与数据风险

1. 多张所谓专业表仍以 `*_json` 保存领域事实，和“不可验证 opaque data blob”的 ADR 护栏冲突；需拆出可验证的关键字段，时序数组仅留在规范化快照 payload。
2. 旧 `daily/routine` 整体写入命令仍可写投影；必须收敛为领域命令／repository，不能作为混合容器回写入口。
3. Garmin 更新路径必须按事实来源隔离，不能把同日 manual 投影改为 `source=garmin` 或覆盖其字段。
4. Meal/Nap/Activity 的可选 UTC 字段必须成为稳定 schema 字段，而不是只在查询阶段临时解析 JSON。
5. 睡眠、HRV、SpO2、体重、Stress 等趋势必须从各自事实或快照正确聚合，不能读取未被导入的旧 daily JSON 字段。
6. 同步状态必须真正保存同步中/失败/最后成功等可恢复状态；空字符串不得被 UI 误判失败。
7. Garmin provider 镜像撤销与“Garmin 记录不可删”需区分：用户不可删不等于同步镜像永不更新。若 provider 不再返回某项，必须以来源同步语义处理并记录，而不是模糊调用用户 soft delete。

## 6. 实施与验收顺序

这是 L3 任务，必须有独立架构/安全审计、实现、测试、验收四角色；协调者不计入角色。子代理不得自行启动 dev/server/test/browser 或后台进程。运行前必须检查工作树与进程所有权；Vitest 与开发会话严格全局独占。

1. 先完成替换矩阵：旧 JSON 读写、Tauri command、AI、Panel、Garmin、`journal_root()`、dataDir 切换及每个调用者。
2. 修复并审计专业 schema、迁移快照、领域 repository、原子 transaction/outbox 与时间字段。
3. 建立真实 production-schema 测试：空库初始化/旧 JSON 未读、跨年/上海日期、manual+Garmin 共存、睡眠醒来日、revision/tombstone/撤销、事务不半写、schema 升级快照、相同 Garmin 内容无 outbox。
4. 实现并以 fixture/probe 验证 Garmin 规范化层：真实字段、零值/missing、UTC、日快照 hash、活动/步数真实性、失败不 SSO/不重试风暴。
5. 再构建完整 Health 页面骨架与共享时间系统；不要先把原始线画满 canvas。
6. 最后做 UI 边界测试、真实 `dev.bat` 启动检查及人工 Tauri 验收。未运行的层必须明确写为未验证。

## 7. 交付时必须如实报告

- 每个角色的审计/改动范围；
- 所改文件和对应行为；
- 每条测试或启动命令及结果；
- 未运行/被阻断的验证；
- 是否存在活跃进程；
- 哪些文档因真实状态变化而更新；
- 尚存风险与下一步。

不得把“曲线能画出来”“开发服务器启动”“测试绿字”或“代码已写”描述为完成。只有计划中的行为和 L3 证据均满足，才可标为验收完成。
