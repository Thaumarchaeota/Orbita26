## 0. 为什么本路线被停止

本路线把部分生命周期、Layout、drawer 和事件控制收进了新的壳，却继续使用旧 Detail renderer、旧卡片 DOM/CSS 与可变 Store 对象。这不是用户要求的“保留卡片体验、彻底重构实现”，而是旧页面的迁移包装。

这是严重错误，后续实现者不得淡化为“只差样式”或“再补几个 selector”：

1. 旧字符串 HTML renderer 仍决定卡片结构、编辑宿主和状态样式，故 DetailSurface 没有独立渲染所有权。
2. `#detail-list`、重复页面 ID 和跨模块装配协议继续存在，和 keep-alive 多实例不相容。
3. Detail/drag/edit 直接原地修改 Store 条目，破坏 Store 作为 mutation、确认 token、异步与数据一致性的唯一 owner。
4. 现有 Grid、drawer 与 portal 是可保留地基，但没有真实窗口证据时绝不能写成 UI 完成。
5. 曾把静态扫描、测试和“控制权部分迁入实例”描述得近似成品，违反 README 的真实状态纪律。

因此，本文后文任何“已改为”“已落地”仅可作为历史审计线索，不能证明当前交付，也不能成为保留旧 DOM/CSS 的理由。新实现必须遵循新执行计划的淘汰清单、阶段门与双证据验收。

## 1. 目标与完成定义

重构目标不是给旧 Finance 页面继续加样式，而是在不改变账本写入语义的前提下，形成一个可长期维护的本地账本客户端：稳定视图、明确所有权、可预测的窄窗口行为、受控弹层和可验证的数据安全边界。

本轮完成必须同时满足：

1. Finance 根与内部视图切换保持工作副本、滚动和局部状态；只有 host dispose 或 dataDir change 才销毁。
2. 每个状态、DOM 根、滚动根、弹层和异步请求有唯一 owner；不得以全局 ID 或 sibling DOM 互相控制。
3. 主列、右栏和窄窗口 drawer 在 1440、1280、1024px 可见实机下均无重叠、裁切或误点击。
4. §25 的候选校验、原子提交、账户约束、统计和结构操作安全契约不被 UI 重构削弱；本规格列出的未完成缺口得到修复和验证。
5. 没有自动化与实机证据的事项不得标记完成。

这里借鉴成熟桌面客户端（包括 Telegram）的是架构纪律，而非复制视觉或功能：稳定的 destination/view 生命周期、单一 ownership、命令驱动状态变化、异步过期保护，以及内容与 chrome 的清晰边界。

## 2. 冻结的既有边界

以下不是本轮重构对象，任何改变须另立计划：

- Finance 唯一根为 `{dataDir}/bill`；数据目录切换是换数据集，不复制、迁移或泄漏旧数据。
- `write_target` 是相对 `bill/` 的单一 `ledger/YYYY.bean`；load、validate、commit 只处理该文件。
- `account.bean`、`category.bean` 是声明上下文，普通 Finance Commit 不写入它们。
- Parser 只读；候选版本在隔离临时目录经 Beancount 校验；token + hash 只能提交同一候选；单文件 Commit 原子写入后必须重读真源。
- 不支持 Finance 打开期间的外部并发编辑、合并或 revision 保护。
- Panel、Agent 和 app boot 不启动 Python；Insight fire-and-forget ensure Service，前端不得猜测 `:8000`；重试必须重启本进程追踪、根目录正确的 sidecar。
- Insight Host 的 cached destination、hide/show、dataDir guard、frameless chrome 和全局 modal/click-through 约束保持不变。

## 3. 前端所有权契约

```text
Insight Host
  └─ Finance destination (activate / deactivate / dispose)
       └─ FinanceShell (内部路由、keep-alive、view handles)
            ├─ FinanceLayout (viewport、Grid、breakpoint、drawer、scroll regions)
            ├─ FinanceChrome (标题、返回、筛选、导入、保存、管理命令)
            ├─ LedgerStore (load、baseline、work copy、mutation、save state、generation)
            └─ FinanceView handles
                 ├─ DetailSurface (virtual list、anchor、inline、pointer drag、focus)
                 ├─ Composer (draft → Store command)
                 ├─ Dashboard / Stats / Structure
                 └─ Import modal / picker (global portal)
```

- `FinanceShell` 只持有 view handle；不得 import 或查询 DetailSurface 内部 DOM。
- 每个 view `mount()` 返回至少 `{ getScrollTargets(), dispose() }`；需要定位时增加 `focusItem(id)`。Shell 仅通过 handle 保存/恢复滚动。
- `FinanceLayout` 是 viewport、Grid、breakpoint、right drawer 和滚动区域的唯一 owner；它不读取账本数据或保存状态。
- `FinanceChrome` 只呈现 Store snapshot 并发出 router/Store command；不查询列表、不调用 Parser/Commit。
- `LedgerStore` 是所有 load、mutation、validate、commit、baseline 与 generation 的唯一 owner。视图不得自行 fetch 或直接写账本。
- `DetailSurface` 独占虚拟列表 DOM、事件委托、inline 编辑、pointer drag、日期 pin 与滚动锚定；不得使用 `document.getElementById`、模块级可变 DOM 或跨 view selector。
- 每个异步请求必须由 generation 和/或 `AbortController` 保护；deactivate、dispose、filter、write target 或 dataDir 变化后的旧响应不得改变当前会话。

## 4. Layout、drawer 与弹层

1. 双栏只使用同一 CSS Grid 内的正常 grid item；不得以 `absolute`、`fixed`、`translateX` 或负 margin 作为主布局。
2. 宽度大于 1180px 时，主列与 300px 右栏并列；右栏是独立滚动区域。布局代码须允许以后以 token 调整该阈值。
3. 宽度小于或等于 1180px 时，右栏默认收起；用户点击 chrome 按钮后以 drawer 打开。drawer 覆盖仅限该明确的次级 surface，关闭后主列恢复全部可用宽度。
4. Insight sidebar 的展开/收起不得再次人为扣减 Finance 内容宽度。所有 layout root 都保持 `min-width: 0` 与 `min-height: 0`。
5. Detail 的唯一主滚动根属于 DetailSurface；右栏单独滚动；Chrome、页面容器和隐藏 view 不争夺滚动。
6. Finance 根使用 `isolation: isolate`。普通内容不使用竞争性 `z-index`；dialog、导入、日期和账户 picker 必须使用现有 `#orbita-modal-root` 或同等受生命周期管理的 portal，不能 append 到 body、rail 或领域 root。

## 5. §25 非 UI 安全收束

以下实现与测试优先于视觉润色：

- 保持白名单 LedgerItem（transaction/pad/balance）、未知字符串 metadata round-trip、`orbita-id` 一次性补齐/唯一性、`bkeasy-type` 优先且保守 type 推断、同日 `seq` 与 Pad/Balance 根类型限制。
- `reporting_currency` 必须随 `.bkeasy/settings.json` 的 GET/PUT 完整读写并保留 `write_target`；它只影响统计/展示，绝不重写历史交易。
- Composer、CSV、inline 共用账户存在性与允许币种预校验；统计按真实 Expenses/Income postings 聚合，未分类交易不能漏算。
- 账户/分类删除前扫描所有年份的 transaction、Pad、Balance 引用与子账户；只有零引用才允许明确确认和原子声明更新。
- canonical name 迁移必须无脏 session；先生成所有候选文件、执行 Beancount 校验、展示受影响摘要、经明确确认后以可回滚的整体替换提交。任一失败时原文件字节保持不变，绝不逐文件造成半迁移。

涉及 sidecar、数据写入、迁移、并发限制、drawer/portal 生命周期的代码附近必须写简短原因注释并链接本文或相应领域规格。

## 8. 明确不做

- Pad/Balance CRUD、最终账户管理信息架构、跨年度统计、投资域、Connection/Relation 产品模型。
