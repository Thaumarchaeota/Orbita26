# v0.0.18 Journal / Health SQLite 与 Insight 初版

> **Outcome（部分完成后收束，2026-09-02；代码基线 `0.0.17-snapshot`）：**完成 SQLite 专业事实、Journal / Health 读写边界、Garmin ingest 与 Health 总览的实施交付。全 catalog Garmin 实机、L3 独立验收和轨道 UI 用户手验未完成，未改写为已验收；它们作为 0.0.19 Sync S0 与真实数据接入的前置证据继续保留。网络同步、服务端、手机端、Finance v2 仍不属于本计划。

> **状态**：部分完成后归档（2026-09-02；未完成验证项转为 0.0.19 前置门槛）。  
> **前序证据**：[已归档的早期 SQLite 计划](v0.0.18-journal-sqlite-sync-foundation.md) 保留讨论过程；本文件在 0.0.18 收束前曾是唯一当前执行输入。  
> **原目标**：以新的本地 SQLite 真源承接 Orbita Journal / Health，完成纯回看/分析的 Insight Health 初版，并为后续 `orbita-sync` 提供无需重构本地真源的同步基础。  
> **风险级别**：L3。涉及用户数据写入、SQLite schema、Garmin 同步和未来跨端同步。实施必须按 `docs/AGENTS.md` 的架构/安全审计、实现、测试、验收四个独立角色组织。

## 1. 范围与完成线

0.0.18 交付的是桌面端的 Journal / Health 新本地真源与 Insight Health 初版；不是 Linux 服务、手机端或 Finance 同步。

| 纳入 | 不纳入 |
| --- | --- |
| 一个新的 `{journalRoot}/journal.sqlite`、schema、稳定 ID、revision、tombstone、outbox | `orbita-sync` 网络 API、认证、冲突裁决、ack 或 tombstone 回收 |
| Journal / Health 专业领域记录、Garmin 日摘要与时序快照 | Finance `.bean`、Finance SQLite 投影或远端写账 |
| Panel 改从 SQLite 读取；移除手工喝水编辑 | Panel 的 Health / Journal 页面重做或新增今日 UI |
| Insight Health 的纯回看/分析总览；Panel / AI 对新数据层的兼容 | Journal Insight UI、手机端、`archiveRoot` 拆分、SQLite 文件同步、通用 Event 模型 |
| 有界 Garmin capability probe 与已确认的抓取目录 | Activity/FIT 详情、Garmin Nutrition、女性健康、设备设置、成就/挑战 |

**最高验收原则**：

1. 除旧 JSON 不被带入新库这一明确选择外，用户不需要理解或操作数据库；读写、保存失败和同步状态维持直接可信的产品体验。
2. 本地变更从第一天起具备稳定 ID、来源、版本、软删与原子 outbox；后续 `orbita-sync` 直接消费记录快照，不能迫使客户端再次迁移真源。

## 2. 已确认的产品与数据决定

### 2.1 新库与旧 JSON

- 实际路径为 `{journalRoot}/journal.sqlite`；`journalRoot` 继续遵守既有设置，默认才是 `dataDir`。
- 文件不存在即自动创建空库。**不读取、不导入、不删除、不改写**旧 `{journalRoot}/journal/YYYY.json`；它仅保留为历史备份。
- 因而首次启用后的 Garmin 数据须重新同步，历史 meal 须用户自行补记；不得以 JSON fallback 假装旧数据仍在线。
- App State、凭据、token、Garmin 原始响应/文件和缓存、Finance `.bean` 均不迁入该库。SQLite 文件绝不经 SMB、Git、网盘或文件复制方式同步。

### 2.2 专业事实表，而非 `daily` / `routine` 大对象

`daily` 与 `routine` 不再是混合来源的持久化容器，而是日期页查询投影。新库不建立万能业务 Event 表，也不把每类事实塞进一段不透明 `data` JSON。

| 类别 | 真源记录 | 所有权 / 关键时间 |
| --- | --- | --- |
| Garmin 汇总与时序 | `daily_metrics`、`metric_day_snapshots`、`sleep_nights`、Garmin nap、活动摘要 | `garmin`；时序保存 UTC；夜睡另带 `wake_date` |
| Health 手工事实 | `meals`、手工 `naps`、手工 `activities`、`body_measurements` | `manual`；有精确时间才存 UTC，否则仅 `local_date` |
| Journal 手工事实 | `events`、`moods`、`notes`（UI 名称「随记」） | `manual`；业务日固定 `Asia/Shanghai` |
| 同步基础 | 各事实共享的 ID / 来源 / revision / 删除字段；`sync_outbox` | 不定义新业务对象 |

每条可同步事实都有不含文件路径或年份的全局 UUID、`source`（首版仅 `manual | garmin`）、`revision`、创建/更新时间和 tombstone。日期、来源与领域字段独立保存。手工记录可只有 `local_date`，没有用户填写的时刻就不得虚构 `occurred_at_utc`。

### 2.3 所有权、读写和删除

- **Garmin 来源事实永远只读且不可删**；纠错在 Garmin 完成后手动重新同步。0.0.18 不做字段 override、双真源、恢复 Garmin 或 Orbita → Garmin 上传。
- 手工 Meal、Nap、运动、体重/体成分，以及 Event、Mood、随记均可新增、编辑、软删和撤销。手工 Nap 与 Garmin Nap 可同日共存，后续同步不能清掉手工条目。
- Meal 是独立的 **Orbita Health** 事实。保存发生日期、可选时间、餐别、食物/描述/备注和预留 `nutrition`（kcal、蛋白质、碳水、脂肪等）；日摄入和 Panel 三环从 Meal 聚合，绝不再存第二份可变日热量。
- Note 是独立的 **Orbita Journal** 事实：日期必填、时间和标题可选、正文必填。
- 手工删除立刻从正常查询隐藏，提供 5 秒撤销；底层保留 tombstone，不自动清理。撤销是新的版本化 upsert，不是物理回滚。服务器确认与回收留给 `orbita-sync`。

### 2.4 原子 outbox 和 Garmin 快照

- 每次手工新增、编辑、软删、撤销，均在同一 SQLite transaction 中写事实、递增 revision 并追加 outbox。
- Garmin 只有**规范化内容**真实变化才写入新 revision / outbox；`fetched_at` 不进入内容 hash，不得造成同步噪声。
- 日摘要与全天 HR、Stress、Body Battery、Respiration、SpO2、HRV 等高密度数据按“**本地日 + 指标 + 规范化快照**”同步，不逐采样点写 outbox。一个快照保存样本、coverage、内容 hash 和来源时间；缺失、接口不支持与零值必须可区分。
- outbox 至少包含 `op_id` UUID、领域/记录类型、记录 ID、revision、`upsert | delete`、origin、可重放的完整快照、创建时间。0.0.18 不发网络、不 ack、不解决冲突、不清理 outbox。
- 任一事实或 outbox SQL 失败即整个 transaction 失败，向调用方返回可行动错误；禁止 JSON fallback 或“已保存”假象。

### 2.5 Garmin 范围与安全

初版 catalog 已由 [ADR 0008](../../adr/0008-garmin-health-initial-fetch-catalog.md) 确认：日健康摘要；全天 HR、Stress、Body Battery、Respiration、SpO2；睡眠详情与 HRV；喝水；体重/体成分；血压只做可选 capability probe。

实施开始前必须先做一次有界、只读的“今天 + 昨天”探测，核对真实字段、采样频率、空洞、时区和速率预算；它不得触发 SSO、重试风暴、数据写入或自动历史回补。所有 Garmin 同步路径继续遵守零 SSO、token 与限流契约。

## 3. Insight 初版

### 3.1 共通边界

- Journal 只进入 SQLite / 同步基础；其 Insight UI 延期。0.0.18 仅保证 Panel、AI 和既有调用通过新的领域读写边界兼容 Journal 数据。
- Insight Health 是纯回看/分析，不承担创建、编辑、删除、跳转、详情下钻或统一记录管理；手工 Health 的既有 CRUD 继续留在 Panel。
- Panel 迁到新读取边界；除去移除手工喝水编辑，不新增 Health / Journal UI，也不承担历史检索或批量管理。

### 3.2 Health 总览

Health 默认入口是 **Health 总览**，由三层组成：

```text
连续日内轨道 → 长期趋势 → 当前选中日摘要
```

- 轨道是可连续平移的时间线，不是锁死在某一天的图。选择日期 `D` 的默认视口是 `D-1 22:00 → D 24:00`（26 小时）；平移时以视口中心的上海日期更新日期控件和摘要，日期控件反向把轨道定位到该窗口。
- 共同横轴严格时间对齐；跨日明确标日期。hover 提供统一时间游标和 tooltip。没有有效样本就不画元素、不补 0、不连跨空洞曲线；数据缺失与同步失败是不同状态。
- Track 1：Sleep/Nap 区间、HR、夜间 HRV、SpO2；Respiration 初版抓取但默认关闭。Track 2：Stress 与 Body Battery（0–100 左轴）。Track 3 三分区：上 Activity 区间条、中 Steps 柱+累计线、下 Meal pill（Lucide 刀叉 + 中文餐次，DOM 叠层）。Activity/FIT 详情不拉取、不实现详情页。
- 三轨独立卡片 + 共享时间网格 overlay；图例为 Lucide 图标（SpO2 为 lungs + 渐变描边）。轨道仅提供 hover 信息，不做点击、编辑、删除、跳转或详情下钻。
- 图例始终存在，首次进入默认开启全部指标。点击一项后它变灰并隐藏对应图形；开关状态跨日期、再次进入 Health 后保留。统一 tooltip 只显示仍开启的指标。
- 顶部统一 Garmin 状态：成功显示最后成功时间并可手动同步；同步中显示进行状态；失败在同处提供重试。不得在每条曲线旁塞重试。
- 长期趋势范围固定 `7D / 30D / 90D / 1Y`，仅控制趋势。首次只同步最近 7 天；切到更长范围时只展示本地已有数据，并提供明确的「获取更多历史」操作，绝不自动拉取一年。布局为一行四张等宽面板：恢复（睡眠/HRV/SpO2）、身体与能量（体重/记录能量平衡）、喝水、Stress；各子指标独立纵轴，共享日期轴。
- 趋势的主值为当前窗口聚合（睡眠/HRV/Stress/喝水等取日均，体重取窗口最新测量），并同紧邻的上一等长窗口比较；不使用“相对昨天”。当前日摘要只讲选中日实际值，并包含能量卡：**已记录摄入 / Garmin 消耗 / 记录差额**。0 餐显示“未记餐食”，不能当作 0，也不得进入能量差额平均；能量趋势必须显示有餐食记录的天数覆盖度。
- 轨道图例始终存在；某个指标从未在本机出现则不显示其摘要卡。曾出现过但选中日缺失时摘要显示 `—`。趋势面板仅在当前窗口至少有两个有效日点时显示。
Journal 的 Insight 管理、筛选和搜索均延期；本计划不为它新增 UI。
