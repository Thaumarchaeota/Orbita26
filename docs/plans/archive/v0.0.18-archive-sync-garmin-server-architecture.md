## 1. 范围与非范围

本架构解决三件事：

1. PC 与手机对 Orbita local-first Archive 事实的双向同步；
2. Linux 服务端作为 Garmin **单向**采集、规范化和分发者；
3. 从本地提交到设备 ACK 的可追溯、可报告和可调试同步链。

明确不在本轮范围：

- TickTick / Dida、OAuth、外部 command、双向映射和任何 TickTick worker；
- Finance、`.bean`、Finance Service 或 Finance 多副本协调的**实现**；Finance v2 Transaction / Posting 未来仍复用本文定义的通用 Sync Core，不另建 Finance 同步机制；
- 当前 Journal / Health SQLite、`dataDir`、`archiveRoot` 的迁移；
- Travel、Media、Knowledge 的对象模型；
- Garmin 凭据导入、真实 API 调用、SSO、原始 FIT/路线的客户端分发。

TickTick 是 Plan 的可移除外部适配器，不是 Sync Core 的权威，也不与本地 Plan / Work 事实共享写入通道。

## 2. 不可违反的数据边界

Registry 的 `classification` 决定同步语义，而不是物理表：

| 分类 | 是否可独立引用 | 同步方式 | 例子 |
| --- | --- | --- | --- |
| `object` | 可作为 `ArchiveRef` / Connection Member | 可独立成为 aggregate 根 | Connection、Entry、Meal、Activity、Project、PlanItem |
| `data` | 不可 | 随所属 aggregate 或独立 data-root 同步 | Health Day、Health Sample、Plan Group |
| `component` | 不可 | 永远随父 aggregate 原子同步 | Connection Member、Sleep Stage、Interval、Schedule Block |

`ArchiveRef = { domain, type, id }` 只接受 registry 中 `object`；UUID 不编码类型。Connection、Timeline、投影、缓存、outbox、remote shadow、外部 command 和 connector receipt 都不是 Archive 事实。

领域保持真源与规则所有权。服务端保存规范化副本、历史、投递状态和冲突，并不把不同 Object 塞进万能 Event / JSON 表，也不以文件复制方式同步 SQLite 或 Markdown 目录。

## 3. 同步的两个原子单位

### 3.1 `SyncAggregate`

`SyncAggregate` 是一个可独立校验、版本化、冲突和恢复的完整领域快照：

```text
aggregateKey = { domain, type, id }
```

`health/day` 在 S0 前不进入生产 allowlist：Registry 目前只定了业务键 `localDate`，尚未定其稳定 `id`、多 Garmin account 行为或时区迁移。S0 必须确定稳定 day id，以及 `(account, connectorAccount, businessTimezoneVersion, localDate)` 的唯一性和 Garmin upstream 日期的解释规则；之后才可把 Day/Sample 作为 aggregate。

它不是统一的业务表。每种 aggregate 的 payload 仍由 Registry 和领域约束决定。

| Aggregate 根 | 必须随之原子提交的记录 |
| --- | --- |
| `archive/connection` | Connection、本体 detail、全部 Connection Member |
| `journal/entry` | Entry、本体 detail |
| `health/meal`、`health/nap`、`health/activity` | Object 本体 |
| `health/sleep-night` | Sleep Night、完整 Sleep Stage Segment 集合 |
| `health/day` | Health Day、该日完整 Health Sample 集合 |
| `work/segment` | Segment、全部 Interval |
| `plan/plan-item(kind=schedule)` | PlanItem、全部 Schedule Block、仅 PlanItem detail |
| Project、Node、Session、普通 PlanItem | 各自 Object 本体 |
| `finance/transaction`（未来） | Transaction、全部 Posting；Observation、对账工作数据与 `.bean` materialization 不在 aggregate 内 |

Component 和 strict-child data 不拥有独立 cursor、ACK、Connection 引用或冲突卡片；它们只出现在父 aggregate 的完整 canonical snapshot 中。`health/day` 是 data，但在其稳定 identity 收束后，因日快照替换语义而作为独立 data-root aggregate。`plan/group` 和带 ScheduleBlock detail 的 PlanItem 暂不进入生产 allowlist；在 Group 的稳定字段、树、删除事务及 Block detail namespace 定案前，PlanItem 的 `groupId` 必须为 null。

### 3.2 `CommitGroup`

一个用户动作可能同时改变多个 aggregate，必须用 `CommitGroup` 保持领域原子性，而不是发出若干中途可见的记录更新。例如：

- 创建 Connection 并加入成员；
- Node 移动父级并调整排序；
- Segment 的明确操作同时更新其关联 Schedule；
- 完成 Node 时执行全后代检查后更新受影响状态。

单个客户端 `CommitGroup` 有 account-scoped 的不可变 `opId` 与 semantic group hash，包含 `1..N` aggregates。服务端必须在一个数据库事务的 post-group view 中验证并接受或拒绝整个 group；同 `opId` 而不同语义必须拒绝。客户端 remote apply 亦必须在一个本地事务中写事实、shadow、inbox receipt 和 cursor。普通编辑只是只含一个 aggregate 的 group。

外部 connector 不伪装成客户端 CommitGroup。它使用 `ServerCanonicalCommit { connectorRunId, traceId, fence, observedAt, mappingRevision, aggregates }`：可复用同一 aggregate revision/change-log 发布管道，但不携带 deviceId、clientCommittedAt、客户端 outbox 或客户端授权。服务端 audit 必须永久区分 `actor=device` 和 `actor=connector`。

## 4. 规范 envelope、版本与兼容性

每个 group 传输完整快照而非 patch：

```text
CommitGroup {
  protocolVersion, registryVersion, opId, deviceId, clientCommittedAt,
  aggregates: [{
    aggregateKey, baseServerVersion,
    mutation: create | replace | tombstone | restore,
    canonicalPayload, payloadHash,
    referencedRecordKeys, detailManifest
  }]
}
```

- `serverVersion`：aggregate 单调版本；`changeSeq`：账户内服务端投递序列；两者不得与本地 revision 混用。
- `payloadHash` 为真正规范化序列化后的完整 aggregate 内容 hash，包含受管 detail manifest，不包含本机路径、outbox、UI 缓存或 connector 私有状态。
- `baseServerVersion` 等于 current 才可接受。若内容 hash 相等则幂等；否则创建 durable conflict，绝不最后写入获胜。
- `tombstone` 是版本化事实；`restore` 是显式新 mutation。物理 purge 必须同时满足领域引用规则、保留期、活跃设备投递下界和恢复策略。
- 服务端以 Registry 验证 domain/type/classification、variant、父子、时间、引用和领域 invariant；Registry 是语义表，不是 DDL。
- 未知 type 不允许由客户端新建或修改；仅已由服务端保存的 opaque revision 才可转发/备份。已知 type 有未知字段时客户端显示兼容风险并禁止重写。不能因旧客户端保存而丢字段。

需要先落一份跨语言 canonicalization contract（含 RFC 8785 vectors、Unicode、浮点边界与 detail hash），然后才实施 wire protocol。

## 5. Detail Markdown 不是文件同步

`{archiveRoot}/details/{id}.md` 只是本机物理路径，不是网络身份或共享文件。

1. `hasDetail=1` 必须在同一 group 提交 `{detailId, sha256, byteLength, utf8Markdown}`；`hasDetail=0` 必须提交受版本化的删除状态。
2. 客户端下载 detail 后先写 staging、校验 hash，再与 aggregate 事务一起原子发布；成功持久化前不得 ACK。
3. 服务端把内容作为账户隔离、加密的 blob 版本保存；日志、普通 metrics、support bundle 和 Timeline 不得出现正文。
4. 并发 detail 编辑默认产生 whole-detail conflict，保留 base/local/server 三份；未定义行级合并前不得静默合并。
5. ScheduleBlock 的 `hasDetail` 尚缺明确 namespace、生命周期与冲突语义；在确认前不得实现其 detail 同步，也不得允许带 Block detail 的 Schedule 进入生产。

Journal note 固定无 detail，Journal document、Connection 和 PlanItem 遵循 Registry 规则。读取到缺失本地文件显示“详细内容缺失”，仅用户显式操作可重建空白 detail。

## 6. 双向 PC / 手机同步

```text
领域本地事务
  └─ facts + local shadow + immutable outbox CommitGroup
       └─ push ──> server validate / history / change log
                         └─ pull issued delivery ──> client durable apply
                                                          └─ ACK
```

### 写入与 push

- 本地写成功即为本地成功，UI 显示 pending，不伪称已同步。
- facts、detail staging、outbox 与本地 shadow 必须同一 SQLite 事务；远端 apply 绝不再次生成 outbox echo。
- 服务端校验账户/device、Registry 版本、hash、引用、领域 invariant、group 原子性和 `baseServerVersion`，再写 current、不可变 revision、change log、conflict 和 operation event。
- `opId` 幂等键必须覆盖完整 group 语义；服务端已接受但响应丢失时重试返回同一 receipt。

### pull、应用与 ACK

- 注册新设备后，服务器生成固定 `snapshotCutoverSeq` 的账户一致性 bootstrap；客户端完整落盘后 ACK cutover，随后只 pull `> cutover`。绝不复制 PC SQLite、MD 目录、token 或 cursor。
- `pull` 每页产生服务端签发的 `deliveryId` 和连续 `issuedChangeSeq`。设备只能 ACK 自己已被签发且连续的水位；不能报账户 global head，也不能以客户端 cursor 跳过缺页。
- 客户端按 delivery id 去重，校验 schema/hash 后一次事务 apply；ACK 丢失只会安全重发该页。
- cursor/ACK 只优化投递，不单独授权历史清理；retention 必须考虑 tombstone、冲突、恢复和已撤销/过期设备策略。

### 冲突与删除

冲突以 aggregate 为单位，保存 base/local/server snapshots 与 detail refs，冻结该 aggregate 的自动覆盖，但不阻塞其他 aggregate。resolve 是新的 CommitGroup，显式 choose-local、choose-server 或手工快照。

Connection Member 的对象软删后引用保留并显示“已删除”；Connection 本体 tombstone 不删除历史成员。Node/PlanItem 有领域引用时必须 cancelled 而非物理删除。

## 7. Connection 与 Work / Plan 领域校验

服务端与客户端均预检，但服务端事务是最终权威：

- Connection member 必须引用 `classification=object`；同一 member 不重复；嵌套 Connection 禁止直接或间接环；对并发写做串行 cycle check。
- Work Node 父节点必须同 Project 且无环；完成/归档门槛、Phase 后代检查、Segment 引用和 Interval 时间并集仍由 Work domain 验证。Session start（至少一个 Segment）、Session end（收束全部 active Segment）和 Node completion 必须由一个列出完整 prospective aggregate set 的 CommitGroup 原子验证，禁止逐 aggregate 半提交。
- ScheduleBlock 每侧最多三条、顺序与主时段连续；Todo/Schedule 转换保持 PlanItem id、detail、Connection、group、recurrence 与历史。
- `Segment → Node`、`Segment → Schedule`、Work tree 是专门强关系，不能改写为 Connection。

Registry 与 ADR 0013 尚有需要收束的字段差异：Session 的 `status/title`、Node 描述、Schedule–Segment 双方字段、`startAt` 命名、Plan Group 的稳定字段和删除/排序规则。其 schema 未定前，相应 record type 只能设计为 reserved，不进入生产 allowlist。

## 8. Garmin：服务器唯一单向导入者

Garmin 是 Orbita Health 的外部事实来源，不是 Archive Domain、同步客户端或 Connection Member。服务器是唯一 Garmin credential holder、API caller、normalizer 和 Garmin-origin writer；PC/手机只能从 Sync Core pull。

```text
Garmin upstream
  → encrypted raw receipt / external mapping (private adapter infrastructure)
  → deterministic normalizer + registry validator
  → Health ServerCanonicalCommit
  → canonical current/history/change log
  → PC / mobile delivery and ACK
```

### Garmin 事实边界

- Activity、Sleep Night 是 Object；Sleep Stage 是其完整 child data set；Health Day + Sample 是按 `localDate` 的完整 data aggregate。
- external mapping 用 `(connectorAccount, externalKind, externalId)` 映射稳定 Orbita UUID；外部更正复用 UUID。
- Garmin 日快照 hash 相同不写；不同则**同一事务**更新日字段、删除该日所有 Garmin sample、写完整新集，再发布一个不可拆分 aggregate revision。禁止逐点 merge。
- 首版 Health Day/Sample 必须 Garmin-only，或另行设计 source partition；当前 Registry 不允许静默混手填日指标。
- 外部列表暂时消失只能形成 `missing_candidate` reconciliation finding，不能立刻 tombstone；删除宽限期和用户确认策略待定。
- 原始 payload、FIT、路线、逐点指标、cursor、lease、credential、raw shadow 和 connector 状态全属 adapter infrastructure，绝不进入 ArchiveRef、Connection、用户 Timeline 或普通同步 payload。

服务端必须持久化 authoritative ownership/provenance：`(account, aggregateKey, authority=garmin|user, connectorAccount?, externalMapping?, sourceRevision)`。它是每次 push、restore、resolve、tombstone 的授权输入；客户端 payload 的 `source` 仅是业务数据，绝不用于授权。只允许 Garmin Write Gateway 创建或 replace `authority=garmin` 的 aggregate；普通设备不得把既有 Garmin aggregate 重标为 manual，也不得 delete/restore/resolve 它。手工与 Garmin 同类 Object 必须使用不同 UUID；用户注释/override 将来只能走显式独立层。

每份 raw receipt / FIT / route 必须作为 adapter 私有、不可变、加密对象或经验证外部定位保存，记录 raw hash、normalizer version、获取窗口和授权下载策略；其保留、删除、备份和用户下载策略仍是开放决定，不能只留 hash 后静默丢失原始运动资料。

### 单写入状态机

```text
disabled → credential_required → read_only_discovery → backfill
→ catching_up → active ↔ degraded | paused → revoked
                         └→ quarantined (manual release)
```

每次 run：`scheduled → lease_acquired(fence) → fetch → raw_receipted → normalized → validated → staged → reconciled(noop|applied|quarantined) → published → complete`。

唯一 Garmin Write Gateway 必须在每次写入事务中验证 account、connector phase、未过期 lease、严格单调 fencing token 和可信 connector principal；禁止以客户端 `origin/source` 声明授权。旧 worker、重复 job、失效 fence 和普通设备上推 Garmin-owned aggregate 一律返回 `ownership_violation`。

桌面 collector 迁移只可：desktop drain 到固定 checkpoint → server read-only discovery/reconciliation → 显式批准 server active → desktop normal Sync replica。回滚先停止并 join server worker、撤销 fence、记录水位，再恢复唯一 collector；绝不双写。

## 9. 追溯、报告与 Sync Doctor

所有可观察状态均为不可变事件，不写业务 payload。三个标识分别承担不同职责：

| 标识 | 含义 |
| --- | --- |
| `opId` | 一次 CommitGroup / Garmin canonical commit |
| `traceId` | 一轮同步或 connector run 的跨步骤关联 |
| `deliveryId` | 服务端向一个设备签发的一次投递 |

必须可查询以下 durable 链：

```text
local fact committed → local outbox durable → push attempted
→ accepted | deduplicated | conflicted | rejected
→ change published → delivery issued → client durable apply | failed → ACK
```

Garmin 在此链前增加：`fetch → raw receipt hash → normalize → validate → reconcile → canonical commit`。

每个端也必须有自己的 append-only audit：客户端记录 `localOpSeq/opId/deliveryId`、本地状态、稳定错误码和单调时间；服务器记录 server-issued `traceId/request receipt`、变更与投递事实。客户端上传的只是脱敏、可关联的状态证明或用户显式 support bundle，不能被当成服务端事实。Sync Doctor 必须标示证据来源为 `client-reported` 或 `server-observed`，并以序列/因果顺序而非墙钟比较来处理时钟偏差。

持久化审计至少包含：

- aggregate revision/history：加密 snapshot/blob ref、hash、版本、base、actor、reason；
- operation event：脱敏 account/device/aggregate 指纹、版本、seq、delivery、outcome、error code、时间；
- device delivery：issued/applied/ack watermark、延迟、重试与 schema compatibility；
- conflict：base/local/server refs、状态与 resolution；
- Garmin account/run/receipt/mapping/reconciliation：窗口、cursor 前后、限流、hash、coverage、缺失候选和 fence；
- backup/restore、migration、容量和 retention 状态。

日志与 support bundle 只允许稳定错误码、HMAC 化标识、版本、hash、计数和时间；严禁 Markdown、健康值、原始 Garmin payload、FIT、token、OAuth code、凭据、SQLite 错误原文或本机路径。

普通设备 token 只能看自身 delivery 与脱敏摘要。跨设备时间线、connector audit 和账户支持包需要独立受控 admin/support capability，并记录该诊断查询本身。

稳定错误分类至少有：`auth`、`schema`、`compatibility`、`invariant`、`base_version`、`conflict`、`detail_hash`、`storage`、`lease_fence`、`connector_auth`、`rate_limit`、`normalize`、`reconciliation`、`delivery`、`client_apply`、`ack`。

## 10. 实施顺序与强制验收

1. **S0：Registry/协议收束。**补齐 aggregate map、canonical contract、schema compatibility、detail manifest、未定 Registry/ADR 字段的决定；不写生产数据。
2. **S1：身份与客户端 Sync Core。**先定 account、设备公钥/凭据、一次性 enrollment、撤销/过期、最小 protocol/registry capability、换机和 bootstrap authorization；再实现本地 outbox/inbox/shadow、CommitGroup 事务、remote apply、delivery/ACK、冲突与 tombstone。
3. **S2：服务器协调器。**账户/device/auth、current/history/change log、blob store、conflict、retention、Sync Doctor、隔离 restore。S1/S2 任一身份模型未验收前，禁止真实 Archive 数据或 seed 上传。
4. **G1：Garmin connector。**先 discovery/report，再 backfill/catch-up，最后单 writer cutover；不与 TickTick 同期上线。
5. **W1：TickTick。**另立设计和计划，不能复用 Garmin write gateway 或改变本地事实同步。

上线前的故障演练必须涵盖：双端离线并发、CommitGroup 中断、响应/ACK 丢失、乱序重放、旧 schema 写入、detail 缺失/hash 错误、Connection cycle、Node 跨 Project/cycle、Sleep stage 重叠、HealthDay 完整替换、旧 Garmin fence、重复 page、partial snapshot、外部消失，以及恢复后 reconciliation。任何一个场景都必须能从 `opId / traceId / deliveryId` 定位责任边界。

## 11. 实施前必须由维护者决定

以下不是实现者可自行猜测的字段细节：

1. aggregate map 与跨 aggregate CommitGroup 上限；
2. Markdown 最大大小、服务端可见性、加密/密钥托管、保留与合并策略；
3. tombstone、history、撤销设备和 GC 保留期；
4. Connection 删除/恢复、未解析引用、成员排序、最大嵌套深度；
5. Garmin external delete/恢复语义、missing grace、历史回拉窗口、raw/FIT 保留策略与 Business Time Zone；
6. Garmin Activity/Sleep 的人工注释或 override 是否另立层；
7. Registry 与 ADR 0013 的 Work/Plan 字段差异及 Plan Group 完整模型；
8. 初始 seed 的账户模型、最大离线期、订阅域与灾备 RPO/RTO。

在这些决定和 S0 L3 证据齐全前，服务端不得接收真实 Archive 数据，也不得启用 Garmin 写入。
