## 1. 目标、范围与原则

在 Orbita Insight 的 Finance 领域内重建 Finance UI 与账本读写管线。目标不是给现有页面打补丁，也不是做 Beancount IDE；目标是一个可靠、顺滑的本地账本客户端：用户在内存中整理候选版本，经候选验证和明确确认后，才由唯一 Commit 边界原子写入当前年度账本。

### 1.1 必须达成

1. 记一笔、inline 编辑、软删、时间编辑和 CSV 导入均只改内存工作副本，绝不绕过 Commit 写盘。
2. 一个受管理的 `ledger/YYYY.bean` 可被完整 canonical render，但不支持的 Beancount 内容必须被定位并阻断提交，绝不能被静默删除。
3. 界面结构、滚动、弹层、异步加载和账本状态解耦；UI 重建不能改变写入语义。
4. 同日顺序、稳定交易 ID、账户/币种约束、候选校验和诊断归属各有单一所有者。同日顺序由 transaction `time` metadata 与数值 `seq` 稳定兜底决定，不提供用户拖拽重排。见 [`ADR 0002`](../../adr/0002-finance-chronological-order-without-drag.md)。
5. 体验应保持“即时但不冒进”：局部状态立即反馈、长列表不跳动、切换不丢上下文、失败保留用户工作副本。此处是对成熟客户端体验的借鉴，不要求模仿任何产品的视觉或额外功能。

### 1.2 本轮不做

- 手机端、NAS、公共 Web API、BQL、Rust 重写 Parser/Commit。
- 跨年度编辑/一次 Commit、多文件交易 Commit、外部编辑器或 Fava 的并发合并、revision 保护。
- 投资域、lot、`@` 单价、`{}` cost、commodity，以及任意 metadata 编辑器。
- 跨年度统计、Dashboard 真实指标的额外产品定义、跨领域 Connection 的产品形态。
- Pad/Balance 的完整 CRUD 或未确认的信息架构。

### 1.3 未决定事项：必须停在边界

以下不是“留给实现者自由发挥”，而是禁止自行决定：

1. Pad/Balance 的 CRUD、同日编辑和排序规则；本轮只做 §7.3 定义的只读最小卡片。
2. 账户管理的最终信息架构；本轮暂放 Finance 顶部右侧二级管理入口，但不得据此决定长期导航。
3. 跨年度统计、投资域、Connection 及其 metadata 以外的关系存储。
4. validate/commit 未被本规格列出的精确 HTTP 字段与 token 的存储细节；可以实现本规格规定的安全语义，但不得杜撰产品字段。
5. 仅出现在旧计划中的 canonical 排版细节、动效时长、Dashboard 卡片和指标、remark 长度、首屏日期范围等。

实现者必须先完成这些对象的解析、候选校验、canonical render 与诊断；在没有新的产品决定前，不得用“自动配对”“固定在交易后”等临时规则伪造 UI 语义。

## 2. 运行环境与不可破坏边界

```text
Orbita（单一 Tauri 进程）
├─ Orbita Panel（main）          不启动 Finance Service
└─ Orbita Insight（admin）
   └─ Finance UI
      └─ loopback HTTP → Python Finance Service
         ├─ Parser / canonical renderer
         ├─ candidate validator + Beancount loader
         └─ atomic writer
```

- Finance 只在 Orbita Insight 中提供完整 UI；不要拆成第二个应用、iframe 或新的常驻服务。
- Panel、Agent 与应用启动不得启动 Python。Insight 打开时异步 ensure Finance Service，窗口显示不得等待 Service。
- Service 继续使用既有 sidecar 生命周期、数据根与端口契约。本轮不改变其启动时机、根路径或端口策略。
- 客户端只能使用 Rust 返回的实际 loopback base，不能猜测或回退到 `:8000`。重试必须重启/重新连接受追踪且根目录正确的 Service，不能收养未知健康端口。
- 本轮前提是个人单机使用：不支持 Finance 打开期间的外部并发写入、合并或 revision 保护；代码注释与测试不可掩盖此限制。

### 2.1 数据根与文件所有权

唯一数据根是 `{dataDir}/bill/`：

```text
{dataDir}/bill/
├─ account.bean
├─ category.bean
├─ ledger/YYYY.bean              # 当前唯一 write_target
└─ .bkeasy/settings.json         # write_target、reporting_currency
```

- `write_target` 必须是相对 `bill/` 的 `ledger/YYYY.bean`。加载、候选校验与 Commit 每次只处理这一个文件。
- Service settings 决定实际 write target；客户端传入的 target（如保留）只可作为一致性断言。拒绝绝对路径、`..`、分隔符绕过或任何换出 `bill/` 的路径。
- `ledger/YYYY.bean` 是 Orbita 托管的交易文件：第一次成功 Commit 后，允许将受支持的完整内容 canonical render、排序并原子覆写。
- `account.bean` 与 `category.bean` 是账户声明上下文，普通 Finance Commit 绝不写它们。创建、标签、删除和迁移属于单独的受控结构操作。
- dataDir 切换是切换数据集，不是迁移：不复制旧数据；重载 webview，重启 Service；新空根不得显示旧账本。

## 3. 客户端架构与体验边界

### 3.1 模块职责

| 模块 | 唯一职责 | 明确禁止 |
| --- | --- | --- |
| `finance-shell` | Finance 内部路由、keep-alive、视图挂载/卸载、滚动位置 | 解析 bean、直接操纵子视图 DOM |
| `finance-layout` | Grid、窄宽模式、右栏显隐、滚动根注册 | 筛选、保存状态、领域数据 |
| `finance-chrome` | 标题、返回、筛选开关、导入、全局保存、二级管理入口 | 列表渲染、提交细节 |
| `ledger-store` | baseline、工作副本、加载状态、保存状态机、诊断、generation、全部 mutation | CSS/DOM 查询、表单展示 |
| `detail-surface` | 虚拟明细、inline 编辑、错误标记、滚动锚定 | fetch、Commit、文件写入、拖拽重排 |
| `composer` | 简单/高级交易草稿，创建内存 transaction | Pad/Balance 编辑、直接 Commit |
| `import-modal` | CSV 选择、纯前端解析/规范化、校验、确认 merge | 调用 bean Parser、独立导入页、直接写 bean |
| `structure-manager` | 账户/分类的结构操作 | 日常 transaction 编辑 |
| `balance-stats` | 已落盘账本的只读余额与轻量统计 | 工作副本金额 |

模块只能通过 `ledger-store` 的显式命令、事件或 mount handle 通信。禁止跨模块 `getElementById`、模块级可变 DOM 引用，以及由列表/Composer 自己 fetch 或 Commit。

### 3.2 生命周期、滚动与弹层

- 每个 `mount()` 返回最小 handle，例如 `getScrollTargets()`、`focusItem(id)`、`dispose()`；Shell 只通过 handle 保存/恢复滚动和焦点。
- `dispose()` 必须撤销该 mount 注册的 listener、`ResizeObserver`、pointer capture、timer 与异步回调。
- 详情列表以首个可见条目为锚点；补载和行高变化后修正 `scrollTop`，不得让用户阅读位置跳动。筛选后的 `LedgerItem` 数量不超过 10,000 时，使用同一 renderer 的全量连续渲染，不使用 spacer、窗口挂卸或日期组 observer；超过 10,000 时才启用虚拟窗口。虚拟窗口按完整日期组扩展，滚动导致的可见窗口更新必须同步完成；异步工作仅限高度测量等非可见正确性任务，不能等待 rAF 才使进入视口的卡片正确。见 [`ADR 0001`](../../adr/0001-finance-detail-render-threshold.md)（性能阈值；拖拽专属禁用逻辑已移除，见 [`ADR 0002`](../../adr/0002-finance-chronological-order-without-drag.md)）。
- 所有加载请求带递增 `generation` 和/或 `AbortController`；dataDir、write target、视图实例或筛选上下文变化后，旧响应不得写入 Store。
- Finance 根使用 `isolation: isolate`。普通内容区不参与 `z-index` 竞争；modal/popover 必须使用统一 overlay root/portal，不能被右栏、虚拟列表或 chrome 裁切。
- Finance 的 dialog/confirm 必须接入全局 `#orbita-modal-root` 和既有 motion 生命周期；confirm 是全局单例。不得把 backdrop 临时 append 到 body/任意 `#app`，也不得只用 CSS `z-index` 解决原生 click-through。弹层关闭后必须恢复窗口可交互状态。

### 3.3 交互信息架构

Finance 默认使用 Dashboard Hub，并钻取统计、明细/整理和导入；不要恢复六个平铺 tab。详情页的导入是原页 modal，不是独立的写盘工作流。账户/分类入口本轮暂放 Finance 顶部右侧的二级管理入口，不能因为现有代码存在就塞入主导航，也不代表长期信息架构已定。

Finance 注册到 Insight Host 的 cached `finance` root；Host 在顶级领域切换时只 activate/deactivate 此 root，不重新 mount 或清空 Finance。Finance 自己的 Dashboard、统计、明细和导入仍使用内部 keep-alive，保留 DOM、内存工作副本和滚动位置。加载、筛选或弹层的短暂状态不得重置用户正在编辑的账本会话；完整 Host 契约见 [`v0.0.17-insight-spec.md`](v0.0.17-insight-spec.md)。

### 3.4 UI 架构闸门（拒收条件）

以下任一成立即**不得**将 Finance UI 标为完成，也不得用 Parser/API/Store 测试替代：

1. **禁止套壳**：不得在旧 `#detail-list` / `.entry-block` DOM 与 CSS 上仅外包 `page-shell` 即声称重构完成；明细必须由 `detail-surface` 拥有滚动根，卡片使用 `detail-card`（或后继 surface）类名体系。
2. **禁止叠盖布局**：`finance-layout` 右栏必须是 CSS Grid 的正常列（`grid-template-columns: minmax(0,1fr) var(--ledger-rail-width)`），**不得**以 `position: absolute` + `translateX` 作为主布局；窗口宽度不足时主列与右栏仍不得重叠。
3. **禁止旧口径**：筛选、type、Composer 不得出现规格已排除的 type（如 `inv`）；不得保留仅用于旧 UI 的全局 DOM 查询作为模块边界。
4. **可见验收**：布局须在实机 resize（含 &lt;1280px）下确认主栏与右栏无重叠后，方可勾选 §9.2 布局相关项。

数据层（Parser、validate/commit、ledger-store）与 UI 层验收**分开计**；前者通过不能自动勾选后者。

### 3.4 架构重建闸门（不可用旧页面套壳）

本轮的 Finance 目标是**替换**旧 Detail 页面架构，不是在旧列表、旧卡片和旧全局 DOM 外包一层新的 page shell。现有 `page-shell`、`detail` renderer、`entry-block` CSS 和其调用链只可作为迁移前基线；当它们与本规格冲突时，必须移除或重写冲突部分，不能通过兼容分支继续保留为新页面的骨架。

以下任一项存在即拒收 Finance UI：

1. **布局不是真 Grid。** 明细主列与右栏必须是同一 layout grid 的正常 grid item。右栏不得用 `position: absolute`、`position: fixed`、`translateX` 或负 margin 作为主布局手段，也不得覆盖、挤压或遮挡主列。窄桌面宽度下，右栏只能保持已分配列宽，或进入明确的 collapsed/drawer 状态；主列绝不能与右栏重叠。
2. **Detail Surface 没有独立 root。** 虚拟列表、日期分组、卡片、滚动锚点和诊断标记属于 `detail-surface`。不得继续以全局 `document.getElementById("detail-list")`、`#save-btn`、`#filter-*` 或跨模块 DOM 查询协调；模块只能在自身 mount root 内查询自己的节点。
3. **明细卡没有重建。** 新 Detail Surface 不得继续把旧 `.entry-block` renderer/CSS 作为 transaction UI 的结构骨架。颜色、字体、边框等设计 token 可以复用；但 card 的 DOM 信息层级、编辑宿主、状态标记和 Pad/Balance card 必须由新 surface 统一产出。
4. **四层发生越界。** Chrome 只发出命令并呈现状态；Layout 只分配空间；Surface 只渲染和派发用户意图；Store 是唯一 mutation、fetch 和保存状态所有者。直接操作另一模块 DOM、绕过 Store fetch/commit 均视为未完成。
5. **拿功能测试代替 UI 验收。** Parser/API/build 通过不构成 Finance UI 完成证据。在此闸门通过前，不得将明细 UI、布局或 Finance 架构标为完成。

闸门先使用静态 fixture 条目跑通，再接真实账本数据：列表、右栏、筛选展开、Pad/Balance card、滚动容器和 overlay 必须在可见运行窗口中无重叠。实现者必须提供打开/收起右栏、切换筛选和调整桌面窗口宽度后的实机截图或录屏；仅提供 build 输出、单元测试或代码说明一律不验收。

## 4. 领域模型、身份与受支持语义

### 4.1 文档模型

Parser 先构造结构化 document model，再映射到编辑 UI；不得以“一条 transaction 大正则 + 字符串拼接”作为长期边界。

```ts
type DecimalString = string;
type ISODate = string;
type Seq = string;
type Metadata = Array<{ key: string; value: string }>;

type Posting = {
  account: string;
  amount: DecimalString;
  currency: string;
  cost_amount: DecimalString | null; // 仅支持 @@ total cost
  cost_currency: string | null;
};

type Transaction = {
  kind: "transaction";
  id: string;                         // 稳定 orbita-id；旧交易首次保存前可为临时 id
  source_file: string;
  source_line: number;
  date: ISODate;
  flag: string;
  payee: string;
  remark: string;
  tags: string[];
  postings: Posting[];
  metadata: Metadata;
  type: "expense" | "income" | "transfer" | "";
  seq: Seq;
};

type Pad = {
  kind: "pad";
  id: string;                         // 仅会话/诊断 identity
  source_file: string;
  source_line: number;
  date: ISODate;
  account: string;
  source_account: string;
  seq: Seq;
};

type Balance = {
  kind: "balance";
  id: string;
  source_file: string;
  source_line: number;
  date: ISODate;
  account: string;
  amount: DecimalString;
  currency: string;
  seq: Seq;
};

type LedgerItem = Transaction | Pad | Balance;
```

`_is_new`、`_deleted`、编辑中的诊断和 UI 展开状态只属于 `ledger-store` 的工作副本，不能写进 bean。`seq` 也是 API/内存顺序键，绝不落盘。

### 4.2 白名单与阻断策略

托管年度文件只允许：

- transaction：单/双描述字符串、tags、posting、`@` unit price、`@@` total price、`{}` cost、账户-only 空 posting、transaction-level string metadata；
- `pad`；
- 精确金额、单一币种的 `balance`。

下列内容必须返回含源文件和行号的阻断诊断：`open`、`close`、`event`、`price`、`document`、`note`、`commodity`、`custom`、`include`、options/plugins，或不支持的交易/分录语义（links、posting flag、posting metadata、非字符串 metadata 等）。Parser 可读取它们以报告问题，但不得让 renderer 接收它们，也不得在 canonical Commit 时静默删除。`@`、`@@`、`{}` cost 与账户-only 空 posting 属于支持语义：仅透明保存并由 Candidate/Beancount 校验，不在前端实现配平或投资 UI。

### 4.3 metadata、type 与稳定 ID

- 仅支持 transaction-level `key: "string"` metadata。未知 key 必须 parse → model → render 透明保留；没有通用编辑器不等于可丢失。
- transaction-level 字符串 metadata 中的 `time` 参与同日排序：仅当恰有一个 `time` 且值严格为 `YYYY-MM-DDTHH:mm:00+08:00` 且日期部分等于 transaction `date` 时，才得到有效 `HH:mm` 排序键；不规范或日期不一致的历史 `time` 原样保留但不参与排序。重复 `time` key 由 Candidate 阻断。其他 metadata 不参与排序、筛选或统计。
- `bkeasy-type` 是受控兼容 metadata。有效值优先于自动推断；手动选择 type 更新该键；清除 type 删除该键。
- 无 metadata 时，仅对**恰好两条** posting 的严格结构推断：`Expenses + Assets/Liabilities` 为 expense，`Income + Assets/Liabilities` 为 income，两侧皆为 `Assets/Liabilities` 为 transfer。其他复杂交易为 `type = ""`（未分类），不是错误，也不阻断保存。`inv` 不是本轮 type。
- transaction 的 `orbita-id` 必须为 `txn_` + 26 位 Crockford Base32 ULID，匹配 `^txn_[0-9A-HJKMNP-TV-Z]{26}$`；每笔交易恰有一个，重复或格式错误阻断 Commit。
- 新 transaction 创建时生成 ULID。旧交易打开时仍可用 `source_file:source_line` 作为会话身份；第一次正常 Commit 的候选模型补齐缺失 ID，且仅在确认写入成功后才进入真实 bean。
- canonical metadata 顺序固定为 `bkeasy-type`、`orbita-id`、其余 key 按字典序。未知 metadata 的 key/value 必须保留，但无须保留原排列。

### 4.4 同日顺序

Parser 按每个日期内的原始文件顺序分配 `a0`、`a1`……。Commit 对全部 `LedgerItem` 按统一比较器输出：`date ASC`、同日有效 `time ASC`、无有效时间记录在后、数值 `seq ASC`、稳定兜底。UI 展示为 `date DESC`、同日有效 `time ASC`、无有效时间在后、数值 `seq ASC`。不提供用户拖拽重排；Pad/Balance 无时间，排在当日所有有效时间 Transaction 之后。见 [`ADR 0002`](../../adr/0002-finance-chronological-order-without-drag.md)。

## 5. Parser、renderer、账户索引与候选验证

### 5.1 读路径

`parse_write_target()` 只读返回 `items`、文件定位、源顺序和支持性诊断；它不修复、不写回文件。

账户 parser 独立读取 `account.bean` / `category.bean` 的 `open` 声明，提供根类型、canonical name、允许币种、label 及派生 `label_path`/`brief` 的唯一索引，供 transaction、Pad、Balance 的选择和预校验共同使用。

### 5.2 canonical renderer

renderer 只接收已经通过模型约束的完整 `LedgerItem[]`，不接收 UI 拼接片段。它按以下顺序工作：

1. 过滤软删项；
2. 为首次 Commit 补齐缺失 transaction `orbita-id`；
3. 按统一比较器排序（`date ASC`、同日有效 `time ASC`、数值 `seq ASC`、稳定兜底）；
4. 以固定 transaction/posting/metadata 格式渲染完整年度文件；
5. 返回文本及不可变 `candidate_hash`。

必须有 `render → parse` 的自动化语义 round-trip 测试；不要求原始排版不变。任何白名单外内容都不得进入 renderer。

### 5.3 验证对象与诊断

Beancount 在既有 Python sidecar 内作为候选账本的最终会计语义校验依赖；不另启守护进程、不启用 BQL、不在键入时检查真实文件。

```text
完整 LedgerItem 工作副本
  → Orbita 模型 / 账户 / 币种校验
  → canonical render
  → 隔离临时 bill 上下文
       （候选 ledger + account.bean + category.bean）
  → Beancount load/check
  → diagnostics + candidate_hash + validation_token
```

临时上下文只能写入隔离临时目录，不能改真实年度文件。Orbita 校验负责字段级、可编辑的错误；Beancount 负责最终会计语义。

```ts
type CandidateDiagnostic = {
  message: string;       // 用户可读的短句
  item_ids: string[];    // 可为空，表示全局错误
  raw?: string;          // 仅日志和开发排查
};
```

一个诊断关联多个 item 时，所有 item 均显示错误态；界面只自动滚动/聚焦第一个。无法可靠归因的诊断必须保留为 Balance 或全局错误，禁止伪造“首个罪魁交易”。

## 6. API 与两步保存协议

Service 路径由 Service settings 绑定，客户端不能通过 payload 指定任意文件。所有失败响应必须保留面向用户的可行动信息；不得把失败包装为成功。

| API | 责任 |
| --- | --- |
| `GET /api/settings` / `PUT /api/settings` | 读取/设置相对 write target 与 `reporting_currency`；设置变更不重写交易。 |
| `GET /api/accounts` | 账户/分类声明、label 派生、允许币种，以及 Pad 专用 Equity 选择数据。 |
| `GET /api/entries` | 当前 write target 的分页/分段读取、支持性诊断和加载边界。 |
| `POST /api/validate` | 接收当前**完整**工作副本，产生并校验候选；绝不写真实 ledger。 |
| `POST /api/commit` | 仅确认同一已校验候选，执行单文件 atomic write。 |
| 结构 API | 创建、标签、删除扫描和账户迁移的受控上下文；与 transaction Commit 分离。 |
| 只读余额/统计 API | 只读已落盘真源，绝不读取工作副本。 |

### 6.1 validate / commit 的硬契约

- `validate` 必须取得完整 active items（含所有非删除项），服务端重新执行所有模型、账户、币种与候选账本校验。部分加载时不可调用。
- validate 成功返回 `validation_token`、`candidate_hash`、诊断（空）和必要的规范化 identity 回填；token 只对应这一候选。
- `commit` 只接受 token/hash（或等价的“完全同一候选”声明），并验证 token 未失效且 hash 未改变。禁止旧式 `files` map、多文件 Commit 和 `207` 部分成功协议。
- 无法证明提交的是已验证候选时，服务端必须拒绝，客户端回到 `edited` 并保留工作副本。
- Commit 使用单文件 atomic write。成功后客户端必须重新读取真实源并替换 baseline，不能以本地工作副本伪造成功。

### 6.2 保存状态机

```text
unedited
  └─ mutation / CSV merge / inline edit → edited
edited
  └─ 保存 → checking
checking
  ├─ 字段 / 模型 / 候选错误 → edited
  └─ validate success(token + hash) → confirming
confirming
  ├─ 任意语义 mutation → edited（token 作废）
  └─ 确认保存 → submitting
submitting
  ├─ atomic-write failure → confirming（保留工作副本与可重试 token）
  └─ success → authoritative reload → unedited
```

- `partial` 是全量年度条目尚未加载完成的加载保护，而不是保存结果。它期间禁止 validate/commit，以防局部 UI 覆盖整文件。
- 首次保存按钮进入 `checking`；候选通过后按钮只显示“确认保存”，不向普通用户暴露 Beancount 或候选文件术语。
- confirming 中的任一语义变更都必须作废 token 回到 `edited`；成功提交后才可清除 new/modified/deleted 视觉状态。
- 写入或网络失败不丢失候选；只有真实写入成功并重读后才报告“已保存到账本”。创建/编辑成功的即时反馈只能说“已加入待保存”。

## 7. 交易、CSV 与只读统计

### 7.1 Composer 与 inline 编辑

Composer 和 inline 编辑只能调用 Store mutation。Store 负责创建 transaction ULID、标记 `new/modified/deleted`、作废确认 token，并向列表/Chrome 通知。

- 简单模式支持支出、收入、转账，默认 `reporting_currency`；选择单币种账户时切换到该币种。
- 高级模式支持 2–10 条 posting、日期、payee、remark、flag、tags、`@@` 和手动 type；metadata 仅透明保留。
- 当两端没有共同币种或需要 `@@` 时，引导进入高级模式；简单模式不得暗含换汇算法。
- transaction、CSV 与 inline 编辑只能选 `account.bean` / `category.bean` 中已声明账户。未知账户、违反账户 `open` 币种限制均为可定位字段错误。
- 普通 transaction/CSV 不允许 Equity。Balance/Pad 的账户限制见 §8。
- 编辑、删除以及“记录”都不写盘；“记录”只把 transaction 加入工作副本。

### 7.2 CSV staging modal

导入位于详情页标题区、“保存”左侧。流程固定为：

```text
选择/拖放 CSV → 模板、表头和逐行校验 → 用户确认添加
→ merge 到工作副本（new 绿底）→ edited
→ 保存 → 候选校验 → 确认保存 → Commit
```

- modal 不离开详情页，不得成为单独的持久化导入页。
- CSV 只导入**普通两分录 transaction**，不承担复杂账本编辑。多分录、`@@`、投资、lot、`@`、`{}`、Pad 和 Balance 均不在 CSV 支持范围内。
- 模板的英文表头及顺序固定为：

  ```csv
  date,time,type,amount,currency,from_account,to_account,payee,remark,tags
  ```

  `date` 必须是 `YYYY-MM-DD`；`time` 可为空，非空必须是本地 24 小时制 `HH:mm`；`type` 只能是 `expense`、`income` 或 `transfer`；`amount` 必须为大于零的精确十进制数；`currency`、`from_account`、`to_account` 必填。`payee`、`remark`、`tags` 可为空；非空 `tags` 是以英文逗号分隔、无 `#` 前缀的标签列表。含英文逗号的 `tags` 字段必须按 CSV 规则整体加双引号。
- 类型决定账户根的合法组合和 transaction 的符号：expense 为 Assets/Liabilities（`from_account`，负数）→ Expenses（`to_account`，正数）；income 为 Income（`from_account`，负数）→ Assets/Liabilities（`to_account`，正数）；transfer 两端均为 Assets/Liabilities，from 负、to 正。账户不存在或币种不满足其 `open` 约束都是逐行、可定位的错误。
- CSV 解析器是 `import-modal` 内的纯前端解析/规范化器：它只把通过行转换为标准 transaction 草稿，再调用 Store mutation。它不读取 bean、不替代 `parse_write_target()`，也不承担最终会计校验。
- `time` 非空时，解析器仅在 draft 的 transaction-level metadata 写入 `time: "${date}T${time}:00+08:00"`；它不修改 transaction date 或 `seq`；merge 后按统一时间比较器重排展示顺序。
- 新选择文件替换旧 pending session；任一行失败时不得部分 merge。
- 确认添加后为每个新 transaction 创建 `orbita-id`；只清 modal pending 状态。
- CSV 不自动去重、不静默跳过、绝不自动 Commit。每次确认添加都是显式新增一批待保存交易。
- 导入成功后清空日期/type 筛选并定位首条新增记录，确保 new 条目立刻可见。

#### 7.2.1 CSV 解析/规范化器契约

实现一个无副作用的函数（名称可不同），其输入是文件文本、当前账户索引、当前 write target 与用户选择的行序；输出只能是完整的 `Transaction[]` 草稿或按 CSV 物理行号分组的错误集合。它不能直接 mutate Store、请求 Service 或写文件。

```ts
type CsvImportOrder = "forward" | "reverse";

type CsvRowError = {
  row: number;                 // 表头为第 1 行；数据行从第 2 行计
  field: string | null;        // 文件/整行错误可为 null
  message: string;
};

type CsvParseResult =
  | { ok: true; drafts: Transaction[] }
  | { ok: false; errors: CsvRowError[] };
```

按以下固定顺序实现：

1. 以 UTF-8 读取文件，只移除开头 BOM；使用能正确处理双引号、内嵌逗号、换行和转义引号的 CSV 解析器。不得用 `split(',')`。完全空白的尾行可忽略；其他空行和字段数不为 10 的行都是行错误。
2. 表头在 BOM 移除后必须与 §7.2 的十个字段**逐列完全一致**；不得猜测中文别名、调整列序、容忍缺列或静默丢弃额外列。
3. 逐行 trim 文本字段，校验日期、可选 `time`（`HH:mm`）、type、正金额、必填币种和两端账户；再用与 Composer/inline 相同的账户索引校验根类型、账户存在性与 `open` 币种限制。所有发现的行错误都收集后一次返回，不只报告首错。
4. 规范化 `tags`：空值为 `[]`；否则按英文逗号切分、trim 每项、移除空项。其余可选字符串保留为 `""` 或规范化后的文本，不能用 CSV 值注入 metadata。
5. 将每个通过行建立为标准两 posting `Transaction`：金额使用精确十进制字符串；posting 正负号和账户根组合严格遵守 §7.2；`cost_amount`/`cost_currency` 均为 `null`；metadata 写入与 CSV `type` 相同的 `bkeasy-type`、新生成的 `orbita-id`，以及非空 `time` 对应的 `YYYY-MM-DDTHH:mm:00+08:00` 字符串。
6. 每个草稿使用对应 `orbita-id` 作为 `id`，`source_file` 为当前 write target，`source_line` 为 `0`（仅新建条目的会话占位，不能用作身份或排序），并由 Store 在 merge 时按选定行序、逐日期分配 `seq` 与 `_is_new`。
7. 行序控件只影响 merge/seq：`forward`（默认）按文件数据行从上到下处理，`reverse` 按下到上处理。它不修改日期、不在解析器中排序，也不改变文件原文。
8. 任意错误时返回 `ok: false`，不得产生 drafts 或调用 merge；全部通过后才显示预览和“确认添加”。确认添加时 Store 将整个批次作为一个 mutation merge，随后统一进入 `edited`。

### 7.3 Pad/Balance 最小展示

Pad 和 Balance 必须像 transaction 一样进入详情虚拟列表、日期分组、滚动锚定和候选诊断，但本轮仅只读展示，不提供 inline 编辑、删除、Composer 或 CSV 入口。

- Pad 使用与普通条目相同的 card 外壳，内容只显示一行：`Pad · {account} ← {source_account}`。
- Balance 使用相同 card 外壳，内容只显示一行：`Balance · {account} · {amount} {currency}`。
- 这两个 card 可以显示诊断错误态，但不得添加未经决定的操作按钮、自动配对或同日位置规则。

### 7.4 已落盘余额与统计

余额/统计只读取当前年度 write target 的已落盘真源，不纳入 staging 数据。

- 优先显示由 Beancount 计算的 Assets/Liabilities 各账户原币余额和最近 balance 断言状态（通过/不通过/无断言）。
- `reporting_currency` 默认 `CNY`，存于 `.bkeasy/settings.json`，可在 Finance 设置中改；它仅改变统计展示口径，不重写交易或 Commit 语义。
- 支出/收入统计按 `Expenses:`/`Income:` postings 聚合，不能按 UI `type` 聚合，以免漏掉复杂或未分类交易。
- 若已有报告币 Expenses posting，直接聚合并忽略同交易 `@@`；否则仅在可明确归属的 `@@` 总成本中推导。无法明确归属的外币属于“未折算外币支出”，不得混入报告币总额。

## 8. 账户、分类与受控结构操作

### 8.1 账户约束与展示

- `name` 是 Beancount canonical 身份和交易 key；`label` 是唯一落盘的中文展示文本；`label_path`、`brief` 都由 label 推导，不能单独写。
- Expenses/Income 分类树中，去除根后的 canonical 层级必须与 `label_path` 一一对应；`brief` 只是最后层的解释文本。
- Assets/Liabilities 按根类型分组，label 是自由短名。Equity 不进入普通账户管理。
- `balance.account` 和 `pad.account` 只允许 Assets/Liabilities；`pad.source_account` 只允许 Equity。Pad 来源选择器可读 Equity，但普通交易/CSV 不可选。

### 8.2 新建、标签、删除、迁移

- 新建可直接填写完整 canonical path；校验根、语法与全账本唯一性，不强制父级已有 open。仅向对应声明文件添加 open 行；若存在更早交易，必须阻止并说明原因。
- 同层 label/brief 编辑只改声明注释。分类 label 的层级数或锚定关系变化属于结构变化，不能作为普通 patch。
- 删除只在没有脏 session 时可开始：扫描所有年度 ledger 的 transaction posting、Pad、Balance 引用和 `name:` 子账户；零引用且无子账户才可显示二次确认与原子删除。
- canonical 改名/移动是账户迁移：无脏 session → 扫描所有年度文件 → 结构化修改 posting/Pad/Balance/open 行 → Beancount 候选校验 → 展示受影响文件、条目、账户数量与 diff 摘要 → 用户确认 → 全部临时文件准备成功后整体替换 → 全量 reload。
- 严禁裸字符串 replace、半迁移，或在普通 inline 操作中改 canonical name。

## 10. 明确不继承的旧口径

下表的左列可能仍出现在当前代码、旧计划 §1–24 或旧 Finance spec 中；它们不是实现候选，不能为“兼容”而恢复。

| 不继承的旧口径 | 本规格的替代约束 |
| --- | --- |
| transaction-only `Entry`，`type` 含 `inv` | `LedgerItem = Transaction | Pad | Balance`；type 仅支出/收入/转账/未分类。 |
| `source_file:source_line`、`new:<timestamp>`、CSV 行号作为长期 ID | `orbita-id` 是唯一稳定交易引用；旧 source 定位只作会话临时身份。 |
| `/api/commit` 的 `{ files: ... }`、多文件提交或 `207` 部分成功 | Service settings 绑定单一 write target；commit 只确认同一 validation token/hash。 |
| 旧 parser 的隐式零金额补平、默认 CNY、宽松 type 推断 | 结构化白名单模型、明确账户/币种校验和 Beancount 候选校验；不偷偷修复用户账本。 |
| 旧式独立导入页、部分 merge、自动补空 posting 或直接写盘 | 明细 modal staging，完整校验后一次 merge 到 Store，再走同一保存状态机。 |
| 分类单击 patch、账户只读或不允许结构操作 | 创建、标签、删除和迁移均为独立、受控、可扫描/校验/确认的结构工作流。 |
| 按 UI type 做统计，或把本月消费当作唯一核心指标 | 只读已落盘账本；余额核验优先，Expenses/Income 按 posting 根聚合。 |
| 旧式全局 DOM ID、跨模块 DOM 操作、视图重建丢上下文 | Store 命令/事件与 mount handle；keep-alive、dispose、generation 和虚拟列表锚定。 |

## 11. 实现纪律

- 本规格取代旧 Finance UI/API 的实现假设；当现有代码与本规格冲突时，应重建相应模块，而不是添加兼容分支掩盖冲突。
- 不更改用户账本、dataDir 或历史文件，除非用户通过本规格规定的明确确认操作触发受控写入。
- 所有数据写入、临时文件、sidecar 生命周期、并发限制和兼容层附近必须有简短注释，说明不可破坏的边界并链接本规格。
- 未在本文件明确决定的产品语义必须提出问题，不得从旧 1–24、历史 BKeasy 或“常见做法”自行推导。
