## 1. 定位、目标与非目标

Finance 不是一个把 Bean 文本绑定到 UI 的编辑器。它是一个有明确 staging 边界的本地账本客户端：用户在内存中整理候选版本；服务端验证候选版本；用户明确确认后，单一 Commit 边界才原子覆写受管理的年度交易文件。

本架构的首要目标是：

1. 任何正常的记一笔、编辑、软删、拖拽和 CSV 导入都只改变内存，不能绕过 Commit 写盘。
2. 受管理的 `ledger/YYYY.bean` 能由 Finance 完整 canonical render，同时不会静默丢弃不受支持的 Beancount 语义。
3. 前端布局、滚动、overlay、视图导航和账本状态相互独立，重构 UI 不改变数据写入语义。
4. 同日自然顺序、稳定交易引用、账户约束、候选校验和错误定位都有单一所有者。

本轮明确不做：完整 Beancount IDE、BQL、跨年度交易编辑/一次 Commit、多文件交易 Commit、外部编辑器并发合并、投资 lot/`@`/`{}` 语义、任意 metadata 编辑器、跨年度统计，以及未确认的 Pad/Balance 复杂 UI。

## 2. 运行边界与文件所有权

```text
Insight Finance UI
  ├─ Finance shell / ledger store                （内存工作副本）
  └─ loopback HTTP
       └─ Python Finance Service
            ├─ Parser + canonical renderer
            ├─ candidate validator + Beancount loader
            └─ atomic writer
                 └─ {dataDir}/bill/
                      ├─ account.bean
                      ├─ category.bean
                      ├─ ledger/YYYY.bean        （当前单一 write_target）
                      └─ .bkeasy/settings.json
```

- Service 继续由 Insight 的既有 sidecar 生命周期管理；本轮不改变其启动、根路径或端口契约。
- `write_target` 必须是相对 `bill/` 的 `ledger/YYYY.bean`。明细加载、候选校验和 Commit 每次仅针对该一个文件。
- `ledger/YYYY.bean` 是 **Orbita 托管交易文件**。一经确认保存，允许被整文件规范化、重排和覆写。
- `account.bean` 与 `category.bean` 是账户声明上下文，交易 Commit 绝不可写入它们。它们的创建、标签变更、删除、迁移各走受控结构操作。
- 本轮假设个人单机使用；不实现 Finance 打开期间的外部文件变更检测、revision token 或合并。这个限制必须在实现注释与测试假设中保持清晰。

## 3. 分层与模块边界

### 3.1 前端层次

| 层 / 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `finance-shell` | Finance 内部路由、keep-alive、视图挂载/卸载、滚动位置 | 解析 bean、计算账本字段、直接操作 DOM 外的组件 |
| `finance-layout` | Grid、窄宽模式、右栏显示与收起、滚动根注册 | 筛选、保存状态、业务数据 |
| `finance-chrome` | 标题、返回、筛选开关、导入、全局保存、二级管理入口 | 列表渲染、提交 API 细节 |
| `ledger-store` | 已加载 baseline、工作副本、状态机、诊断、加载 generation、所有 mutation | CSS/DOM 查询、业务表单展示 |
| `detail-surface` | 虚拟明细、inline 编辑、拖拽、错误标记、滚动锚定 | 文件写入、全局 ID 查询 |
| `composer` | 简单/高级 transaction 草稿，创建内存条目 | Pad/Balance 编辑、直接 Commit |
| `import-modal` | CSV 选择、校验结果、用户确认 merge | 独立导入页面、直接写 bean |
| `structure-manager` | 账户/分类创建、标签、删除扫描、迁移预览/确认 | 日常 transaction 编辑 |
| `balance-stats` | 已落盘余额与轻量统计的只读展示 | 工作副本的临时金额 |

模块之间只经 `ledger-store` 的显式命令、事件或 mount handle 通信。禁止跨模块 `getElementById`、模块级可变 DOM 引用，或让列表/Composer 自己 fetch/commit。

### 3.2 前端生命周期与滚动

- `mount()` 必须返回最小 handle（如 `getScrollTargets()`、`focusItem(id)`、`dispose()`）；Shell 保存和恢复滚动，只认识这些 handle。
- 每一个 mount 注册的 listener、`ResizeObserver`、pointer capture、计时器和异步回调，都必须在 `dispose()` 解除。
- 详情虚拟列表负责首个可见条目的锚定：补载或高度变化后修正 `scrollTop`，不能让用户阅读位置跳动。
- 加载请求使用递增 `generation` / `AbortController`。dataDir、write target、视图实例或筛选上下文改变后，旧响应不得写入 store。
- Finance 根使用 `isolation: isolate`；普通内容区不竞争 `z-index`。modal/popover 通过统一 overlay root/portal 挂载，避免被右栏、虚拟列表或 chrome 截断。

## 4. 领域模型与身份

### 4.1 受支持的文档模型

Parser 首先构造结构化 document model，再映射给编辑 UI；不能继续以“一条 transaction 大正则 + 拼接字符串”作为扩展边界。

```ts
type Metadata = Array<{ key: string; value: string }>;

type Posting = {
  account: string;
  amount: DecimalString;
  currency: string;
  cost_amount: DecimalString | null; // 仅 @@ total cost
  cost_currency: string | null;
};

type Transaction = {
  kind: "transaction";
  id: string;                         // orbita-id，旧数据首次保存前可为临时 id
  source_file: string;
  source_line: number;
  date: ISODate;
  flag: string;
  payee: string;
  remark: string;
  tags: string[];
  postings: Posting[];
  metadata: Metadata;
  type: "expense" | "income" | "transfer" | "";
  seq: Seq;
};

type Pad = {
  kind: "pad";
  id: string;                         // 会话/诊断 identity，不作为跨域稳定引用承诺
  source_file: string;
  source_line: number;
  date: ISODate;
  account: string;
  source_account: string;
  seq: Seq;
};

type Balance = {
  kind: "balance";
  id: string;
  source_file: string;
  source_line: number;
  date: ISODate;
  account: string;
  amount: DecimalString;
  currency: string;
  seq: Seq;
};

type LedgerItem = Transaction | Pad | Balance;
```

`_is_new`、`_deleted`、编辑中的诊断和 UI 展开状态是 `ledger-store` 的工作副本状态，不能被 renderer 写入 Bean；`seq` 是 API/内存顺序键，也不能落盘。

### 4.2 受支持语法白名单

托管年度文件仅允许：

- `transaction`（单/双描述字符串、tags、posting、`@@`、transaction-level string metadata）；
- `pad`；
- 精确金额、单一币种的 `balance`。

暂不支持的 directive（`open`、`close`、`event`、`price`、`document`、`note`、`commodity`、`custom`、`include`、options/plugins 等），以及 transaction/posting 的不支持语义（links、posting flag、`@`、`{}`、自动配平、posting metadata、非字符串 metadata value 等）必须产生带文件/行号的阻断诊断。它们可以被读到“不可提交”状态，但绝不能在首次 canonical Commit 中静默消失。

### 4.3 metadata、稳定 ID 与 type

- metadata 仅支持 transaction-level `key: "string"`；未知 key 必须 parse → model → render，无通用编辑 UI。
- `bkeasy-type` 是受控 metadata：有效值优先覆盖推断；手动改 type 更新该键；清除 type 删除该键。
- `orbita-id` 的值必须为 `txn_` + 26 位 Crockford Base32 ULID（`^txn_[0-9A-HJKMNP-TV-Z]{26}$`）。新 transaction 在创建时生成；同一 transaction 只允许一个；重复或格式错误阻断 Commit。
- 旧 transaction 首次正常 Commit 时，在候选模型中批量补齐缺失 ID；打开/读取本身不产生脏数据。确认落盘后，这个 ID 才成为 Connection 可引用的稳定 `ArchiveRef` 身份。
- canonical metadata 排序固定为 `bkeasy-type`、`orbita-id`、其余 key 字典序，得到稳定 diff。
- `type` 只服务浏览/筛选/Composer，不参与会计正确性。仅严格两 posting 结构可推断；复杂、代买、报销等为 `""`（未分类）而非猜测。

### 4.4 同日顺序

Parser 在每个日期内按真实文件顺序分配 `a0`、`a1`……。Commit 对 **全部 LedgerItem** 按 `date ASC, seq ASC` 输出。交易拖拽只能重排同日 transaction 的 seq；Pad/Balance 不自动配对或被强行安排到固定位置。

Pad/Balance 的最终 CRUD 入口、时间线布局和同日可编辑策略仍为 **待定**。在产品决定前，数据模型、Parser、候选校验、canonical render 与诊断定位必须先完整支持；不得自行发明“自动配对”“一律在交易后”等规则。

## 5. Parser、renderer 与候选验证

### 5.1 Parser

`parse_write_target()` 只读返回：`items`、文件定位信息、支持性诊断，以及源顺序。其职责是保留可表达语义、识别不可表达语义；不是修复或写回文件。

账户 parser 独立读取 `account.bean` / `category.bean` 的 `open`：根类型、canonical name、允许币种、label、派生的 `label_path` 与 `brief`。账户 parser 也为 transaction/Pad/Balance 的账户选择与预校验提供唯一索引。

### 5.2 canonical renderer

renderer 只接受已通过模型约束的 `LedgerItem[]`，不接受 UI 拼接的片段。它：

1. 过滤软删 item；
2. 补齐首个 Commit 所需的缺失 `orbita-id`；
3. 按 `date ASC, seq ASC` 排序；
4. 以固定 transaction/posting/metadata 格式生成完整年度文件；
5. 返回文本及其不可变 `candidate_hash`。

`render → parse` 的语义 round-trip（不要求保留原始排版）是必须自动化测试。对于白名单外内容，禁止进入 renderer。

### 5.3 候选账本校验

Beancount 在既有 Python sidecar 进程内作为依赖调用，不另起常驻守护进程，也不在键入期间轮询真实文件。校验对象永远是当前工作副本 render 的候选账本：

```text
LedgerItem work copy
  → Orbita model / account / currency validation
  → canonical render
  → temporary isolated bill context
       (candidate ledger + account.bean + category.bean)
  → Beancount load/check
  → diagnostics + candidate_hash / validation_token
```

临时上下文只能写入隔离临时目录，不能触碰真实年度文件。Beancount 是最终会计语义检查；Orbita 本地校验仍负责产生字段级、可编辑的错误。

诊断统一为：

```ts
type CandidateDiagnostic = {
  message: string;       // 面向用户的短句
  item_ids: string[];    // 0、1 或多个
  raw?: string;          // 仅日志/开发排查
};
```

多 item 诊断要同时标记每个条目；界面只自动滚至第一个。无法可靠归因的余额失败可只关联 Balance 或完全作为全局错误，绝不假装找到了“罪魁交易”。

## 6. API 与两步保存协议

### 6.1 API 责任

旧计划中面向多文件的 `files` map / `207` 协议不适用于本轮单一 write target；实施时应收敛为单文件候选协议。路径由当前 Service settings 绑定，客户端不能借 request map 指定任意文件。

| API | 职责 |
| --- | --- |
| `GET /api/settings` / `PUT /api/settings` | 读取/设置相对 write target 与 `reporting_currency`；设置变更不重写交易。 |
| `GET /api/accounts` | 账户/分类声明、label 派生、允许币种，及 Pad 专用 Equity 选择数据。 |
| `GET /api/entries` | 当前 write target 的分页/分段读取、支持性诊断与加载边界。 |
| `POST /api/validate` | 接收当前完整工作副本，生成并校验候选版本；绝不写真实 ledger。 |
| `POST /api/commit` | 仅确认同一通过校验的 candidate，执行单一文件 atomic write。 |
| 结构 API | 创建/改 label/删除扫描/账户迁移的受控 context；与 transaction Commit 分离。 |
| 只读余额/统计 API | 仅加载已落盘真源，不读取工作副本。 |

请求中的 `write_target` 若保留，仅作为防止 UI 与 Service settings 脱节的断言；服务端必须验证它等于当前设置，且不可替换服务端选定的文件。所有路径都须规范化为 bill 下的相对路径，拒绝绝对路径、`..` 与分隔符绕过。

### 6.2 保存状态机

```text
unedited
  └─ mutation / CSV merge / inline edit → edited
edited
  └─ 保存 → checking
checking
  ├─ field/model/candidate error → edited
  └─ validate success(token + hash) → confirming
confirming
  ├─ 任意语义 mutation → edited（token 失效）
  └─ 确认保存 → submitting
submitting
  ├─ atomic-write failure → confirming（保留工作副本与可重试 token）
  └─ success → authoritative reload → unedited
```

- `partial` 是“全量年度条目尚未加载完成”的加载保护状态，不是保存结果。它期间禁止 validate/commit，防止局部 UI 覆盖整文件。
- `POST /api/validate` 接收完整 active items（含所有非删除 item）和该会话候选 hash 前置数据；服务端重新执行全部验证，成功返回 `validation_token`、`candidate_hash` 与规范化后的必要 identity 回填信息。
- `POST /api/commit` 只接收 token / hash（或等价的完全相同 candidate 声明），服务端验证 token 尚未失效且候选 hash 不变，然后 atomic write。若无法确认相同候选，返回可行动错误，客户端退回 `edited`。
- 成功后必须重新读取真实文件并替换 baseline，不能以本地工作副本伪造成功；软删、新增、修改样式只在这时消失。
- UI 面向用户的文案分清“已加入待保存”和“已保存到账本”。确认态按钮只显示“确认保存”，不暴露内部 Beancount 术语。

## 7. 账户、分类与结构工作流

### 7.1 账户约束与展示规则

- transaction、CSV、inline 编辑只能引用 `account.bean` / `category.bean` 已声明的账户。未知账户是字段错误。
- Assets/Liabilities 的 `open` 允许币种直接约束输入：未列币种不限制；列出一个或多个时只允许这些币种。
- Pad 的 target account 只能是 Assets/Liabilities，source account 只能是 Equity；普通交易/CSV 不开放 Equity。
- Expenses/Income 是分类树：中文 `label_path` 与 canonical name 去掉根后的层级一一锚定；`brief` 是最后一级 `_` 后的说明，不参与树层级。
- Assets/Liabilities 仅按首段分资产/负债组；它们的 label 是自由短名，不要求中间 canonical 路径映射为中文树。

### 7.2 受控结构操作

- 新建可直接填写完整 canonical path；校验根、语法、全账本唯一性，且不强制父级已有 open。新增仅追加对应 `open`，默认 open 日期为今天并允许回填更早日期；若已存在更早交易，必须阻止并提示。
- label 的同层改名与 brief 修改仅改变声明注释。分类 label 的层级数/锚定关系变动则是结构变化，不可作为普通 label patch。
- 删除只在无脏 session 时可请求；服务端扫描所有年度 ledger 的 transaction posting、Pad、Balance 引用和 `name:` 子账户。零引用且无子账户才能二次确认并原子删除。
- canonical 改名/移动是账户迁移：无脏 session → 扫描所有年度文件 → 结构化修改 transaction posting、Pad、Balance 与 open 行（含子账户）→ 候选 Beancount 校验 → 展示文件/条目/账户计数与 diff 摘要 → 用户确认 → 全部临时文件准备成功后再整体替换 → 全量 reload。禁止裸字符串 replace 和半迁移。

## 8. 交互数据流

### 8.1 交易编辑与高级模式

Composer 和 inline 编辑都只调用 store mutation；store 负责生成新 transaction 的 ULID、标记 `new/modified/deleted`、作废 confirming token，并广播列表/Chrome 更新。高级模式允许 2–10 条分录、账户/金额/币种、`@@`、日期、payee、remark、flag、tags、手动 type；metadata 透明保留但不提供编辑器。

简单模式默认 `reporting_currency`；选择单币种账户时切换到该币种。两端没有交集或需要 `@@` 时引导进入高级模式，不能在简单表单中暗含换汇算法。

### 8.2 CSV staging

导入是 detail surface 上的 modal，不是一个独立的持久化页面：

```text
选 CSV / 拖放 → 表头与逐行校验 → 用户确认添加
→ store merge 新 transaction（绿底 new）→ edited
→ 统一 validate → 确认保存 → Commit
```

新选择文件替换旧 pending session；校验失败不能部分 merge；确认添加后只清 modal pending 状态。CSV 不自动去重、也不自动保存；导入后清空日期/type 筛选并定位第一条新增记录。

### 8.3 已落盘余额与轻量统计

余额/统计 API 永远读取已落盘当前年度 write target，不纳入绿底 staging 数据。优先级是账户余额核验：Beancount 计算 Assets/Liabilities 原币余额和最近 balance 断言的通过/不通过/无断言。月度 expenses、分类 Top N、未折算外币支出仅为辅助。

`reporting_currency` 可在设置中改，默认 CNY。统计按 posting 而非 UI type 聚合：已有报告币 Expenses posting 时直接使用；没有时才在可明确归属的单一 `@@` 总成本中推导；其余展示为未折算外币支出，绝不强行汇总。

## 9. 实施顺序与依赖

1. **模型与安全读写基础**：LedgerItem document model、白名单 diagnostics、canonical renderer、seq、metadata/ULID、round-trip tests。
2. **候选验证与单文件 API**：临时候选 context、Beancount 校验、token/hash、atomic single-file Commit、状态机与失败恢复。
3. **store 与页面骨架**：Shell/Layout/Chrome/handle 生命周期、generation 防竞态、完整加载保护与 virtual list anchor。
4. **交易能力**：inline、Composer 简单/高级、type、账户币种约束、同日 transaction 拖拽。
5. **CSV 与诊断体验**：modal staging、多条诊断标记、导入后的定位与筛选重置。
6. **账户结构与余额**：创建/label、删除扫描、迁移候选管线及最小余额核验。
7. **Pad/Balance UI**：先依据已验证的数据与校验能力完成最小展示；具体 CRUD/布局仅在产品决定后实现。

每一阶段都先完成下层契约测试，再把 UI 接上。不得为赶页面进度让前端绕过候选校验或 Commit。

## 10. 验收门槛

### 自动化

- 白名单的 parse → render → parse 保持 LedgerItem 语义；未支持 directive/语义阻断 Commit 且原文件不变。
- transaction metadata、`bkeasy-type`、`orbita-id` 解析、固定排序、ID 格式/重复检测，以及首次 Commit 补 ID。
- 同日 transaction/Pad/Balance 的 `seq` 保留和 commit 排序；删除最后一项能写出规范空年度文件。
- 候选账本使用临时目录，失败/中断/Beancount 报错不改真实文件；atomic write 失败原文件完整。
- validating token 在任意 mutation 后失效；validate/commit 成功、失败、网络失败的状态机均保留或重置正确工作副本。
- 账户存在性、open 币种、Pad/Balance 根类型限制；复杂 transaction 不误推断 type。
- CSV BOM、空文件、错误表头、逐行账号/币种错误、`@@`、正逆行序、重复导入；确认添加后仍未写盘。
- 结构删除零引用/有引用/有子账户；迁移扫描、候选校验、全临时准备失败不产生半迁移。

### 手工回归

- 500+ 条详情的初始补载、筛选、滚动锚定、同日拖拽与保存禁用，无错误覆写或跳动。
- 新增、编辑、软删、撤销、改回 baseline、confirming 中再编辑，以及 dataDir/write target 改变时旧异步响应不污染新会话。
- CSV modal 完整流程：新增绿底可见、状态为待保存、保存后才变为已落盘。
- 候选诊断可关联多项，第一项获得焦点，其他项均保留错误态；全局错误不会被误映射。
- 资产/负债余额与最近 balance 断言状态可用于核验；统计不因未分类 transaction 漏算 Expenses/Income posting。
