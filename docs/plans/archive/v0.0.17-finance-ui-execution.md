## 1. 目标与完成定义

目标是保留用户熟悉的账本卡片阅读方式，同时从零重建其 DOM、CSS、实例边界和交互所有权。不是把旧页面套进新 Layout，不是把旧 renderer 改名，也不是仅修复重叠、z-index 或响应式。

完成必须同时满足：

1. Detail 是新的 **CardDetailSurface**：日期分组的账本时间线、交易卡片、只读 Pad/Balance 卡片、受控展开编辑，以及右侧 Composer + 余额核验 rail 组成新的渲染树。
2. 用户可见的卡片密度、账本块式信息阅读和 bean 对照心智可以延续；旧 `.detail-card` / `.entry-block` 的 DOM、字符串 renderer 和详情 CSS 不得被复用。
3. Store 是数据加载、工作副本、mutation、validate、commit、token、baseline 与 generation 的唯一 owner。视图只能读 snapshot、派发 command，绝不能原地修改条目。
4. 1440、1280、1024px 真实 Tauri 窗口中，卡片、筛选、右侧 Composer + 余额核验 rail/drawer、Insight sidebar 与弹层都无重叠、裁切、错误命中或滚动竞争。
5. 数据安全、Host、sidecar、Parser、Candidate Commit 和现有 portal 不因 UI 重构而被重写或削弱。

只有同时具备“旧链路已删除、自动化实际通过、真实窗口证据已记录”才可标记 UI 完成。

## 2. 已完成基础：保留，不得重做

以下是当前工作树已存在的实现基础。它们仍需在最终回归中验证，但不是本轮重新设计对象。

| 基础 | 不可破坏边界 |
| --- | --- |
| Insight Host / Finance destination | cached root、activate/deactivate、dataDir guard、dispose 是上层唯一生命周期；Finance 不能把数据或 DOM 状态挪回 Host。 |
| Finance Shell | 内部页面 keep-alive 和 handle 化恢复只管理 view handle，不窥探 Surface DOM。 |
| FinanceLayout | 宽屏 CSS Grid、窄屏 drawer、scrim/Esc/focus、主/次滚动区域与 sidebar 不二次扣宽是 Layout 的职责。右侧 rail 由 Composer 与余额核验组成，不是只有表单。 |
| Modal / picker portal | 使用既有受管理 portal 和全局 modal root；不重新造 body/rail 局部浮层。 |
| Finance Service / 数据 | `{dataDir}/bill`、sidecar 真实端口/根、Parser、LedgerItem、候选 Beancount 校验、token/hash 两步确认、atomic Commit、settings 和结构安全流程遵循 `v0.0.17.md` §25。 |

禁止以“彻底重构”为借口替换以上模块、重写后端、改变 API/Commit 语义、改变数据根，或再引入另一套 Store。任何确有必要的修复必须先有可复现失败证据，并只改最小边界。

## 3. 前两次实现的严重错误与永久禁令

### 3.1 旧 UI 套壳：永久拒收

下列文件/概念只能作为删除对象或历史对照，绝不能作为新 Surface 的输入：

- `views/detail/render.ts` 的字符串卡片 renderer；
- 旧 `.detail-card`、`.entry-block` 及其详情专用 CSS 结构；
- `#detail-list`、`#save-btn`、`#ledger-page-*` 等页面装配 ID；
- 以 `innerHTML` / HTML 字符串拼出交易编辑宿主的实现；
- 以旧 CSS class 维持卡片信息层级的兼容分支。

保留卡片外观不等于保留上述实现。新卡片必须由新目录中的 CardDetailSurface 自身创建，采用私有 class 或 `data-role`，其样式从新的、以 surface root 限定的样式模块提供。颜色 token、文案和账本信息语义可以迁移；旧 DOM/CSS 不能迁移。

### 3.2 所有权违规：永久拒收

```text
Insight Host → Finance destination → FinanceShell
  ├─ FinanceLayout       只拥有 viewport / Grid / drawer / scroll-region
  ├─ FinanceChrome       只渲染 Store snapshot、发 route/store command
  ├─ LedgerStore         唯一拥有 state、fetch、mutation、validate、commit、generation
  └─ CardDetailSurface   唯一拥有 Detail DOM、事件、虚拟列表、焦点、锚定与清理
       ├─ Composer       只维护 draft，提交时发 Store command
       └─ BalanceAudit   只读已落盘余额/断言，在 Commit 成功重读后刷新
```

- Shell 只能通过 view handle 获取滚动、焦点或 dispose；禁止查询 CardDetailSurface DOM。
- Layout 不得读取账本、脏状态或保存状态机；Chrome 不得调用 Parser/Commit 或查询卡片。
- Surface/Composer 禁止 `fetch`、Commit、全局 DOM 查询和原地修改 `LedgerItem`。所有编辑、删除、标签、成本展开均调用显式 Store command。
- Store 只暴露只读 snapshot / selector；不能把可修改数组或对象引用交给视图。
- 每次 mount 的 listener、observer、timer、pointer capture 和异步回调必须由该实例的 `dispose()` 取消。请求还须由 generation 和/或 `AbortController` 防止旧响应污染新会话。

### 3.3 证据造假式完成：永久拒收

“代码存在”“静态扫描通过”“单元测试通过”“开发服务已启动”“截图看起来正常”是不同证据，任何一个都不能替代其他项。不得把自动化测试写为手工验收；不得把没有窗口证据的 Grid/drawer/portal 写为已交付；不得把一部分 controller 实例化写为 UI 已重构。

## 4. 目标 CardDetailSurface

### 4.1 信息层级

卡片模式是本轮唯一实现的 Detail 呈现。未来可新增行式 Surface，但不做入口、不做切换、不共享 DOM；它必须另立计划。

```text
Finance detail root
├─ continuous Finance chrome（标题、筛选、导入、保存、rail toggle）
├─ CardDetailSurface primary scroll root
│  ├─ date group / sticky date pin
│  ├─ transaction card
│  │  ├─ identity: 状态、日期、描述、type、tags
│  │  ├─ postings: 账户、金额、币种、成本摘要
│  │  ├─ pending / diagnostic state
│  │  └─ controlled edit region（仅用户进入编辑态后）
│  ├─ read-only Pad card
│  └─ read-only Balance card
└─ Finance rail secondary scroll root（宽屏 rail；窄屏 drawer）
   ├─ Composer
   └─ BalanceAudit（余额核验优先；本月支出等仅辅助）
```

卡片应保持可逐块对照 bean 的阅读方式，而非强制表格化。transaction、Pad、Balance 共享新的卡片外壳，但其业务能力严格遵循 §25：Pad/Balance 本轮只读、不可由 Composer/CSV 创建、不可被 type 或统计误当交易。同日顺序由 `time` metadata 与数值 `seq` 决定，不提供拖拽重排（[`ADR 0002`](../../adr/0002-finance-chronological-order-without-drag.md)）。

**卡片左侧色条（`cds-stripe-*`）**：主观展示语义，不写入会计真源；由 `bkeasy-type` metadata 或保守推断映射。默认色与可调项见下表；默认值在 `.ledger-app` 的 `--cds-stripe-*` CSS 变量，用户可在「账户与分类 → 卡片色条」写入 `.bkeasy/settings.json` 的 `card_stripes`（`surface` CSS 不得硬编码色值）。

| Stripe kind | 中文 | 默认语义 |
| --- | --- | --- |
| `expense` | 支出 | 橘黄 |
| `proxy-expense` | 代支出 | 浅橘（`bkeasy-type: proxy-expense`） |
| `income` | 收入 | 沿用现有绿色 |
| `transfer` | 转账 | 沿用现有蓝紫 |
| `repayment` | 还款 | 浅蓝（`bkeasy-type: repayment`） |
| `unknown` | 未分类 | 淡灰（`--cds-stripe-unknown`） |
| `pad` | Pad | 深灰（与 Balance 同色） |
| `balance` | Balance | 深灰 |

### 4.3 明细右侧：记一笔与余额核验

Finance 明细是编辑**与核验**页面，不是只有录入表单的页面。宽屏右侧 rail 从上到下固定承载：

1. **Composer**：创建待保存 transaction；“记录”仅加入工作副本。
2. **BalanceAudit（校验）**：用户可通过 `+` 添加 0–3 个校验槽位；每槽两行——上行短框选类型（收入/支出/资产/信贷/平衡）+ 长框选账户，下行显示已落盘原币余额。阶段 A 仅静态外壳与 fixture 演示；阶段 C 订阅 `write_target` 真源并在 Commit 重读后刷新。辅助统计（本月支出等）延后，不阻塞核验优先级。

BalanceAudit 的优先级高于消费统计，严格遵循 `v0.0.17.md` §25.11：它只读取已落盘的真源，绝不把 staging 或未保存草稿算作真实余额。用户确认保存成功、Service atomic Commit 完成且 Store 重读真源后，它必须立即刷新；保存前可显示“有待保存变更，核验值尚未包含”这一状态，但不得伪造实时余额。窄屏时 Composer 与 BalanceAudit 作为同一 rail 的两个区段进入 drawer，二者共享 rail 的唯一 secondary scroll root，不得各自抢滚动或跨模块操作 DOM。

### 4.4 连续 Finance chrome、日期分组与卡片宽度

Finance chrome 是主列顶部的一个连续结构，不是两张悬浮卡片：工具栏（标题、筛选、导入、保存、rail toggle）贴主列顶部并占满主列宽度；筛选展开区直接从工具栏下方以短促动画展开/收起，与工具栏共享外壳、边界和宽度。它们之间不得有空隙、独立圆角外框或无职责的额外容器。筛选收起时主滚动区紧接工具栏；展开时紧接筛选区。

**筛选区（Phase A）**：
- 日期区间使用 `orbita-date-picker`（compact）；触发器与弹层经 `mountPopoverPortal`，与类型下拉互斥；使用 `--finance-control-radius`（默认 8px）圆角、浅底、无描边，不得透出下方列表。
- 类型筛选为可多选按钮列表（`expense` / `proxy-expense` / `income` / `transfer` / `repayment` / `unknown`）；左侧色条标识类型，选中时色条动画铺满为行底色（无 checkbox）；Phase A 仅 UI，不接 Store；Phase B 接入 `CardDetailStore` 筛选。下拉须经 `mountPopoverPortal`；`--cds-stripe-*` 须同步到 `#orbita-modal-root`（见 `card-stripe-tokens.ts`）。

**日期 pin（`cds-date-pin`）**：
- 格式 `YYYY-MM-DD Mon`（如 `2026-08-09 Sun`）；与首卡间距 6px。
- 单一 sticky 样式（13px / 500 / muted），无 `is-stuck`、无 IntersectionObserver、无过渡动画；文字行 `background: var(--ledger-bg)`，`::after` 约 20px 渐变（`ledger-bg → transparent`）使下方卡片淡出。
- 与卡片同宽 gutter；色条默认见 §4.1 表。

**卡片与空字段**：
- Pad/Balance 单行只读；空 payee/remark/tags 默认隐藏，hover 显示浅灰 ghost 框（非斜体）。
- **跨卡片字段列对齐（Phase B 硬契约）**：每张 transaction 卡片按「日期、时间、flag、标题、收款人、tags、删除」的顺序使用同一套稳定的 CSS Grid 列轨；其中标题是现有 `remark` 字段的用户可见名称和主弹性列，收款人仍对应 `payee`，不得改 API、bean 或写入语义。日期列必须完整显示 `YYYY-MM-DD`，时间列显示有效 `HH:mm` 或 ghost，不能按内容收缩；任一字段为空时仍占用其列轨（可显示既有 ghost），不得让后续字段横向补位。相同屏宽、同一列表中的这些字段必须自上而下对齐。
- **收窄行为**：断点必须依据 Detail 实际可用宽度（含 Insight sidebar 与 rail 的影响），不能只看全局 viewport。收窄后改为稳定两行 Grid：首行放日期、时间、flag、标题和删除，次行放收款人与 tags；标题保留主弹性空间并以完整字形截断，tags 不得被挤为无约束的第三行或遮盖标题。
- Composer：金额（窄）+ 日期（宽）同行；右侧「校验」为 0–3 槽可增删外壳。

### 4.2 mount handle

CardDetailSurface 的 `mount(root, dependencies)` 至少返回：

```ts
type CardDetailHandle = {
  getScrollTargets(): { primary: HTMLElement; secondary?: HTMLElement };
  focusItem(id: string): void;
  dispose(): void;
};
```

依赖只包括实例 Store 的只读订阅/command、Layout 提供的已拥有容器、portal 服务和必要的纯函数。禁止传入其他 view DOM、旧 renderer、全局 ID 或可写条目引用。

## 5. Layout、滚动与弹层硬契约

- 内容宽度大于 `1180px` 时：同一 Grid 的主列 `minmax(0, 1fr)` 与 300px Finance rail 正常并列；主列与 rail 各自滚动。宽屏 rail 收放通过 `@property --ledger-rail-col`（`300px` ↔ `0px`）动画；`rail-inner` 固定宽度、外层 grid 列裁剪，禁止 `display: none` 硬切。
- 小于或等于 `1180px` 时：Finance rail 默认关闭；只由 Chrome command 打开为 Layout 所有的 drawer。Composer 与 BalanceAudit 一并进入 drawer；关闭后主列立即占满可用宽度。
- Insight sidebar 展开/折叠不得再次从 Finance 内容扣除固定宽度。所有相关 Grid item 都必须有 `min-width: 0` 与 `min-height: 0`。
- 只有 CardDetailSurface 拥有 Detail 主滚动；Chrome、page root、隐藏 view 不得参与滚动竞争。
- Finance root（`.ledger-app`）`isolation: isolate`；层叠只通过具名变量：`--finance-layer-chrome`、`--finance-layer-sticky-pin`、`--finance-layer-drawer-scrim`、`--finance-layer-drawer`；浮层 popover 用 `#orbita-modal-root` 的 `--orbita-popover-z`。
- 主滚动区/卡片为基础层，不写 `z-index`。连续 Finance chrome（`finance-chrome-shell`）整体占 `--finance-layer-chrome`；工具栏与筛选同属 chrome，不得再建 stacking context。
- sticky date pin 在滚动区内，仅用 `--finance-layer-sticky-pin`，必须低于 chrome。drawer/scrim 由 Layout 用 drawer 变量管理。
- modal、日期/账户/类型 picker 必须走受管理 portal（`mountPopoverPortal`）；禁止在筛选区内用更高 `z-index` 压过滚动区。筛选控件圆角用 `--finance-control-radius`（`.ledger-app` 与 `#orbita-modal-root` 均须定义，含 fallback）。
