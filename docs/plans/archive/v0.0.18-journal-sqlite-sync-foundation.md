## 后续工程拓扑与交接边界

本计划只实现桌面端 Journal/Health SQLite 基础，不移动当前目录、不重写 Git 历史，也不创建 Android 或 Linux 服务。待桌面收束后，另立仓库重组计划；目标为一个 Git 仓库中的多应用工程：

```text
Orbita/
├── apps/
│   ├── desktop/       # 现有 Tauri 桌面应用
│   └── android/       # 独立的 Kotlin / Compose 客户端
├── services/
│   └── sync/          # 独立部署的 Linux orbita-sync 服务
├── contracts/         # 版本化 API、schema 与脱敏测试样例
└── docs/
```

- 三个运行单元各自维护构建依赖、运行时、发布版本和 CI；不共享 Tauri、Kotlin 或服务端实现代码。
- `contracts/` 是跨端共享的工程边界，只保存版本化协议、字段语义和脱敏 fixtures；不得存放用户数据、SQLite 文件、token、凭据或环境配置。
- `orbita-sync` 是 API 服务，不是 SMB/网盘同步器。桌面、Android 与服务端各维护独立 SQLite 副本，只经 API 同步记录、版本、删除标记和确认结果；严禁传输、挂载或复制 SQLite 文件。
- 本计划建立的 outbox 只服务 Journal/Health。Finance 仍以 `.bean` 为唯一账本真源，服务端不得并发改写；Finance 同步、手机端功能、认证和冲突处理另立计划。
- 产品版本可统一对外表达；各运行单元与 contracts 的发布版本、兼容矩阵独立管理。协议不兼容变更必须先定义新的 contracts 版本与迁移路径。

## 目标

以全新 SQLite 库承载桌面端可多端编辑的 Journal 数据。新库必须能可靠表示稳定记录 ID、版本、删除标记和待同步操作，为独立的 `orbita-sync` API 接入作准备。

## 最高验收原则

1. **用户侧无感**：存储从 JSON 切到 SQLite 不得要求用户理解数据库、执行迁移或面对两套 Journal/Health 入口。已有 Panel/Insight 读取必须经同一领域边界使用新库；加载、保存、删除、Garmin 状态和失败反馈保持直接、可信且不暴露存储实现细节。
2. **下一版本可直接同步**：本地库必须已经具备稳定 UUID、来源、逐记录版本、tombstone 与原子 outbox；未来 `orbita-sync` 只需消费/确认这些操作，不得要求再次改造 Journal/Health 的本地真源或重新解释历史变更。

“无感”不等于伪造旧数据仍存在：本计划已确认不读取/迁移旧 JSON，所以首次创建空库后，Garmin 数据须重新同步、meal 须人工补记。这是明确可见的数据状态变化，不能被 UI fallback 掩盖。

当前个人数据量很小；Garmin 事实可从外部来源重新同步，既有 meal 由用户通过 Insight Health 人工补记。因此本版本不把旧 Journal JSON 导入 SQLite，也不实现兼容读取。旧 JSON 保留为不改写的历史备份。

本计划只建立本地基础；它不宣称已实现服务器同步、手机端、认证、冲突解决或 Finance 多端写入。

## 已确认决定日志

### 2026-08-22 — 不迁移旧 Journal JSON

- **决定**：不实现 JSON → SQLite 导入或双读；从空 SQLite 库开始。
- **理由**：现有数据量很小，Garmin 记录可重新同步，剩余 meal 可经 Insight Health 人工补记；迁移的复杂度和风险不值得承担。
- **边界**：旧 `{journalRoot}/journal/YYYY.json` 只作为不改写的历史备份。不得静默删除、覆盖、重建或将其伪装为已迁入的新库。
- **未决**：Insight Health 首期可补记的具体字段、日期入口与 Garmin 重新同步后的核对体验。

### 2026-08-22 — Health 与 Journal 作为完整 Insight 领域推进

- **决定**：0.0.18 不将 Insight Health 限于 meal 补记；Health 与 Journal 都要从当前壳层推进为可独立使用的领域，并以 Finance 的信息组织、可编辑性与可信保存反馈为质量目标。
- **理由**：用户不希望只为少量历史 meal 制作一次性补录工具；SQLite 基础应直接服务后续日常记录、回看与同步。
- **边界**：这不是“复制 Finance UI”或把所有 Finance 功能照搬到 Health/Journal。Finance 当前仍有未收口项目；“达到记账水平”的具体能力矩阵、各领域已有 kind 的编辑边界、Dashboard/统计/AI 是否属于 0.0.18，均待明确后才能写入验收。

### 2026-08-22 — 0.0.18 Insight 工作区完成线

- **决定**：Insight Health 与 Insight Journal 都必须覆盖每种现有记录的新增、查看、编辑、删除，并提供按日期回看、筛选/搜索与可信保存反馈。
- **决定**：Garmin 同步状态必须可见、可手动重试，且不得覆盖人工数据。
- **不纳入完成门槛**：Dashboard 指标、复杂统计、CSV 导入、AI Chat-first、手机端与将来尚未定义的 `capture`。
- **未决**：Garmin 来源字段被人工编辑或删除后，下一次同步的精确所有权与恢复语义。

### 2026-08-24 — 手工记录软删与统计进入范围

- **决定**：Orbita 自己拥有的 meal、手工 nap、手工运动和 Journal 记录采用 Finance 式删除：立即从列表移除、短暂可撤销，底层保留删除标记（tombstone）供未来同步。Garmin 来源记录仍不可删除。
- **决定**：Health 统计是 0.0.18 的核心交付，不能只交付管理列表；睡眠的近日期统计是已明确的最低需求。本决定取代先前将 Dashboard/复杂统计排除在完成门槛外的概括性表述；只有本段明确的 Health 统计进入范围。
- **决定**：Health 统计默认查看近 7 天睡眠，并允许用户切换时间范围。
- **未决**：睡眠统计的具体指标、时间范围选项、Health 与 Journal 各自统计边界，以及统计是否在 Insight 独立视图或工作台内呈现。

### 2026-08-24 — 0.0.18-a 单一 Journal/Health SQLite 库

- **决定**：在现有 `journal_root()` 解析出的根目录中使用一个 `journal.sqlite` 承载 Journal 与 Health 的领域记录、版本、删除标记和同步 outbox。默认根目录是 `dataDir`，但设置中的自定义 Journal 数据根必须继续生效，因此实际路径为 `{journalRoot}/journal.sqlite`。
- **理由**：`daily` 与 `routine` 已混合承载 Health 和 Journal 事实；单库使“写记录 + 写待同步操作”、首次初始化、dataDir 切换与未来同步保持事务边界简单明确。
- **边界**：库内以领域表/记录 kind 保持 Journal 与 Health 的模型边界；它不是泛化的 `orbita.sqlite`。App State、设置、窗口状态、凭据、Garmin 原始文件/缓存和 Finance `.bean` 均不迁入此库。
- **初始化**：Journal/Health 只检查当前 `{journalRoot}/journal.sqlite`；文件不存在即自动创建空库。旧 JSON 不参与判断、不读取、不导入，也不提示迁移；初始化不触碰旧文件。

### 2026-08-24 — Garmin 写入也进入本地 outbox

- **决定**：Garmin 同步写入 SQLite 的新增或更新，也生成本地 outbox 操作，供未来 `orbita-sync` 同步到服务器和其它设备。
- **边界**：这些操作与手工写入一样可同步，但记录必须保留 Garmin 来源标识；其它客户端仍只读，不能因此取得修改 Garmin 事实的权限。
- **理由**：服务器应成为跨设备一致副本，而非要求每个设备分别从 Garmin 拉取并各自生成可能不同的统计数据。

### 2026-08-24 — 本地删除保留 tombstone

- **决定**：0.0.18-a 对 Orbita 拥有的记录仅做软删：保留 `deleted_at`/删除状态与版本，正常查询隐藏；撤销只取消删除标记，并为同步写入对应 outbox 操作。
- **边界**：本地不自动清理 tombstone。何时在服务器确认、跨设备同步后回收，属于 0.0.20 的 `orbita-sync` 协议，不在本版提前实现。

### 2026-08-24 — SQLite 记录 ID 与物理存储解耦

- **决定**：新 SQLite 记录使用不含文件路径或年份的全局稳定 UUID；`kind`、业务日期和来源均为独立字段。
- **理由**：SQLite 不再按年文件组织；未来 API、outbox 与跨设备同步不能依赖本地物理路径。旧 JSON 不迁移，故不建立路径前缀兼容层。

### 2026-08-24 — 统一记录信封与领域 data

- **决定**：每条 SQLite Journal/Health 记录共有 `id`、`kind`、业务日期、`source`、`revision`、创建/更新时间与 `deleted_at` 等信封字段；各领域特有字段保存在 `data`。
- **边界**：统一的是持久化、CRUD、tombstone 与 outbox 的基础机制，不是把 Health/Journal 的业务语义合并成万能 Event；各 kind 继续由领域规则校验。

### 2026-08-24 — 当前来源枚举

- **决定**：0.0.18-a 的记录来源仅有 `manual` 与 `garmin`。
- **边界**：AI、手机和服务器尚不是本版本的来源；未来扩展来源时另行定义其确认、所有权和同步语义，不预先占用 schema 或 UI 概念。

### 2026-08-24 — 0.0.18-a 基础实现默认值

- **保留既有业务约束**：`daily` 每个上海日只能一条；`routine` 每个醒来日只能一条。日期语义继续固定为 `Asia/Shanghai`。
- **删除反馈**：手工记录删除后立即隐藏，提供 5 秒撤销；底层维持 tombstone，不物理删除。
- **本地变更一致性**：每次成功的手工写入、删除或 Garmin 实质变化都递增记录版本，并在同一 SQLite 事务写入 outbox。无实质变化的 Garmin 同步不产生重复 outbox 项。
- **失败边界**：数据库写入或 outbox 写入任一失败即整体失败并给出可行动错误；绝不回退读取旧 JSON。
- **备份边界**：0.0.18-a 不增加日常自动备份任务；每次 SQLite schema 升级前保留本地快照。服务器副本与长期恢复策略留给后续 `orbita-sync` 计划。

### 2026-08-22 — Panel 纳入 0.0.18

- **决定**：除重做 Orbita Insight 的 Health 与 Journal 外，0.0.18 令 Orbita Panel 改从新的 SQLite 数据源读取 Health/Journal。
- **决定**：取消 Panel 的手工喝水编辑；喝水只展示 Garmin 同步结果。若数据有误，用户在 Garmin 修正后再手动同步。
- **边界**：除移除喝水编辑这一必要的来源一致性修正外，Panel 不新增 Health/Journal UI、跨日期检索、批量管理、Garmin 历史或独立写入状态机；完整读写工作区只在 Insight。

### 2026-08-22 — Garmin 来源数据只读

- **决定**：喝水、睡眠以及其他 Garmin 来源的数据在 Orbita 中不可编辑或删除；Garmin 是这些事实的唯一写入者。
- **理由**：Garmin 数据不能由 Orbita 上传；提供编辑会制造无法回写、下次同步又可能被覆盖的错误承诺。
- **混合记录边界**：`daily` 可同时包含 Garmin 字段和人工 meal；只锁定 Garmin 来源字段，meal 仍可由用户新增、编辑、删除。不得因记录混合而把整个 `daily` 锁死。
- **后果**：Insight/Panel 对 Garmin 来源记录必须呈现只读来源与同步状态，而非编辑/删除操作；发现错误由用户在 Garmin 修正后再手动同步。0.0.18 不实现 Garmin 原始值与人工覆盖值并存、字段级 override 或“恢复 Garmin”机制。
- **来源拆分**：同一领域允许 Garmin 与 Orbita 手工记录共存。手工 meal、手工午睡（`naps`）和不带 Garmin `externalId` 的手工运动均可新增、编辑、删除；Garmin 同步出的 nap 与运动仍只读。同步只能更新其自身来源记录，绝不删除手工记录。

### 2026-08-24 — Insight 领域不做跨域总览

- **决定**：Insight Health 与 Insight Journal 保持两个独立栏目，各自独立回看、筛选、搜索与编辑。
- **边界**：0.0.18 不做同日期跳转、Health/Journal 混排总览、统一 Event，或记录间自动关联/复制；未来手机端时间线与 Connection 另立计划。

### 2026-08-24 — Insight 采用 Finance 式管理工作台

- **决定**：Insight Health 与 Insight Journal 都以管理为核心：顶部提供紧凑的日期定位/「今天」快捷入口、筛选与搜索；主体为可查看和编辑的历史列表。
- **职责边界**：Insight 不复制 Panel 的“今日内容面”；日常今天查看属于 Panel。Health/Journal 各自独立使用这一工作台结构，不彼此混排。

### 2026-08-29 — Insight 可编辑 daily / routine 容器，但不取得 Garmin 写入权

- **决定**：Insight 初版为 `daily` 与 `routine` 提供按日期打开和编辑的完整容器页；这不是只允许 meal 或 nap 进入独立小弹窗。
- **边界**：容器可编辑不等于其中一切字段可编辑。Garmin 拥有的 hydration、睡眠、Garmin nap、Garmin exercise 及其它 Garmin 事实继续在该页只读；用户手工拥有的 meal、手工 nap、手工 exercise 与后续明确指定的手工字段可编辑。同步只能更新 Garmin 自己的事实，绝不覆盖手工部分。
- **理由**：用户希望在 Insight 有完整的日常/作息整理能力，同时不能给出 Orbita 可以回写 Garmin 的错误承诺。
- **开放项**：除 meal、手工 nap、手工 exercise 外，`daily` 与 `routine` 初版还应有哪些手工字段，以及是自由文本还是结构化字段，尚未决定。

### 2026-08-29 — Meal 是 Orbita Health 的独立事实，预留营养结构

- **决定**：餐食归 Orbita Health，不归 Orbita Journal；SQLite 初版中每餐是独立、可寻址的手工 Health 事实，不再嵌在混合来源的 `daily` 容器中。
- **数据边界**：Meal 保存发生日期/时间、餐别、食物、描述/备注，并预留结构化 `nutrition` 字段（热量及未来可选的蛋白质、碳水、脂肪等）。Health 的日摄入或 Panel 三环从 Meal 聚合，不能另存第二份可变的日汇总热量。
- **明确不做**：本版本不做营养自动换算、AI 估算、独立营养日志、补剂/无法归餐的营养修正记录，或把 Meal 显示为 Journal 记录。日后确有需求再另立 `nutrition_adjustment` Health 记录计划。
- **理由**：先消除 `daily` 混合 Garmin 与手工 meal 造成的覆盖/同步风险，同时为后续营养能力保留干净的扩展位置。
- **长期依据**：[`adr/0006-health-owned-meals-with-nutrition-envelope.md`](../../adr/0006-health-owned-meals-with-nutrition-envelope.md)。

### 2026-08-29 — Journal 初版有独立的随记记录

- **决定**：新增面向用户的 Journal「随记」记录类型；它与 event、mood 并列，是一条独立、可寻址、可同步的手工事实，不属于 `daily` 或 Health。
- **最小字段**：业务日期必填；发生时间可选；标题可选；正文必填。它支持新增、查看、编辑、软删、撤销、按日期回看和全文搜索。
- **边界**：event 继续表达简短的“发生了什么”，mood 继续表达结构化心情；随记不因此获得标签、附件、知识库、跨领域链接或 AI 自动结论。
- **长期依据**：[`adr/0007-journal-note-as-a-first-class-record.md`](../../adr/0007-journal-note-as-a-first-class-record.md)。

## 已确认范围

### 纳入

- Orbita Journal 的现有记录种类及其既有业务语义：`daily`、`routine`、`event`、`mood`、`exercise` 与其他 Journal 多条 kind。
- 保留当前稳定 ID、`Asia/Shanghai` 日历日、`daily`/`routine` 覆盖、`exercise.externalId` 去重，以及 Garmin 写入必须合并 `daily.meals`、保留 `routine.naps` 的契约。
- SQLite schema、迁移版本、读写仓储层、本地版本/删除标记/outbox，以及全新库初始化。
- Insight Health 与 Insight Journal 中每种现有记录的新增、查看、编辑、删除；按日期回看、筛选/搜索与可信保存反馈。
- Garmin 同步的可见状态与手动重试；Garmin 记录通过既有安全同步重新拉取，Orbita 不提供对其的编辑或删除。

## 0.0.18-a：可直接实施的详细规格

这一阶段的交付是：**在不读取旧 JSON 的前提下，让现有 Journal/Health 命令、Garmin 写入和 Panel 读取都改由一个全新的 SQLite 库服务，并为未来服务器同步可靠记录本地变化。** 它不是 Insight 重做；除移除 Panel 的喝水编辑外，不自行新增或改版 UI。

### A1. 允许与禁止改动的边界

允许在完成审计后修改的主范围：

- `orbita/src-tauri/src/journal.rs`，或其直接拆出的同领域 Rust 模块：SQLite schema、repository、领域写入与查询；
- `orbita/src-tauri/src/commands/integration.rs`：仅为保持现有 Journal command facade 的接线；
- `orbita/src-tauri/src/garmin.rs`：仅将已有 Garmin 同步的 Journal 持久化改走新 repository；
- `orbita/src-tauri/src/agent/tools/journal.rs` 及直接调用点：仅做命令兼容所必需的调整；
- `orbita/src/integrations/journal/`：client 兼容改动，以及 `today-panel.ts` 移除手工喝水写入；
- 与以上行为直接对应、且不与他人修改重叠的测试与本计划/当前事实文档。

明确禁止：Finance `.bean`、Finance 模型及同步、App State、设置格式、凭据/token、Garmin 原始文件/缓存、`docs_legacy/`、用户 `dataDir` 内容、Linux 服务、网络 API、认证、服务器/手机端、自动备份任务、UI 重做、统计页面、AI 产品语义。不得引入第二个 SQLite/ORM 依赖；仓库已有 `rusqlite` bundled 依赖，应复用它。

### A2. 必须先保留的外部兼容面

先阅读并保留下面的调用契约，避免“换库”变成隐性 UI 重写：

| 位置 | 不能破坏的契约 |
| --- | --- |
| `src-tauri/src/journal.rs` | 现有 `journal_list`、`journal_upsert`、`journal_delete` 的调用语义；`daily`/`routine` 单例、上海日期、`exercise.externalId` 去重、primary mood、跨年查询。 |
| `src-tauri/src/commands/integration.rs` | 现有 Tauri command 名称与请求/响应形状保持可用。 |
| `src/integrations/journal/client.ts` | `journalList`、`journalUpsert`、`journalDelete` 的 TypeScript 调用者不用知道 JSON 改 SQLite。 |
| `src-tauri/src/garmin.rs` | Garmin Python 同步生命周期、错误传播、token/SSO 处理不变；只替换落库方式。 |
| `meals-dialog.ts` / `primary-mood.ts` / AI Journal 工具 | 仍能经公共 Journal facade 写入；任何全量 `data` payload 都不得擦掉非本次所属的字段。 |

如果现有 command 形状不足以安全表示字段所有权，可以在 Rust 内部增加语义化 repository 方法，但不得把新的存储细节泄漏为前端必须理解的 SQLite API。

### A3. 数据库与迁移规则

1. 通过现有 `journal_root()` 取得路径。在 `{journalRoot}/journal.sqlite` 不存在时创建空库；**绝不**根据任何 `{journalRoot}/journal/YYYY.json` 是否存在而迁移、合并或 fallback。
2. 使用 schema version 表。打开已有 SQLite 时，先检查版本；每一次实际 schema upgrade 前在同一根目录创建一个可识别、不可覆盖的快照，然后才升级。首次建库不需要常规备份。升级/快照失败必须停止打开并返回可行动错误。
3. 推荐最小表集合：
   - `schema_migrations(version, applied_at)`；
   - `journal_records(id PRIMARY KEY, kind, business_date, source, revision, data_json, created_at, updated_at, deleted_at, external_id)`；
   - `journal_outbox(op_id PRIMARY KEY, record_id, record_revision, operation, origin, snapshot_json, created_at)`。
4. 对正常列表至少索引 `business_date`、`kind + business_date`、未删除记录；为 Garmin 幂等查询建立 `external_id`（必要时加 kind/source）的唯一性或等价约束。具体 SQL 可调整，但不能放弃这些查询与一致性约束。
5. `id` 是新生成的稳定 UUID，不能包含文件路径或年份。`revision` 是每条记录的正整数，只在记录语义真的变更时递增。所有时间戳使用统一、可测试的格式；业务日固定 `Asia/Shanghai`。
6. `data_json` 保留现有领域载荷，以减少前端兼容面；它不是绕过领域校验的任意 JSON 垃圾桶。持久化边界必须拒绝不合法的 kind、日期、关键字段或无法解析的数据。

### A4. 来源所有权与混合记录（不可破坏）

`source` 在本阶段只有 `manual` 与 `garmin`。它是记录/操作来源，不是让代码把整个 `daily` 或 `routine` 一概锁死的授权开关：两类容器本来就可能混合事实。

| 数据 | Orbita 操作 | Garmin 同步操作 |
| --- | --- | --- |
| `daily` 中的 meal | 可新增、编辑、软删 | 必须保留，不能覆盖或删除。 |
| hydration、夜间睡眠及 Garmin daily 字段 | 不可编辑、不可删除；Panel 不提供写入口 | 仅更新 Garmin 自己字段。 |
| 手工 nap | 可新增、编辑、软删 | 必须保留。 |
| Garmin nap | 只读、不可删除 | 按 Garmin 标识更新其自身。 |
| 手工 exercise（没有 Garmin `externalId`） | 可新增、编辑、软删 | 必须保留。 |
| Garmin exercise | 只读、不可删除 | 按 `externalId` 幂等更新其自身。 |
| Journal 手工 event/mood 等 | 可新增、编辑、软删 | 不得被 Garmin 写入触碰。 |

因此 repository 必须提供或在内部执行有明确名称的合并行为，例如“更新手工 meals”“应用 Garmin daily”“应用 Garmin night/routine”“应用 Garmin exercise”。不得把前端的整个旧 `data` 原样覆盖入库，造成 Garmin 同步丢失 meal 或一次 meal 编辑擦掉 Garmin 字段。也不得仅凭容器根部 `source` 决定前端能否写入。

### A5. 写入、删除与 outbox 的原子性

以下每一个成功事件必须在**同一 SQLite transaction**完成“变更记录 + revision 递增 + 写一条 outbox”：

- 新建、修改、删除、撤销删除任何 Orbita 手工拥有的记录；
- Garmin 导入产生的新增或实质性内容变更。

Outbox 至少要带：独立 `op_id` UUID、记录 ID、变更后的 revision、`upsert`/`delete` 操作、`manual`/`garmin` origin、变更后可重放的记录快照，以及创建时间。未来服务只消费该表；0.0.18-a 不发送网络请求、不标记 ack、不做冲突解决、不清理 outbox/tombstone。

删除是 soft delete：写 `deleted_at`、递增 revision、记录 `delete` outbox，正常查询排除；5 秒撤销取消该标记、再次递增 revision 并写 `upsert` outbox。不得物理删除。Garmin 记录/字段不提供 Orbita 删除。若同一 Garmin payload 与当前事实语义相同，不得递增 revision 或重复产生 outbox。任一 SQL 失败即整个 transaction 回滚并报错，禁止显示“已保存”。
