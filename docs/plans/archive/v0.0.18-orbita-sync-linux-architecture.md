# v0.0.18+ Orbita Sync：Linux 同步服务总体架构

> **Outcome（已被替代，2026-09-02）：**本稿的 Journal / Health v1、桌面 Garmin collector 与 TickTick authority 前提已被 0.0.19 的一个 Sync Core、Garmin Ingest、Schedule Adapter 三模块边界取代。它未授权实现或部署，仅保留历史约束与故障推演供追溯。

> **状态**：架构设计输入，尚未授权实现。它为 0.0.18 的本地 SQLite / outbox 奠定网络侧目标，不改变该计划的范围、字段或实施状态。
>
> **范围**：从客户端本地事实到深圳 Linux 上 `orbita-sync` 的离线同步、冲突、历史、运行与恢复架构。首版只覆盖 Orbita Journal / Health；Finance、手机客户端和服务端 Garmin 接入均不在本计划实现。
>
> **前提**：截至 2026-08-30 工作树，`journal.sqlite` v1、专业事实表、稳定 UUID / revision / tombstone 与同事务 `sync_outbox` **正在实现，尚未验收**。它们只提供本地事实和可重放快照的基础，不包含任何网络 ACK、cursor、远端基线或冲突状态。启动网络同步前必须完成本文件 §3.1 的 S0 迁移与 L3 验收。

## 1. 结论与不变量

Orbita Sync 不是文件同步、网络盘或“把一个 SQLite 拷到另一台机器”。它是一个在私有网络中运行的、**记录级的离线同步与恢复服务**：各客户端永远先可靠地写自己的本地数据库；联网后以可重放操作和增量游标与服务器收敛；服务器保存当前副本、不可变历史与冲突分支。

```text
桌面 Orbita                         未来 Android
本地 Journal/Health SQLite           本地 Journal/Health SQLite
  领域 repository                       领域 repository
  + 事务 outbox                          + 事务 outbox
          │                                      │
          └──── Tailscale 私网 + HTTPS + 设备身份 ────┘
                                      │
                         深圳 Debian · orbita-sync
            API / device auth / sync engine / history / conflict / recovery
                                      │
                  独立服务器 SQLite（current + operation log + versions）
                                      │
                     加密备份与恢复演练（不是同步传输路径）
```

以下是不变量，任何实现或后续提案不得绕过：

- 每个客户端和服务器的 SQLite 都是独立副本；只传受版本控制的记录、删除标记、操作确认和增量变化，**绝不**复制、挂载或共享 SQLite 文件。
- v1 只接受 Journal / Health 的已列明专业事实与规范化 Garmin 快照；不建立万能 `Event`，不以不透明 JSON 取代领域 schema。
- 本地写入在离线时仍成功。网络失败绝不撤销本地事实、删除 outbox 或假报“已同步”。
- 传输是 *at-least-once*，效果以 `op_id` 去重达到“至多应用一次”；任何请求、响应或客户端崩溃后均可安全重放。
- 同一记录的离线并发修改、修改/删除、删除/修改都保存为冲突，不使用静默 LWW；用户显式 resolve 才生成新的规范版本。
- `.bean` / Beancount 继续是**当前** Finance 的唯一真源。v1 路由对 Finance 返回明确的 `not_supported`，不得接收账本文件、不得写 `.bean`、不得启动或冒充 Finance Commit。Finance v2 另立计划后，Transaction / Posting 复用同一个记录级 Sync Core，而不是新增 Finance 专用同步通道。
- Garmin 仍由已拥有 token 的桌面端按既有零 SSO、限流契约拉取，再把规范化事实同步出去。首版服务端不保存 Garmin token、不做 SSO、不定时抓取。
- Tailscale 是私有传输层，不是应用授权层。每台设备仍须有可撤销的 Orbita 身份和最小权限。

这些结论落实 `docs/SYSTEM.md` §6、当前 0.0.18 SQLite 计划、`docs/specs/orbita-journal-health.md`、DigitalInfra 的 ADR 0004、0009、0026、0027、0028；其中已接受的服务器 SQLite 决定优先于“为了并发而立刻改 PostgreSQL”的建议。

### 当前实现审计：同步尚不可直接接线（P0）

当前工作树的 `journal_db/schema.rs` v1 已有 `sync_outbox(op_id, domain, record_type, record_id, revision, operation, origin, snapshot_json, created_at_utc)`，并且 Journal 写入/删除与 Garmin batch 均把事实和 outbox 包进本地事务。这是正确的本地基础；但它**不是**可直接发送到服务端的完整 wire protocol，原因如下：

- 缺少 `base_server_version`、contract version、ACK/status、重试/lease、错误、cursor、inbox/dedupe、远端影子与冲突存储。
- 当前 `revision` 是单个本地数据库中每条事实的计数，不是跨设备可排序版本，不能用作 server cursor 或并发判定。
- 当前 `content_hash` 是 Rust 本地 `serde_json` 序列化后的 SHA-256；尚不是 Android、服务端与桌面共享的 canonical JSON 规范。部分 outbox snapshot 还没有包含重建业务键所需的全部字段：已发现 `metric_day_snapshot` 快照缺少 `metric_name` 与 content hash。
- `daily_metrics(local_date)`、`sleep_nights(wake_date)`、`metric_day_snapshots(local_date, metric_name)`、`activities(external_id)` 的现有唯一约束没有统一包含 `source`。这与“Garmin 与手工同日/同类事实可共存”的 ADR 方向存在 P0 矛盾；服务端不得抢先猜测合并规则。
- 当前 `garmin_sync_meta` 仅代表本机 Garmin 拉取状态，不能拿来显示或驱动 orbita-sync 状态。

因此 S2 不得“读取现有 outbox 然后发 HTTP”。必须先通过 S0 明确并迁移本地/契约的同步语义；本节是实现事实快照，不把其他 agent 的在制代码宣称为完成。

## 2. 责任边界与首版范围

| 层 | 拥有者 | 做什么 | 明确不做 |
| --- | --- | --- | --- |
| 领域 repository | 桌面 / Android | 事实校验、本地读写、日期/来源语义、tombstone | 直接调用 HTTP 或自行裁决远端冲突 |
| Sync Core | 每个客户端 | outbox、inbox、游标、重试、设备会话、同步状态 | 业务 UI、Garmin 登录、直接修改另一端 DB |
| `contracts/` | 跨端边界 | 版本化 schema、错误码、脱敏 fixtures、兼容矩阵 | 用户数据、token、SQLite 或运行配置 |
| `orbita-sync` API | Linux 服务 | 认证、验证、幂等接收、变更流、冲突、历史/恢复授权 | UI 领域业务、原始 FIT 处理、Finance 落盘 |
| Sync Store | Linux 服务 | current projection、操作日志、版本、冲突、游标、保留策略 | 客户端数据库的镜像文件 |
| 运维 / 备份 | Linux 服务 | 生命周期、密钥、备份、观测、恢复演练 | 把云盘或 SMB 当在线同步通道 |

### v1 允许同步的对象

以 0.0.18 的专业表为目标，首批 contract 对象是 Journal `events`、`moods`、`notes`，Health 的 `meals`、手工 `naps`、手工 `activities`，以及 Garmin `daily_metrics`、`metric_day_snapshots`、`sleep_nights`、Garmin nap、活动摘要、体测记录。`body_measurements` 虽已有表，但当前桌面尚无手工 CRUD / 投影入口；它只能作为 contract 预留对象，不能承诺为首版已可手工同步。`daily`、`routine` 是兼容读取投影，绝不是网络对象。高密度数据必须以“本地日 + 指标 + 规范化快照 + coverage/content hash”作为一个同步单元，不能一采样点一条 outbox。

所有对象沿用本地真源的 UUID、`source`、领域类型、创建/更新时间、内容 revision 和 `deleted_at` / tombstone。服务端不重新解释上海业务日、醒来日或 Garmin 的 UTC 时序；它只验证 contract、来源所有权与不可变记录历史。

### 明确排除

- App State、窗口状态、主题缓存、凭据、Garmin token、rate-limit 文件、日志和 AI 密钥；它们不是普通事实操作，凭据若要跨设备须独立安全设计。
- 旧 JSON 的导入、`archiveRoot` 拆分、SQLite 文件迁移；仍由当前桌面计划的明确选择和另立迁移计划处理。
- raw FIT、照片、附件和其他大对象。未来需另设 blob/upload 协议（内容哈希、分块、保留、访问控制），不能塞进本同步快照。
- Finance、TickTick、Obsidian、Knowledge、Media 及跨域 Connection。服务端为它们预留 domain 隔离能力，但不假装已经支持。

## 3. 版本与同步数据面

本地 `revision` 不能充当全球游标：两个离线设备都可能产生 revision `7`。协议必须区分三种版本。

| 名称 | 归属 | 用途 |
| --- | --- | --- |
| `local_revision` | 客户端事实 | 本地写入顺序、outbox 快照可观测性；不跨设备比较大小。 |
| `server_version` / ETag | 单条服务器记录 | 条件写入的前置版本；只有与客户端同步影子中的 base 一致时可应用。 |
| `change_seq` | 服务器 account 的单调变化流 | 不可猜测的增量 cursor；只用于 pull，绝不用时间戳或本地 revision 替代。 |

### 3.1 S0 必须落地的本地同步元数据

客户端 Sync Core 必须由独立 migration（推荐 `journal.sqlite` v2；也可为独立、同数据根的 sync DB，但只能二选一并验证原子边界）落地，不能等到服务阶段“再定字段”。最小模型为：

- `sync_records(domain, record_type, record_id, server_version, server_content_hash, last_remote_change_seq)`：每个领域事实的远端影子；主键是前三项。
- `sync_replica_state(replica_id, bootstrap_state, account_binding, applied_change_seq)`、`sync_cursor(stream, last_change_seq)`、`sync_applied_ops(op_id, applied_at_utc)`、`sync_conflicts(...)`：durable 副本身份、pull 游标、回声/重放去重与用户可处理的冲突。每个 `journalRoot` 都是独立副本：data root 切换到空库必须走 attach/bootstrap，不能把旧根的会话或 token 静默沿用。
- `sync_outbox_delivery(op_id, state, attempts, next_retry_at, last_error, acked_at_utc)`：投递生命周期；保留既有 append-only `sync_outbox`，避免让业务事实表承担传输状态。
- 为每条 outbox operation 在**业务事实变更同一事务**中冻结 `base_server_version`、`contract_version`、`content_hash` 与完整 type-specific snapshot（可作为 `sync_outbox` 新列或一对一 delivery/envelope 表）。base 必须读取当时 `sync_records` 的值，不能在发包时临时计算；同一实体的未确认操作严格串行投递。

远端 apply 必须在一个客户端事务中写领域事实、上述 `sync_records` / cursor / applied-op，并处于明确的 `apply_remote` 模式，**绝不再产生本地 outbox 回声**。同步 worker 必须 single-flight，并在 `dataDir` / `journalRoot` 切换时停掉旧根会话、丢弃其内存状态后从新根重建。

### 操作信封（概念契约）

```text
op_id                 # UUID；设备生成，全局幂等键
contract_version      # 如 journal-health/v1
entity = domain + type + stable record id
kind = upsert | delete | resolve
origin = device identity / garmin importer identity
base_server_version   # 本地最后确认的远端版本；新对象为 null
local_revision        # 仅供审计和本地顺序
snapshot / tombstone  # 完整、可重放的规范化事实快照
content_hash          # 每种对象的 canonical payload hash；fetched_at 等噪声不得改变它
created_at
```

服务端从认证会话取得 account 与 device，绝不相信 payload 声称的 account。`snapshot` 必须符合 `contracts/` 中按 type 定义的 schema、最大体积和来源白名单；所有 SQL 参数化，禁止透传任意字段或文件路径。S0 在 `contracts/` 固定 RFC 8785 或等价的 sorted-key UTF-8 / number / null policy，并为每个 record type 固定 hash 输入与 fixtures；不能把 Rust 当前的 JSON 序列化偶然结果当跨端标准。每个 snapshot 还必须包含其自然键和 schema 所需字段；特别 `metric_day_snapshot` 必须带 `local_date`、`metric_name`、`source`、coverage 和 hash，才能在远端和新设备重建对象。

## 4. 同步循环与崩溃语义

同步由 app 前台、网络恢复、受控周期与用户“立即同步”触发；同一设备只允许一个 single-flight session。周期和退避是实现参数，不能把高频轮询当可靠性。UI 始终显示：上次成功、待发送数、冲突数、当前错误与下次可重试时间。

```text
1. 领域写入：fact + revision/tombstone + full outbox snapshot 在一个本地事务提交。
2. 建立已认证会话，携带上次 durable change_seq 和有限批 pending op。
3. 服务端逐 op 事务：鉴权 → schema/ownership/base 校验 → op 去重
   → append immutable operation/history → 更新 current 或写 conflict → durable ACK。
4. 服务端返回逐 op 结果 + 从 cursor 起的分页变化 + next change_seq。
5. 客户端一个事务应用 remote current/conflict、持久 `sync_records` / inbox-dedupe 与 next cursor，且 remote apply 不产生 outbox；
   仅在此之后把对应 outbox 标为 ACK（或可安全压缩）。
6. 仍有分页或 pending 时继续；任一步中断，重新以同一 op/cursor 执行。
```

服务端可实现为一个 `POST /v1/sync` 会话端点，或语义等价的 `push` + `pull`；接口形态不是重点，以上事务边界不可改变。返回须逐操作区分 `accepted`、`deduplicated`、`conflict`、`rejected`（不可重试）和 `retryable`，不能只给一个 HTTP 200。

客户端处理顺序为 **先 durable 远端应用，再确认本地 outbox**。网络在请求前、服务端提交后、响应前、remote apply 中任意断开，都只能导致重传，不能导致漏记录或重复生效。批量有限（建议初始上限 100 ops）并带分页，避免 metric snapshot 或历史恢复导致内存失控。

首次接入不做危险“全量互相覆盖”：

- 空服务器 + 已有受信任客户端：经明确初始化向导把客户端事实作为首个上传源。
- 空新设备 + 已有服务器：分页 pull 后再允许写入。
- 两个都非空且从未互信的副本：进入 staged import，先列出重复/同 ID 碰撞/来源差异；用户确认合并策略前不得自动上传覆盖。

## 5. 冲突、删除、来源所有权与历史

### 冲突规则

1. UUID 不同即使发生在同日也并存；不能按日期或文本“智能合并”。
2. 同一 ID 且 `base_server_version` 相同，服务器接受并产生新的 `server_version` 与 `change_seq`。
3. 同一 ID、base 不同但 canonical `content_hash` 相同，是幂等 no-op。
4. base 不同且内容不同，服务器保持当前规范版本，存入含 base、双方快照/hash、device、操作和时间的 immutable conflict branch，返回 `conflict`；**不静默选边**。
5. 有冲突的对象默认冻结进一步常规编辑，仅允许显式 resolve。resolve 可选“保留我的 / 采用服务器 / 手工合并 / 另存为新 UUID”，但无论哪种都产生新 operation、新版本并保留冲突历史。

### 删除与恢复

删除是条件版本的 tombstone，不是物理删除。编辑/删除、删除/编辑、删除/删除均按上述规则进入冲突或幂等，不可因“删除优先”静默丢掉编辑。**恢复语义是 S0 的强制决策项**：当前本地实现允许以更新清除 tombstone（用于撤销），而本设计原先的“旧 upsert 不复活、重建用新 UUID”与其不兼容。S0 必须选择并端到端实现其一：显式 `restore` operation（推荐，保留原 UUID 与可审计版本）、只允许新 UUID，或禁用本地 undo；服务端和客户端不得各自采用不同规则。

服务器保存 Journal/Health 版本历史至少 180 天，符合 DigitalInfra ADR 0009。tombstone 的保留期不得短于历史期与支持的最大离线窗口；建议首版保留至少 365 天，之后只有在所有活跃设备水位已越过且不触发恢复承诺时再回收。长期离线或被撤销设备超过窗口后，应被要求全量安全重同步，不能让旧 outbox 复活已删对象。

### 来源所有权

- `source=manual`：所属用户的受信任设备可创建、编辑、软删。
- `source=garmin`：v1 必须在配对时选择唯一 `garmin_collect` device capability；只有它可写 Garmin type，其他客户端只 pull，token 永不上传。服务端按认证设备 capability（而不是 payload 中可伪造的 `origin="garmin"`）授权。迁移到服务端 connector 后才可替换为 server importer identity；两者绝不可并行写同一 Garmin 自然键。普通 UI/API 不得编辑或删除 Garmin 事实；相同内容 hash 无操作，内容变化保留历史。
- 手工与 Garmin 同日共存，服务端不做跨来源合并。服务端唯一性约束应按领域语义实现，例如 Garmin 外部对象的 `external_id`、日快照的 `(metric, local_date, source)`，而非误用 UUID 以外的业务字段覆盖手工记录。

在首次 remote apply 前，0.0.18 schema 必须完成并验收来源型唯一约束的选择：若 ADR 0009 的“手工与 Garmin 事实共存”仍是目标，则相关 natural key 至少采用 `(source, local_date)`、`(source, wake_date)`、`(source, local_date, metric_name)`、`(source, external_id)`，并为投影固定选择/展示规则；若某对象只能有一个权威来源，必须在 contract 和 UI 明示。当前全局唯一键不能直接进入多端同步。

除单条 ID 版本外，S0 还要列出跨记录不变量。已知 `mood.primary=true` 要求每个上海日最多一条：两个设备离线新建不同 UUID 时不会触发同 ID 冲突，却可能得到两个 primary。服务端须采用范围版本（例如 `journal:primary-mood:{local_date}`）并产生 invariant conflict，或在 v1 暂不支持同步 primary；不得静默选一个。Garmin body measurement 目前也没有持久化可供跨设备去重的 external key，且同日多测量语义未定，故在自然键、snapshot 和多次测量规则定案前不得开放该 type 的多端写入。

## 6. Linux 服务与数据存储设计

### 6.1 服务模块

```text
services/sync/
├─ api/                 # HTTPS handler、schema/version gate、rate limits
├─ auth/                # device enrollment、token rotation/revocation、authorization
├─ protocol/            # session、push/pull、cursor、idempotency
├─ store/               # SQLite migrations、transactions、current/history/conflict
├─ retention/           # history/tombstone lifecycle；single leader
├─ recovery/            # audited restore/export only
├─ observability/       # redacted logs、metrics、health/readiness
└─ deploy/              # Compose/systemd、backup/runbook templates
```

服务端 SQLite 是首版单一逻辑写入者，启用 WAL、外键、显式短事务与迁移版本表。它可以承受本计划的一名用户、少量设备的同步规模；不得把 SQLite 文件放在 SMB、mergerfs、云盘同步目录或 NFS 上。数据库 schema 最少区分：`accounts`、`devices`、`device_tokens`（仅 hash）、`records_current`、`operations`、`record_versions`、`conflicts`、`client_checkpoints`、`schema_migrations` 与审计/恢复记录。current projection、immutable operation/version、ACK 或 conflict 必须同一数据库事务。

升级到 PostgreSQL 的触发条件不是猜测：出现需要多实例主动写入、SQLite lock 指标持续超阈值、备份/恢复窗口无法满足已定 RPO/RTO，或服务端需要多租户规模时，先提交迁移计划、双库迁移/回滚和真实压测证据；在此之前坚持独立 SQLite 的既定路线。

### 6.2 部署与网络

- 深圳 Debian 无桌面主机上运行；首版用 Docker Compose 编排 API 与可选的单 worker，或用等价 systemd service。无论形式，都只允许一个 migration/retention leader。
- 外部入口只经过 Tailscale 私网的 HTTPS reverse proxy / ingress；不暴露公网入站端口。数据库没有 TCP 暴露面，只挂给服务进程。
- 应用持久化位于 SSD `appdata` 的专用、非 SMB 路径；服务用户非 root，目录权限 `0700`，容器 root filesystem 尽量只读且仅挂最小数据卷。
- Tailscale ACL/设备允许名单控制网络可达性；API 仍验证设备 token、account scope 与请求大小/频率。所有读取都从会话 account 限定，消除 IDOR。
- 设备配对使用一次性、短寿命批准码或已登录可信设备确认；服务只存随机 token 的不可逆 hash。token 可轮换、过期与撤销。换机与恢复流程必须可从服务器管理面审计。
- 首期服务器可读业务明文，不引入客户端 E2EE；磁盘采用宿主机加密卷或等价 at-rest 方案，异地备份加密，密钥不与备份一起存放。具体工具与密钥恢复责任仍待确认。

## 7. 可靠性、备份与观测

历史不是备份。服务在每次迁移前进行一致性快照；日常备份通过 SQLite 在线一致备份 API 或停写窗口生成，不得生拷活跃 WAL 文件。备份至少包含数据库、迁移版本、必要的非机密服务配置清单和密钥恢复说明；离站副本须加密。

上线前由产品负责人确认 RPO/RTO。当前建议目标：Journal/Health **RPO ≤ 24h、RTO ≤ 4h**；每月抽样恢复、每季隔离环境完整恢复演练。恢复验证检查 current、version history、tombstone、conflict、hash 和 cursor，而不是只确认数据库能打开。

日志采用结构化且脱敏的事件（request/op correlation ID、device ID 的安全摘要、错误码）；日志、metrics、崩溃报告不得包含 token、正文、健康/随记内容。最低指标：认证失败、请求错误/延迟、accepted/deduped/rejected/conflicted、待同步和最老 outbox 年龄、cursor lag、冲突队列、DB size/lock、迁移版本、备份年龄/最近恢复、磁盘余量。分别提供：

- `/healthz`：进程存活；
- `/readyz`：数据库可用、迁移完成且满足已定义的备份新鲜度策略；
- 用户可见状态：不含内容的服务器状态、最后成功、pending、conflict、行动建议。

服务重启、断网和数据库暂时不可用时，客户端退避并保留本地写入；服务端不能启动第二个 worker 或把失败变成无限重试。断电/网络恢复后由 systemd/Compose 自启和 readiness 保护，而不是盲目重跑迁移。

## 8. 分阶段实施计划与门槛

| 阶段 | 交付 | 前置 / 退出证据 |
| --- | --- | --- |
| S0：契约与本地同步迁移冻结 | `contracts/` v1、对象清单、canonical hash、错误码、兼容矩阵、脱敏 fixtures；§3.1 client sync metadata migration；所有 snapshot 含 natural key；来源唯一键、单一 Garmin collector、跨记录 invariant 与 tombstone/undo 决策 | 0.0.18 的本地 schema/outbox 已验收；验证 source collision、remote apply 无 outbox echo、outbox 崩溃状态、metric snapshot round-trip、连续同实体操作的 base 固化、replica/root 切换、primary mood invariant、tombstone/undo；架构/安全审计签字。 |
| S1：服务骨架 | 独立 `services/sync`、SQLite migrations、Tailscale-only ingress、device enrollment/revoke、health/readiness | 空库、迁移失败回滚、未授权/越权/撤销设备均被拒绝；无公网端口。 |
| S2：Journal/Health 同步 | operation log、current/history/conflict、push/pull cursor、桌面 Sync Core 与可见状态 | 离线写入、重试去重、分页 bootstrap、冲突/tombstone、Garmin snapshot 语义均通过。 |
| S3：恢复与运维 | 180 天保留、受审计 restore、备份/告警/runbook、断电与恢复演练 | 达成已确认 RPO/RTO；实际隔离恢复验收，不能只看备份日志。 |
| S4：Android 接入 | 独立本地 SQLite + 相同 contracts / Sync Core 行为 | 新设备 bootstrap、换机、旧/新 contract 兼容；不复制桌面数据库。 |
| S5：Finance（独立计划） | 在同一通用 Sync Core 上接入 canonical finance Transaction / Posting、冲突体验、单一受控 materializer → Finance Commit → `.bean` reconciliation | 此计划完成前，v1 永远拒绝 Finance；必须处理首次导入、物化崩溃重放、审计和实账本回归。 |

每一阶段都是 L3（用户数据、并发、凭据与进程生命周期）。实施时必须有独立架构/安全审计、实现、测试与验收角色；子代理不可自行启动测试/服务，动态验证由协调者串行完成并遵循 `docs/AGENTS.md`。

## 9. 验收矩阵

1. 空设备从服务器分页 bootstrap，cursor 在本地事务中持久化；重复启动无重复记录。
2. 离线新建、编辑、删除后重连：本地不丢，服务端和第二设备收敛；只有 durable ACK 后 outbox 才能清理。
3. 请求前/后、服务端提交后响应前、客户端 remote apply 中崩溃：任意重放均不重复应用、不跳 cursor。
4. 重复、乱序、跨批 op 和相同 Garmin payload：幂等、无重复 history、无 revision 噪声；部分批逐 op 可继续。
5. 双设备对同一 ID 的 edit/edit、edit/delete、delete/edit、delete/delete：均有审计冲突，无静默覆盖；resolve 后各端收敛。
6. Garmin 不可被普通客户端编辑/删除；手工与 Garmin 同日共存；缺 token/429 不因同步服务引发 SSO 或重试风暴。
7. 伪造 account、IDOR、撤销设备、过期/篡改 token、重放旧 op/cursor、超大/错误 schema 均被拒绝且不泄露内容。
8. 旧/新 client 在兼容窗口同步；不兼容明确返回 `upgrade_required`，outbox 不损失；失败 migration 保留完整可恢复 DB。
9. 180 天 history 与 tombstone 回收符合设备水位/离线策略，旧客户端不能复活删除记录。
10. 服务重启、断网、WAL 恢复、single-worker 约束、限流/退避均可观察且无双写。
11. 从加密离站备份恢复到隔离环境，逐项核对 current/history/conflict/cursor/hash，并满足 RPO/RTO。
12. 对最大允许 snapshot、最大批次与大历史分页压测，无 OOM、无错误授权、无数据遗漏。

## 10. 需由维护者确认的决策

下列事项不能被此架构设计或实现 agent 自行拍板；在进入 S1/S2 前应形成 ADR 或明确产品确认。

1. 首期是否严格单 account，还是一开始支持多账户/伴侣身份；设备配对、设备审批、丢失设备撤销与换机恢复的实际 UI。
2. 冲突 UX 是否采用推荐的“冻结常规编辑，集中 resolve”，以及 resolve 页面放在桌面、手机还是服务端管理面。
3. 最大离线窗口、tombstone 的最终保留期（本设计建议 365 天）和超期设备的全量重同步体验。
4. 服务器磁盘加密方式、备份工具、密钥托管、最终 RPO/RTO 和恢复演练责任人。
5. 是否永久保持“桌面 Garmin importer → sync”，或未来让服务器持 token 定时抓取。后者需独立凭据、SSO、429、审计和迁移设计，不能作为 sync v1 的顺手功能。
6. Finance 的 canonical record 模型、首次账本导入、单一 materializer、冲突与审计。它是单独项目，不是 Journal/Health 协议的一个字段扩展。
7. SQLite → PostgreSQL 的具体量化阈值（并发、锁等待、备份时窗、实例数），在没有数据前不提前迁移。
8. 当前不完整 outbox snapshot 的补救方式：在 0.0.18 基线前重建正确 envelope，或明确旧 outbox 清空/重新导入的用户确认与回滚路径；不得让服务端猜 `metric_name`、nap external key 或体测自然键。
