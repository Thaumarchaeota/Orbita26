# v0.0.19：一个 Sync Core 与两个外部 Adapter

> **状态：Proposed 主架构，未授权实现、迁移、外部接入或部署。**
> **日期：2026-09-01**
> **替代：**本文件取代已归档的 `v0.0.18-archive-sync-garmin-server-architecture.md` 作为后续同步设计的主输入；后者仅保留其中仍一致的 aggregate、Garmin 迁移和诊断细节供追溯。
>
> **正式模块：**Sync Core、Garmin Ingest、Schedule Adapter。它们的定义见 `GLOSSARY.md`。

## 1. 一句话架构

所有 Archive `object`、独立 `data` 根及其 `component` / 严格子 `data` 都先写入 PC、手机或服务器各自的 SQLite；**Sync Core** 只负责让这些版本化 aggregate 可靠收敛。Garmin Ingest 与 Schedule Adapter 都是服务器私有 adapter：前者把 Garmin 单向导入变成可信的 Core 写入，后者把已存在的 Schedule object 映射到 TickTick。

```text
PC SQLite ─┐                         ┌─ Garmin upstream
手机 SQLite ─┼─ Sync Core ────────────┼─ Garmin Ingest
Server SQLite ┘                       └─ Schedule Adapter ↔ TickTick
       │
       └─ PC-only Finance SQLite → deterministic .bean output
```

这里没有 Finance Sync、Garmin Sync、TickTick Sync 三套协议；只有一个 Core 和两个 adapter。

## 2. 共用事实边界

Registry 的 `classification` 决定同步身份：

| 类型 | Core 中的角色 |
| --- | --- |
| `object` | 可独立作为 aggregate 根；可构成 `ArchiveRef` / Connection Member。 |
| 独立 `data` 根 | 可作为 aggregate 根，但不可成为 ArchiveRef，例如 Health Day。 |
| `component` / 严格子 `data` | 永远随父 aggregate 完整原子传输；不可独立 ACK、冲突、引用或投递。 |

每个 aggregate 由 `{domain, type, id}` 定位，保存完整 canonical snapshot、detail manifest、server version、tombstone 与历史。物理 SQLite 表、Markdown 路径、投影、缓存、outbox、inbox、shadow、外部 command 和 adapter state 都不是 Archive Object。

Finance v2 采用 `finance/transaction + posting[]` aggregate；Observation、对账工作区、账户映射和 `.bean` materialization 不同步。`.bean` 是 PC 本地 SQLite 的确定性单向输出，用于 Beancount 校验/报告，不能反写 SQLite，也不是第二真源。

## 3. 模块一：Sync Core

### 唯一职责

让多个 SQLite replica 对版本化 Archive aggregate 收敛，并留下可验证的历史证据。

### 唯一输入与输出

| 输入 | 输出 |
| --- | --- |
| 客户端本地领域事务冻结的 `CommitGroup` | accepted / deduplicated / conflicted / rejected receipt |
| Garmin Ingest 的可信 `ServerCanonicalCommit` | current、immutable revision、change log 与设备 delivery |
| Schedule Adapter 经鉴权的 Schedule commit | 客户端 durable apply / ACK、冲突与诊断证据 |

`CommitGroup` 是一次用户动作的 `1..N` aggregate 原子集合；同账户的 `opId` 加 semantic group hash 是幂等键。普通编辑只包含一个 aggregate；Connection 建立成员、Work 的跨 aggregate 动作等必须整体接受或拒绝。Connector 不得假装为客户端 CommitGroup。

### Core 只保留的能力

- account / device enrollment、撤销、协议与 Registry capability；
- 本地事实 + immutable outbox、inbox/delivery receipt、shadow/cursor 的单 SQLite 事务；
- full aggregate canonicalization、hash、版本、current/history/change log、tombstone/restore、冲突和 resolve；
- bootstrap cutover、per-device issued delivery、连续 ACK、retention / restore；
- Registry 与领域 validator 的调用、post-group 原子校验；
- `opId + traceId + deliveryId` 审计、Sync Doctor、脱敏 support bundle、备份恢复证据。

Core 不定义 Meal、Transaction、Work Node 或 ScheduleBlock 的业务规则；领域 Registry / validator 提供它们。Core 也不复制 SQLite、Markdown 或 `.bean` 文件，不调用第三方 API，不做最后写入获胜或未定义的自动文本合并。

### 最小协议

```text
enroll → bootstrap → pushCommitGroup → pull → ack
                                  └→ resolveConflict
                                  └→ diagnostics (read-only, capability scoped)
```

客户端先在本地提交事实和 outbox；服务端只在完整 group 的 post-group view 验证成功后写 current/history/change log。Pull 返回服务器签发的 `deliveryId` 与连续 issued watermark；客户端 hash/schema 校验并本地原子 apply 后才能 ACK。ACK 不得超过该设备已签发的连续水位，也不得取代 history/tombstone 的保留策略。

未知 type 不允许客户端创建或修改；已存 opaque revision 可被转发/备份。已知 type 遇到未知字段则只读并阻止重写，避免旧客户端丢字段。

## 4. 模块二：Garmin Ingest

### 唯一职责

服务器唯一 Garmin credential holder、API caller、raw receipt 保存者、normalizer 与 Garmin-authority writer。

它的唯一 Archive 输出是经过 Registry/Health 校验的 `ServerCanonicalCommit`；该提交只经 Sync Core 的 Garmin Write Gateway 写 current/history/change log，再由 Core 分发。Garmin Ingest 不直接写 PC/手机 SQLite，不维护第二套 delivery/history/ACK。

### 私有状态与所有权

Garmin credential、connector account、lease、单调 fence、cursor/window、external mapping、raw receipt/FIT 定位、run、reconciliation 都在服务器 adapter 私有库中，永不进入 Archive、Connection、Timeline 或普通 payload。

服务端另持久化 authoritative ownership/provenance：

```text
(account, aggregateKey, authority=garmin|user,
 connectorAccount?, externalMapping?, sourceRevision)
```

它是 create/replace/delete/restore/resolve 的授权依据；客户端 `source` / `origin` 从不参与授权。普通设备不能修改任何 Garmin-authority aggregate，也不能将其降级为 manual。Activity / Sleep 用外部稳定映射复用 Orbita UUID；同类手工 Object 使用另一个 UUID。

### 原子导入规则

- Activity 是单 Object aggregate；Sleep Night 与完整 stage set 同一 aggregate。
- Health Day 与全日 Sample 是完整 data aggregate：hash 相同不写；变化时单事务更新 Day、删除旧 Garmin sample、插入完整新集，再发布一个 revision。
- Registry 尚未定 Health Day 的稳定 id、多账号和时区重解释规则；这些未定前 Day/Sample 不进生产 allowlist。
- 外部暂时消失只生成 `missing_candidate` reconciliation finding；没有明确 policy 时不得 tombstone。
- 每次写入均验证 account、active phase、未过期 lease、fence、connector principal 与 ownership。旧 worker、重复 job、错误 source 均拒绝。

迁移只能是：desktop collector drain → server read-only discovery/reconciliation → 明确批准 server active → desktop 成为普通 Core replica。回滚先停止/等待 server worker、撤 fence、记录水位，再恢复唯一 collector；绝不双写。

## 5. 模块三：Schedule Adapter

### 唯一职责

服务器对 `plan/plan-item(kind = schedule)` 与 TickTick 的**可移除双向映射**。Orbita SQLite Schedule 永远是事实源；TickTick 不产生 Work/Task Object，也不拥有 Project、Node、Session、Segment、Todo、Group 或 Connection。

### 边界

- 出站：只消费 Core 已接受的 Schedule revision/change log，生成带 idempotency key 的 TickTick command。
- 入站：adapter 完成 external-id 映射、字段校验和并发判断后，经 Core 的受控 adapter commit 写入同一个 Schedule aggregate；不得直接写 Archive SQL 或绕过 history/conflict。
- 私有状态仅为 credential、external mapping、remote shadow/cursor、pending command/receipt、reconciliation/audit；不进入 Archive 或 Sync payload。
- 停用 adapter 只停止外部拉取/命令，绝不伤害本地 PlanItem。与 PC/手机离线编辑并发时由 Core 形成 aggregate conflict，TickTick 不自动获胜。

TickTick 字段映射、OAuth、external delete/restore、命令幂等与冲突 UX 尚未定案。因此 Schedule Adapter 是 reserved 模块：先固定 Core 接口和 Schedule 领域 schema，再另立实施计划；不得现在接真实数据。

## 6. 追溯与调试属于 Core，不是第四系统

Core 的最小证据链：

```text
client local commit → outbox durable → push
→ accepted | deduplicated | conflicted | rejected
→ published → delivery issued → durable apply | failed → ACK
```

Garmin Ingest 在前面增加：`fetch → raw receipt → normalize → validate → reconcile → canonical commit`；Schedule Adapter 增加：`revision observed → command/mapping → provider receipt → remote revision → Core commit/reconcile`。

客户端保存 append-only local audit；服务器保存 server-observed receipt、revision、delivery、conflict 与 adapter event。Sync Doctor 必须标明每条证据是 `client-reported` 或 `server-observed`，以因果序列而非设备墙钟判断先后。日志和 support bundle 只含 HMAC 标识、hash、版本、状态码、计数与时间，禁止业务 payload、MD、健康数值、raw/FIT、token、OAuth code、凭据、SQLite 原文错误和本机路径。

## 7. 当前与目标的过渡

本文件描述目标，不声称当前桌面已完成迁移：当前 `.bean` 与 Finance Service 仍存在；ADR 0014 的 Finance SQLite 真源方向取代 ADR 0011 所依赖的“各端可写 `.bean` + 独立 finance/v1 同步”路线。迁移前不得形成 SQLite / `.bean` 双真源。

当前旧 Journal/Health 同步、desktop Garmin collector 和 TickTick 直连行为也不因本文自动改变。任何实现必须另立 L3 计划，给出当前数据审计、迁移、兼容、回滚、真实设备验收和单写入 cutover 证据。

## 8. 实施门槛

先完成：

1. Registry 与 ADR 字段收束：Health Day identity、Plan Group、ScheduleBlock detail、Work/Plan 字段差异；
2. Core protocol/identity/canonicalization/aggregate map；
3. PC 与手机本地 SQLite replica、outbox/inbox/shadow、冲突与 bootstrap；
4. Server Core 的 current/history/change log/delivery/backup/Sync Doctor；
5. Garmin Ingest discovery/reconciliation 后的单 writer cutover；
6. 最后才是独立的 Schedule Adapter 计划。

任何环节没有 `opId / traceId / deliveryId` 的可追溯证据、没有 crash/replay/conflict/fence/ACK 故障演练，或让外部 adapter 绕过 Core 时，都不得上线真实 Archive 数据。
