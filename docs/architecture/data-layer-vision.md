# Orbita 数据架构演进方向

> **性质**：长期架构方向，不是当前版本的实现计划，也不是当前代码事实。  
> **适用**：设计 Orbita Archive、Orbita Insight、跨领域关联、时间线或 AI 洞察前。  
> **当前实现事实**：见 [`../CURRENT.md`](../CURRENT.md) 与 [`../SYSTEM.md`](../SYSTEM.md)。

## 1. 核心思想

Orbita 的目标不是建立一个包含所有数据的“大数据库”。它更接近：

> 一个连接个人数据、保留人生上下文、支持长期理解的个人数据系统。

不同领域保留自己的专业结构：健康有健康模型，财务有财务模型，知识有知识模型，媒体有媒体模型。Orbita 不强行把它们压成一张万能表，而是在它们之上增加连接机制，让不同数据形成上下文。

> 保留领域独立性，通过连接产生整体理解。

这条原则同时约束产品与工程：新功能优先扩展所属领域；只有跨领域的共同问题才进入 Archive 的公共约定。不能为了“统一”而把一顿饭、一次骑行、一笔交易、一张照片都改造成同一种 `Event`。

## 2. 产品与数据的边界

Orbita 是一个应用，界面层为：

```text
Orbita
├── Orbita Panel    # 日常进入、今日查看、快速记录
└── Orbita Insight  # 回看、整理、管理、深入操作
```

Panel 与 Insight 都是界面，不是各自的数据仓库。它们读取、写入同一套 Orbita 数据域，只是交互深度不同：Panel 偏当下与低摩擦，Insight 偏历史、管理与关联。

数据层的长期名称是 **Orbita Archive（Orbita 个人档案）**。它保存或稳定指向用户的长期事实；它不是第二个应用，也不是一个 UI tab。

```text
Orbita Archive
├── Orbita Journal
├── Orbita Finance
├── Orbita Health / Exercise
├── Knowledge
├── Media
└── Future: 跨领域关联（未定名）
```

## 3. 当前阶段：单根目录的 Archive 基础

当前实现中，`dataDir` 同时承载应用状态和个人档案数据；也就是说，`dataDir` 与未来概念中的 `archiveRoot` **尚未物理分离**。

```text
当前
dataDir = App State + Orbita Archive

未来可演进为
dataDir     = App State
archiveRoot = Orbita Archive
```

这不是当前阻塞项。现在不得为了“符合未来架构”而擅自移动目录、重命名配置字段或自动迁移用户数据。分根只在备份、跨机器、媒体体积或数据迁移确实需要时，以单独计划、明确确认和可回退方案处理。

当前 Archive 基础的成熟度并不一致：

| 领域 | 角色 | 当前判断 |
| --- | --- | --- |
| Orbita Journal | 每日、作息、餐食等结构化记录 | 已有基础能力。 |
| Orbita Finance | 账本与资产记录 | 正在迁入与收束；领域数据保留 bean/Beancount 语义。 |
| Orbita Health / Exercise | Garmin 健康、活动与原始运动文件 | 已有同步和归档基础。 |
| Knowledge | Zotero、Obsidian 等知识系统 | 主要仍是外部连接，不应假装已完整归档。 |
| Media / Trail | 照片、视频、轨迹 | 方向已定，完整索引和管理尚未实现。 |
| AI conversations | 对话与辅助输出 | 可保存为记录，但 AI 输出不是档案事实本身。 |

## 4. Archive 保存什么

Orbita Archive 的职责是：

> 保存事实。

例如：什么时候吃了一顿饭、在哪里骑了一次车、花了多少钱、看了一篇论文、拍了一张照片。原始数据与领域记录优先；统计、缓存、缩略图、AI 总结和洞察可以重新生成，不能反过来取代真源。

每个领域仍拥有自己的模型和真源：

| 领域 | 领域对象例子 | 当前/预期存储语义 |
| --- | --- | --- |
| Orbita Journal | `daily`、`routine`、`meal`、随记 | 按 Journal 自己的条目与日期规则。 |
| Orbita Health | 日汇总、睡眠、活动、`.fit` | Garmin 是外部来源；原始运动文件优先保留。 |
| Orbita Finance | 账户、分类、交易、余额 | Ledger 是内部账本模型；当前底层为 bean/Beancount，不改成通用事件。 |
| Knowledge | 论文、笔记、阅读记录 | 保留 Zotero/Obsidian 的边界；可先存引用和元数据。 |
| Media | 照片、视频、轨迹 | 原文件与稳定元数据/路径，后续再做索引。 |

外部工具不是 Orbita 的敌人。Garmin、Beancount、Zotero、Obsidian、TickTick 可以继续各自擅长记录和操作；Orbita 的价值在于档案、上下文和连接，而不是把所有工具重写一遍。

## 5. Connection：跨领域关联（仍待设计）

Connection 的工程形态与正式名称都**尚未定案**。Obsidian 双链只是帮助理解的类比：它提示我们“已有对象之间可以双向关联”，但不代表 Orbita 的第一版必须照搬 Obsidian。

```text
Obsidian：笔记 A ↔ 笔记 B
Orbita：Journal 条目 ↔ 骑行记录 ↔ 交易 ↔ 照片 ↔ 地点 ↔ 知识记录
```

目前能确定的边界是：关联不复制或改写主数据；它只描述已有档案对象之间的上下文。第一步不需要图数据库，也不需要 AI 自动理解人生。

### 5.1 候选方向：Context

一次旅行、一个项目、一段时期并不只是两条数据之间的边，而是能汇集多种记录的上下文。**Context（上下文卡片）** 是一个值得验证的候选方向：

```text
Context：2026 年川西旅行
├── 3 次骑行
├── 12 笔交通与住宿消费
├── 多张照片
├── 多条随记
└── 一条路线
```

Context 不取代任何领域对象，只保存它们的引用。用户从任意一条骑行、交易或随记进入时，也可以看到反向关联到的 Context。

是否以 Context 作为第一步、由用户手建还是由系统提出候选，尚未决定。它只是当前最容易说明“同一段经历被不同系统拆散”这一问题的模型。

### 5.2 候选方向：Relation

当出现明确、高价值的两对象关系时，可能需要 `Relation`，例如：

```text
照片 A --拍摄于--> 骑行 B
午餐 A --由--> 交易 B 支付
```

如果采用 Relation，它不应只是自由文本标签，至少应有关系类型、来源、证据与状态；AI 建议的关系永远只是候选，不能自动成为事实。

```ts
type ArchiveRef = {
  domain: "journal" | "health" | "ledger" | "media" | "knowledge";
  type: string;
  id: string;
};

type Relation = {
  from: ArchiveRef;
  to: ArchiveRef;
  kind: string;
  source: "user" | "imported" | "rule" | "ai_suggested";
  evidence?: ArchiveRef[];
  status: "active" | "retracted";
};
```

`ArchiveRef` 是一种候选的公共引用信封：只统一“如何引用一个已有对象”，不统一对象的数据结构。无论 Connection 最终叫什么、采用何种存储，这种“引用而非改写领域模型”的边界值得保留。

## 6. 时间、语义与 Insight

### 时间是横切契约，不是万能表

时间不是普通字段，而是个人数据最重要的共同维度。它需要贯穿各领域：发生时间、记录时间、时间范围、时区、持续时间、来源与前后关系。

但不应为此先建一个万能 Timeline 数据库。每个领域先保存自己的时间语义；未来的时间线、索引或查询视图建立在这些记录之上。

```text
购买跑鞋 → 开始训练 → 训练提升 → 形成习惯
```

时间线应帮助系统理解“事情如何发生”，但必须可回到各领域原始记录。

### 语义是带证据的解释，不是事实

跨领域关联回答“什么和什么有关”；未来的语义能力才尝试回答“为什么可能有关”。

```text
事实：最近 30 天睡眠减少，训练频率增加。
统计：睡眠时长下降，训练次数上升。
推断：可能存在恢复不足。
```

任何 AI 或规则产生的解释都必须保留其依据、来源、时间和不确定性，并允许用户反驳、撤回或忽略。不能把“睡眠不足导致训练表现下降”写回为不可质疑的档案事实。

### Insight 是能力层，不是原始真源

Insight 的长期路径是：

```text
Orbita Archive
  → 跨领域关联（具体产品形态未定）
  → 带证据的统计与解释
  → Insight
  → 用户确认后的 Action
```

Insight 不应在每次打开时粗暴扫描大量原始文件，也不能脱离原始记录给结论。工程上可增加索引、统计和缓存；产品上必须允许用户从洞察回钻到事实、关联和证据。

Insight 的目标不是评价人生，而是发现长期趋势、行为模式、状态变化和数据之间的关系。Action 只能在用户控制与充分依据之上发生。

## 7. 明确不做

- 不把所有领域对象塞入一个万能 `Event` 模型。
- 不为了统一语言或数据库而重写 Garmin、Beancount、Zotero、Obsidian 等专业系统。
- 不把 AI 推断、统计结果或缓存当作原始事实。
- 不在没有真实场景前引入图数据库、自由关系网络或复杂本体。
- 不把跨领域关联的实现作为拆分 `dataDir` / `archiveRoot` 的前提。
- 不在没有用户确认时让 AI 自动建立会影响理解、行动或归因的关系。

## 8. 建议演进顺序

| 阶段 | 目标 | 关键产物 | 暂不做 |
| --- | --- | --- | --- |
| A. Archive 基础 | 各领域事实可靠保存 | 领域模型、原始文件、稳定数据根 | 统一万能模型。 |
| B. 可引用性 | 能稳定指向跨领域对象 | 各领域稳定 id、基本时间/来源元数据 | 自动关联。 |
| C. 关联原型（候选） | 验证“经历上下文”是否有价值 | 可选的上下文卡片、双向浏览或其他原型 | 把候选模型当最终模型。 |
| D. 明确关系（候选） | 验证少量关系类型是否必要 | 若采用，则带来源/证据/状态 | 自由图谱。 |
| E. Insight | 发现有依据的模式 | 可回钻的统计、提示与解释 | 人生总分、不可解释判断。 |

任何阶段要进入实施，都必须另开 `plans/` 文件，写清本轮范围、数据迁移、兼容性、用户确认点和验收条件。本文件不提供任务 checkbox，也不代表这些阶段已被排期。

## 9. 仍待决定的问题

- `archiveRoot` 何时从当前共用的 `dataDir` 中物理拆出，以及迁移/备份如何做。
- Context 在第一版由用户手建、从记录页创建，还是先由 AI 仅提出候选。
- Connection 的首个产品形态究竟是 Context、对象间 Relation、时间线浏览，还是另一种尚未提出的模型。
- 哪些领域对象已有稳定 id，哪些需要先补引用策略。
- Media、Knowledge 是否保存完整副本、稳定引用，还是两者并存。
- 哪些 Relation 类型有足够明确的用户价值，值得成为正式类型。

这些问题不能由代码审查或 AI 擅自“补全”。每一项进入实现前都应形成独立 plan，并在必要时补充 `DECISIONS.md`。

## 10. 架构原则

1. 不替代已有工具，而是连接它们。
2. 原始数据优先，AI 结论不是最终事实。
3. 保留领域模型，不追求万能数据库。
4. 时间是个人数据最重要的维度。
5. 关联让独立数据获得上下文，但关联本身必须可追溯。
6. AI 的价值来自理解上下文，而不是简单记住聊天。
7. Orbita 服务的是时间中的自己，而不是某个标准模板中的自己。
