# 感知流畅与可信完成反馈

- Status: Accepted
- Date: 2026-08-22

## Context

Orbita 的长列表、侧栏与保存操作都可能同时触发网络、持久化、重载、统计和复杂布局。若把用户反馈绑定到所有派生工作完成，用户会把后台延迟感知为“软件卡住”；若在核心事实未确认前显示成功，又会制造不可信的假成功。

Finance 已暴露两类具体风险：侧栏逐帧改变主列表宽度会触发整页重排；账本 Commit 已成功后仍等待权威 reload、列表重算和余额审计，会让绿色成功勾迟到。该原则适用于所有 Orbita 领域，而非 Finance 专属实现。

## Decision

### 可信完成与派生刷新分离

- 绿色勾只表示用户的**核心意图已经由可信系统确认并可恢复**。对本地写入，这意味着原子持久化成功；对远端操作，这意味着服务端已确认其定义的核心事实。
- 核心事实尚未确认时使用进行中状态，不得提前显示绿色勾。仅入队、等待外部同步或尚未持久化的操作，使用“已提交 / 同步中”等不同语义，不复用绿色勾。
- 核心事实确认后立即显示绿色勾。重载、派生指标、余额审计、缓存填充、列表测量等后续工作在后台继续，不得阻塞成功反馈。
- 派生刷新失败不撤销绿色勾，也不得静默吞掉：在原操作位提供非阻塞的“已保存，刷新失败 · 重试”状态。
- 绿色勾后用户可以继续编辑。每次编辑或保存必须推进 generation/version；后台结果仅在仍对应当前 generation 时才可应用，过期结果必须丢弃，不能覆盖新编辑。

### 高成本布局变化的视觉平滑

- 含页面级容器、滚动区、长列表、卡片网格或复杂表单的布局变化，不得逐帧动画 `width`、`height`、`grid-template-*`、`flex-basis` 或会导致同类重排的外边距。
- 这类场景先一次完成逻辑布局切换，再以 `transform` / `opacity` 或 FLIP 处理视觉过渡。小型、孤立且不会牵连复杂后代的元素不受此限制。
- 主内容有既定最大宽度时，侧栏开关不得将其拉满或遮住。外层可用空间改变后，主内容保持宽度，仅平移到新的居中位置。

## Consequences

- 实现保存状态机时必须区分“核心完成”和“派生刷新”；不能以缩短动画或吞错伪造流畅。
- 实现侧栏、筛选区或窗口壳层时，先测量布局影响；涉及高成本子树时必须采用一次布局切换加合成层动画。
- 新的异步操作需要在设计时明确核心事实是什么、何时可显示成功、哪些工作是派生刷新，以及派生失败的局部重试入口。

## Alternatives considered

- 等待所有后台任务完成后才显示成功：状态最少，但把非关键延迟暴露为交互卡顿，未采用。
- 在核心持久化前乐观显示成功：反馈快，但成功语义不可信，未采用。
- 通过逐帧扩缩主内容或以 drawer 覆盖主内容来避免重排：前者造成长列表卡顿，后者改变既定的空间语义，未采用。

## Open questions

- 各领域迁移到此状态模型的具体计划与验收应在对应领域计划中记录。
